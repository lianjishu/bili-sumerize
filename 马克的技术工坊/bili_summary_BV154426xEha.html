视频内容介绍

00:00 – 01:08 · 1 节 · 1 分 08 秒

开场先替观众把最容易冒出来的那句话说了：「装个 Codex 或 Claude Code，发条指令不就行了吗？」UP 主的回答是：软件确实做得出来，但真正的疑问是做出来的效果跟你想的是不是同一个东西。这一章用一分钟把全片要解决的问题、示范方式和边界交代清楚。

1.1真问题：做出来的是不是你要的

00:00 – 01:08

UP 主一上来就预设了质疑：「给我做个笔记软件、给我做个剪辑软件、给我做个电子书阅读器，这不是太简单了吗？还要你来教？」——他承认这个质疑是成立的：给 AI 一个指令，它确实可以帮你把软件做出来。

本片要回答的问题
  • AI 做出来的效果，真的跟你预期的一样吗？
  • 有没有可能你脑子里想的是一个东西，AI 最后交付的完全是另一个东西？
  • 更不用说有些时候，AI 做出来的产品还有很多 bug，跟自己想象的效果相差甚远。

「相信你多多少少都会遇到过这种情况吧」——UP 主用这句话把问题定位成普遍经验，然后给出本片的命题：怎么才能够让 AI 交付一个真正让你满意的作品。

本片的示范方式
  1. 从头做一个电子书阅读器（UP 主给它起名叫「马克阅读」），把完整流程走一遍。
  2. 你会发现这不是「给 AI 发条指令就完事了」，中间要经历好几个步骤。
  3. 不只走流程，还说明每一步到底解决了什么问题、哪些环节可以省、哪些最好不要省。
这一章定下的调子
  • 目标不是给你一套「标准答案」，而是让你理解每一步的作用，从而把它调整成适合自己的 AI 工作流。
  • 这也是本片最有价值的地方：它讲的是流程为什么这样设计，而不是某几个具体按钮怎么点。

「我不仅会带你把流程完整走一遍，还会告诉你每一步到底解决了什么问题。哪些环节可以省，哪些环节最好不要省。理解了这些，你就能把它调整成适合自己的 AI 工作流。」

—— UP 主原话（00:54 前后）

01:08 – 02:24

03

环境搭建

02:24 – 06:26 · 2 节 · 4 分 02 秒

这一章 UP 主花了 4 分钟演示，但结论只有一句话：环境搭建总结下来就两件事——Git 和 AGENTS.md。前者保证「改坏了能退回去」，后者保证「AI 每次开工都记得该守什么规矩」。这两件事是全片唯一一次性的投入。

3.1建目录 + 让 AI 初始化 Git 仓库

02:24 – 03:58

第一步是给产品建一个专门的文件夹，专门存放项目代码。UP 主要做的产品是电子书阅读器，就给它起名叫「马克阅读」，然后创建对应文件夹。

在 Codex 里建项目
  1. 打开 Codex，点里面的加号，创建一个新项目。
  2. 项目类型维持「本地」，点下一步。
  3. 把刚才创建好的「马克阅读」文件夹加进来，点创建项目。
  4. 发出指令：「帮我把当前的目录初始化为一个 Git 仓库」，然后提交。

等 Codex 干活的时候，UP 主顺手给不了解 Git 的观众补了一段解释——这段解释的措辞很有意思，是他整片讲 Git 的基调：

Git 是什么（UP 主的原话解释）
  • 简单来说，Git 就是一个版本管理工具。
  • 我们每做完一个新功能，就可以用 Git 把它保存为一个对应的版本。
  • 这样即使哪天代码被搞乱了，也能够一键回退到之前的可用状态——非常高效，也非常好用。
  • 实际上建议你所有的代码项目都拿 Git 来管理，甚至可以考虑把代码推送到 GitHub 上，这样即使本地代码丢了，也能从 GitHub 上把代码拉下来，防止之前的劳动成果付诸东流。
本片不演示 GitHub：UP 主明确说「否则视频会有些冗长」，所以只演示 Git 本体的用法，GitHub 留给大家自己找材料看。但在 CH7 讲三条原则时，他把「同步到远端仓库」又提了一遍——说明在他心里这属于「条件允许就做」的加强项，而不是必选项。

Codex 做完之后，UP 主打开终端验证：进入「马克阅读」文件夹，执行 git status 命令。「可以看到正常返回了，也没有报错，这就代表当前目录确实已经被 Git 接管了。」

这一节的可复制要点
  • 不用自己敲 git init，让 AI 做，然后自己用 git status 验证——这就是全片「AI 干活 + 人验证」的最小示范，后面每一步都是这个模式的放大版。
  • 「验证」这个动作从第一分钟就出现了，不是等到最后才做。

3.2AGENTS.md：给 AI 的项目说明书，两条硬规矩

04:28 – 06:26

环境搭建的第二件事，也是整个流程里最关键的一步配置：创建一个 AGENTS.md 文件。

指令是：「创建一个 AGENTS.md 文件，写入下面这些内容，最后提交一个 commit」，然后把文件内容贴进对话框一起提交。

AGENTS.md 是干什么的
  • AGENTS.md 相当于给 Codex 写的项目说明书。
  • 每次你开启一轮新的会话，Codex 就会优先读取里面的内容，从而快速了解当前的项目背景和开发规范。

UP 主在文件里写了两条必须遵守的规定。这两条是理解后文所有行为（尤其是 CH6 的「写完自测」）的钥匙：

规矩一
每次改动之后，都必须创建一个对应的 git commit，以便后续追踪和回滚
怎么理解
Codex 每完成一个功能，都要顺手帮我们保存一个版本快照；后面哪一步改出了问题，可以非常方便地找到之前正常的版本直接退回去，不用担心代码越改越乱
规矩二
每次改动之后都必须编写或更新相关的测试，并在交付给用户前确保所有的测试和验收全部通过
为什么这样写
不希望 Codex 写完代码就直接交差，而是希望它自己先跑一遍、测一遍，发现问题就继续修，直到能确认当前改动基本没有问题，再来告诉我们「完成了」——这样就能提前帮我们挡掉不少比较明显的 bug，节省我们的时间
这两条规矩的设计意图
  • 规矩一是给「改坏」买的保险——它不提高 AI 一次做对的概率，但保证做错时可以低成本撤销。
  • 规矩二是把「自测」从人的习惯变成 AI 的义务——这是全片反复强调的「给 AI 自测能力」的规则来源。
  • 两条都不是「让 AI 更聪明」，而是让 AI 的工作可回滚、可验证。这也正是 UP 主整片的方法论底色。

验证方式同样朴素：回到访达（macOS 文件管理器）看一眼，「可以看到文件确实是创建好了，内容也跟我们要求的是一模一样的」。

04

产品方案设计

06:26 – 14:43 · 4 节 · 8 分 17 秒

全片最长的一章，也是最「不写代码」的一章。UP 主在这里做的是三件事：跟 AI 对齐 MVP 边界、亲手把 AI 提的功能一条条砍掉、把共识固化成一份产品设计文档。最后还多讲了一步可选的 demo 环节，并给出「什么时候该做 demo」的判断标准。

4.1先跟 AI 对齐 MVP 边界

06:26 – 08:03

现在知道要做一个电子书阅读器，但具体要做成什么样子，其实心里还没有一个非常确切的答案。UP 主的做法是：先跟 AI 讨论一下产品的设计。

第一句指令（原文）

「我想做一个电子书阅读器，打算先从 MVP 版本开始，你觉得这一版做哪些功能比较合适呢？」

UP 主预判了观众会问「MVP 是什么」，顺手给出了定义和理由——这段解释把整章的思路交代得很清楚：

MVP 是什么
Minimal Viable Product 的缩写，中文一般叫最小可用产品
具体含义
第一版只做最核心、最必要的功能，先把产品的主流程跑通，其他功能以后可以慢慢加
这样做的好处
可以用比较低的成本快速验证产品方向。如果一开始就把功能铺得太大，后面发现方向不对，很多工作可能就白做了
所以本片的做法
先把电子书阅读器最基本的体验做出来，确定没问题后，再逐步往上加功能
关于 MVP 的拼写：UP 主口播为 Minimal Viable Product，通行写法是 Minimum Viable Product。这是口播习惯而非事实错误，本笔记保留原话。

AI 的回答里提了一批功能建议，UP 主逐条看下来，一场「砍需求」就开始了。

4.2逐条砍需求：从 EPUB 一路砍到 TXT

08:06 – 10:19

这一节是全片信息密度最高的演示之一。UP 主的操作习惯很值得学：看完 AI 的回答再统一回复，不急着一条一条提交——「有问题直接追加到输入框里面，最后一起提交」。

砍需求的五刀
  1. 导入格式：EPUB → TXT。「EPUB 是一个非常常见的电子书格式，支持这种格式是没有什么问题的。不过我觉得这个格式可能还是稍微有一些复杂度……一开始就支持导入 TXT 文本文件就行了。」
  2. 目录与章节：直接去掉。「如果只做 TXT 的话，那基本上也就没有什么目录和章节可言了 […] 毕竟 TXT 没有目录和章节的概念，即使有的话，那也不是能够通过固定方法解析到的，那这些也不用做了。」
  3. 主题：三种 → 一种。AI 建议同时支持明亮、护眼、深色三种主题。UP 主：「我们一开始不用支持这么多，就先做明亮主题就好了，护眼和深色可以先不做。」
  4. 书签：不做。「书签其实我们也不需要，因为它们不是必要功能，所以书签也可以先不做。」
  5. 收口。追加一句总纲：「总之我们先做最基本的功能，其余的功能后面再迭代」，并主动反问 AI：「你觉得前面这些想法有没有什么问题呢？」

砍完之后，AI 的回答里提了几个要注意的点，UP 主的反应是「可以的，这些我都赞同」：

文件编码
建议第一版仅支持 UTF-8 就行
阅读方式
第一版只支持纵向滚动，先不做分页
大文件
载入大文件需要给出一些提示
额外产出
还给出了一个可以推迟的功能列表
这一节的方法论
  • 批注式对话，而不是逐条往返：边看边把意见追加进输入框，最后一起提交 —— 省掉了大量往返轮次。
  • AI 是提案方，人是裁决方：功能清单由 AI 起头，但「砍到多小」是人决定的。
  • 砍完要回问一句：既暴露了 AI 的判断，也顺手拿到了编码、滚动方式这些自己没想到的工程细节。

4.3出产品设计文档，但「不用太详细」

10:16 – 11:24

共识谈完，接下来要把它固化下来：整理成一份产品设计文档，当作后续开发的提纲。

为什么必须有这份文档
  • 「这样无论后面是做技术方案，还是让 AI 写代码，大家都有一个统一的依据。」
  • 「简单来说，这份文档就是先把 MVP 的边界给定下来。」

发指令的时候，UP 主特意停下来提醒大家注意他的措辞：

措辞要点：明确说「不用太详细」
  • 指令原文：「我同意你的建议，接下来帮我整理一份产品设计文档，不用太详细，把整体方向和主要功能梳理出来就可以。」
  • 他的理由：「否则字太多了，我们看起来也累，差不多就行了。」
  • 底线：「我们只需要保证大体方向跟我们想的一致就行。如果真的有什么细节跟我们预期的不太一样，后面再迭代就好了。」
这是一个反直觉的建议：很多人以为文档要越细越好。UP 主的逻辑是——文档的读者首先是「接下来要读它的 AI 和你自己」，过细的文档既增加阅读成本，又容易让人误以为「写得这么细一定对」。所以他只要「方向 + 主要功能」，细节留给迭代。

文档写完，「好像是没什么问题，那就这样吧」——产品设计方案基本确认。

4.4demo 要不要做：看后端实现成本

11:26 – 14:43

产品设计的最后，有些时候 UP 主还会再做一个环节：让 AI 画一个 demo。这一节把 demo 是什么、有什么好处、以及「什么时候值得做」讲透了 —— 而这一期的电子书阅读器，他最后并没有做。

demo 是什么
可以把它理解成一个可以实际操作的前端页面
前端
指我们看得见、点得到的界面
后端
与前端相对应，指背后真正处理数据、执行功能的那些逻辑
做 demo 时
通常只把前端做出来，后端暂时不实现，里面的数据一般也都是直接模拟的

UP 主用自己准备的一个「个人知识库」demo 做示范（他特意说明这个 demo 跟本期的阅读器没关系，只是拿来解释 demo 长什么样）：

这个 demo 的形态
  • 它其实就是一个 HTML 文件，直接打开就行。
  • 左边是文档列表，中间系统给出了一些推荐问题。
  • 点击一个推荐问题，它就开始回答；回答完毕之后点「引用文件」，右边就会展示回答所引用的原文。
  • 但注意：「这里面只有前端页面是真的，这个回答和相关的这些示例文件，其实都是模拟的，因为后端逻辑还没有实现。」

「这个页面仅仅是包含前端逻辑，它的主要目的就是为了让用户体验一下整个界面的交互和操作流程到底顺不顺手。如果哪里感觉不对，就可以继续让 AI 修改这个 demo，直到整体体验比较符合我们的预期为止。」

做 demo 的两个好处
  1. 提前验证产品设计。「很多东西光靠文字其实很难想象。真正把页面画出来、亲自操作一下之后，你可能就会发现一些之前没有想到的问题。」发现设计不合理，就继续改 demo，同时把对应的产品设计文档一起调整。
  2. 让后面的产品实现更精确。demo 可以非常直观地告诉 AI「我最终想要的产品大概就是这个样子」——「这个是文字描述很难做到的」。后面实现时把产品设计文档和 demo 一起交给 AI，它既知道要做哪些功能，也知道界面和交互应该怎么还原，做出来的东西一般会更加接近预期。

那到底什么时候适合做 demo？UP 主给了一个非常干脆的判断标准：

判断标准：这个产品的后端实现成本
  • 只看这一个因素，不看项目大小、不看技术难度。
本章收束
  • 产品设计环节正式结束。产出物只有一个：一份「不用太详细」的产品设计文档，它的唯一职责是把 MVP 边界钉死。
  • demo 是可选加分项，判断标准是后端实现成本；本期不需要，所以跳过了。

技术方案设计

14:43 – 17:17 · 2 节 · 2 分 34 秒

产品定了「做什么」，这一章定「用什么做」。UP 主的做法和上一章同构：先讨论方向，再落成文档。中间顺带回答了很多人关心的「上下文会不会越聊越坏」的问题。

5.1技术栈讨论：Electron 与 Tauri

14:43 – 16:40

技术方案可以直接在当前会话后面继续追问，也可以创建一个新的会话——两种方式都可以。UP 主先讨论了「要不要新开会话」这个问题，因为它牵出一个常见顾虑。

上下文会不会越聊越坏？
  • 顾虑：在当前会话继续追问，上下文越记越多，对大模型的效果可能就会有一定程度的影响。
  • UP 主承认：「确实有这种可能性。」
  • 但他的实际体会是：现在的顶级模型对长上下文的驾驭能力越来越强了，再加上对应的上下文压缩机制，正常使用的话一般不用过于担心上下文的问题。
  • 他的实测：「我甚至经常在一个会话里面连续跑几个小时，都没有感觉到有什么太大的问题。」
  • 但他仍然选择新开：「不过为了稳妥一点，也为了让后面的技术方案讨论更为聚焦，我们这里还是新开一个会话，专门来做技术方案的设计。」
这个选择本身很有信息量：他不是因为「上下文一定会坏」才新开，而是因为新开会话能让话题更聚焦。也就是说，新开会话在 UP 主这里是一个「组织话题」的动作，而不是「防止模型退化」的补救措施。

和产品设计一样，技术方案也是先跟 AI 讨论可能的技术设计方向，让它给一些建议。UP 主给了一个很实用的场景：你可能听说 Electron 非常适合做这件事，但你对它没那么熟、拿不定主意——「这个时候你就可以把你的想法跟 AI 说一下，让它帮你看看 Electron 合不合适。」

讨论用的指令（原文）

「在这个目录下面有一份产品设计文档，请你读一遍这个产品设计文档，然后告诉我用什么技术栈设计这个产品比较合适。不用给出过于详细的设计，我们就先探讨一下。我听说 Electron 还可以，你怎么看呢？」

注意这句指令的三个动作：指向已有文档（给它上下文）→ 要技术栈建议（要方向）→ 明确说不用太详细（控成本）→ 把自己的猜测抛出来让它评估（要判断而不是要列表）。和上一章「不用太详细」是同一套控本思路。

AI 的回答：Electron 非常合适、会优先采用，给出了建议的技术栈，同时也给出了 Electron 的缺点，以及另一个可能的选项 Tauri。最后总结出这套架构：

指令（原文）

「行就按你说的来，现在请你写一个技术方案，放在 docs 文件夹里面。」

产品实现

17:17 – 20:15 · 3 节 · 2 分 58 秒

真正敲代码的一段，只占全片 12%。UP 主在这里插了一个「动手前必须做的配置」——先给 AI 一副能自己验证的眼睛，然后才让它实现。而最后那个「上来就报错」的插曲，恰好把整套流程的必要性演示了一遍。

6.1装 Computer Use 与 Chrome 插件：先给 AI 眼睛

17:22 – 18:12

「在正式编写代码之前，我先提一句——我们最好让 AI 拥有自行验证结果的能力。」这是 CH3 那条「规矩二」的落地条件：规矩要求它自测，那就得先给它能测的工具。

用 Codex 的话，建议至少装两个插件
  1. Computer Use —— 可以用来操作电脑。
  2. Chrome —— 可以用来查看 Chrome 页面。

「有了这两个插件，大部分的功能都是可以交给 AI 来验证的，包括我们现在做的这个电子书阅读器也是同样的道理。」如果用别的编程 Agent，「那可以自行查找下对应的插件或者是 skill」。

不给验证环境的后果
  • AI 只会写、不会验 ——「很容易就会写出一堆 bug」，毕竟它没法验证。
  • 人被迫下场当测试员：「来来回回帮 AI 找 bug，极其浪费时间」（这句在 CH7 原则二里被再次点名）。
  • 所以这一步省下的时间，会在后面的来回沟通里成倍还回去。
这一步的定位
  • 它不是「可选优化」，而是让 AGENTS.md 里那条测试要求真正能被执行的前提。
  • 换句话说：规矩是写给人看的，插件是写给 AI 用的——两者缺一，自测都会退化成「AI 声称自己测过了」。

6.2带着两份文档实现，并自己跑测试

18:14 – 19:17

配置好之后，新建一个会话，让 AI 开始实现。指令的设计和前面一脉相承：不重复需求，只指路。

实现用的指令（原文）

「这个目录下面有两个文档，一个是产品设计，一个是对应的技术方案，请你读一下这些文档，然后根据里面的要求实现这个产品。」

「接下来我们稍微等一下，写代码估计要花不少时间。」这里 UP 主没有在提示词里复述任何需求细节——因为细节都已经在前面两份文档里了。这正是 CH4、CH5 坚持要产出文档的直接回报。

结果
「可以看到他不仅把产品做完了，还完成了各种自测，确保他写的代码没有问题」
为什么会有自测
「这符合我们在 AGENTS.md 里面的要求」——即那条「每次改动后必须编写或更新相关测试，并在交付给用户前确保所有测试和验证全部通过」
UP 主的追问
「你是不是都忘了我们在 AGENTS.md 里面写了什么了？没关系，我再给你看一下」
自测能保证什么（UP 主特意划的边界）
  • 「这些测试只能尽可能提高代码的可靠性，帮 AI 提前发现一些明显的问题。」
  • 「并不能够保证最终交付出来的产品就一定没有 bug。」
  • 「真正用起来怎么样，还是得我们自己亲自验证之后才知道。」

这段边界说明很关键：它提前把「有了自测就可以完全放手」这个念头掐掉了，也直接把叙事推到下一节——亲手跑一遍。

6.3亲手跑一遍：第一个报错

19:17 – 20:15

AI 最后提到「执行 npm start 命令就可以启动」。UP 主这就来试试——结果「似乎上来就报了一个错」。

本章小结
  • 动手前先配好验证环境（Computer Use + Chrome），让「自测」这条规矩可执行。
  • 实现时只指路、不复述需求——回报来自前面两份文档。
  • AI 自测能挡掉明显问题，但挡不住全部；人亲手跑一遍是必需的最后一道。
  • 遇到报错的处理姿势：描述现象 → 交给 AI → 再跑一遍验证，人不下场 debug。

7.2参与度取舍：简单不重要 vs 复杂重要

21:41 – 23:11

「当然这几个步骤并不是死板的流程。」UP 主接着给出了全片最重要的一句判据：具体要做到什么程度，取决于你想对最终结果保留多少掌控力。

两个可以整章跳过的环节
  • 如果你并不在意产品具体该怎么设计，只要功能能用就行 → 产品设计这一步可以完全不用管，交给 AI 就行了。
  • 如果你也不关心代码具体怎么实现 → 技术方案同样也可以不用关心，让 AI 自己决定。
  • UP 主的评价：「这么做其实并没有什么太大问题。」
代价是什么
  • 「只是意味着你把更多的决策权交给了 AI。」
  • 「这样的话你对最终结果的掌控自然就会少一些，做出来的东西可能也就没有那么贴合你的预期。」

所以这本质上是一种取舍——UP 主把它讲得非常对称：

参与得越多
对最终结果的把控就会越强，但需要投入的时间和精力也就越多
参与得越少
开发过程会更省事更快，但最终结果和你预期之间出现偏差的可能性也会越高
怎么定这个度
「这个度其实没有一个特别固定的标准。我一般会根据需求的复杂度和重要性来判断。」

7.3三条不能省的原则

23:13 – 24:32

「尽管流程可以根据需求灵活调整，但有三个原则我建议大家尽量坚持。」这是全片最该抄下来的三句话。

原则一：必须有版本管理工具
  1. 比如你可以用最流行的 Git 来管理代码。
  2. 「AI 写代码不可能每次都完全正确，有时候甚至会在修改的过程中把原本能够正常运行的功能改坏。」
  3. 用了 Git 之后，每完成一个功能都可以保存一个对应的版本，后面一旦出了问题，就能很方便地回到之前正常的状态。
  4. 另外如果条件允许，也建议把代码同步到 GitHub 之类的远端仓库——这样即使本地代码不小心丢了，也能够从远端恢复。
原则二：必须给 AI 自测的能力
  1. 「很多人只是让 AI 写代码，但不给它验证的环境。」
  2. 结果是「自己就沦为了测试员，来来回回帮 AI 找 bug，极其浪费时间」。
  3. 正确做法：「我们应该把相关的工具和插件开放给 AI，让它自己写完自己测，这样交付出来的代码质量就会高很多。」
原则三：必须进行人工验证
  1. 「AI 自测再充分，也不可能把所有的问题都覆盖到。」
  2. 容易被漏掉的是：「像交互体验，或者是一些不容易想到的边界情况。」
  3. 所以「产品到底好不好用、是不是我们真正想要的，最终还是要自己试一遍才知道」。
总结：真正不能省的就是这三件事
  • 用 Git 搭建好环境
  • 让 AI 具备自测能力
  • 最后还一定要人工验证
  • 至于产品设计和技术设计要做得多细，「大家看情况决定就好」。
和前面章节的对应关系：原则一 = CH3 的规矩一（每次改动必须 commit）；原则二 = CH3 的规矩二 + CH6 的两个插件；原则三 = CH6 第 3 节那次「上来就报错」。三条原则在前面的演示里都已经出现过一次 —— 这一章只是把它们从操作里抽出来命名。
