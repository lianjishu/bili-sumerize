1.1真问题：做出来的是不是你要的

00:00 – 01:08

UP 主开场先替观众把最容易冒出来的质疑说出来：装个 Codex 或者 Claude Code，直接向 AI 发条指令不就行了？「给我做个笔记软件，给我做个剪辑软件，给我做个电子书阅读器」——这不是太简单了吗？还要你来教？

他先承认这个质疑成立：给 AI 一个指令，它确实可以帮你把软件做出来。然后才把问题往前推一步。

本片要回答的问题
  • AI 做出来的效果，真的跟你预期的一样吗？
  • 有没有可能你脑子里想的是一个东西，AI 最后交付的完全是另外一个东西？
  • 更不用说有些时候，AI 做出来的产品还有很多 bug，跟自己想象的效果相差甚远。

「相信你多多少少都会遇到过这种情况吧」——UP 主用这句话把问题定位成普遍经验，然后给出本片的命题：怎么才能够让 AI 交付一个真正让你满意的作品。

示范方式是从头做一个电子书阅读器，把完整流程走一遍。他给自己的产品起名叫「马克阅读」。他强调这不是「给 AI 发条指令就完事了」，中间要经历好几个步骤；而且要讲的不是流程图，是每一步到底解决了什么问题。

「我不仅会带你把流程完整走一遍，还会告诉你每一步到底解决了什么问题。哪些环节可以省，哪些环节最好不要省。理解了这些，你就能把它调整成适合自己的 AI 工作流。」 —— UP 主原话（00:54 前后）

最后那句「调整成适合自己的 AI 工作流」，是本片最该抓住的一句：它意味着后面给出的流程不是一套必须照搬的规程，而是一个可以被裁剪的模板——这也解释了为什么 CH7 会专门用一整节讲「参与度取舍」。

本章小结

  • 被解决的问题不是「AI 能不能做出软件」，而是「做出来的东西是不是你要的」。
  • 全片以「从零做一个电子书阅读器」为示范载体，最终交付一个 MVP。
  • 本片讲的是可裁剪的流程模板，不是固定规程；目标是让观众能改造成自己的工作流。

思考题（整理者补充）

  1. 回想一次「AI 交付的不是你要的」经历：当时的偏差出在需求没说清，还是出在没人验证？
  2. 如果把「让 AI 交付一个真正满意的作品」当成目标，你觉得最容易被跳过的是哪一步？为什么？

3.1建目录 + 让 AI 初始化 Git 仓库

02:24 – 03:58

环境搭建的第一步是给产品创建一个专门存放项目代码的文件夹。UP 主要做电子书阅读器，就给它起名叫「马克阅读」，然后创建对应文件夹。

接着在 Codex 里建项目：打开 Codex → 点里面的加号创建新项目 → 项目类型维持「本地」 → 下一步 → 把「马克阅读」文件夹加进来 → 点创建项目。然后在对话框里发第一条指令：

「帮我把当前的目录初始化为一个 Git 仓库。」 —— 第 1 条指令（03:14 前后）

等 Codex 干活的时候，他顺手给不了解 Git 的观众补了一段解释。这段解释的措辞值得原样记下来，因为它就是全片讲 Git 的基调：

Git 是什么（UP 主的原话解释）
  • 简单来说，Git 就是一个版本管理工具。
  • 我们每做完一个新功能，就可以用 Git 把它保存为一个对应的版本。
  • 这样即使哪天代码被搞乱了，也能够一键回退到之前的可用状态——非常高效，也非常好用。
  • 实际上建议你所有的代码项目都拿 Git 来管理，甚至可以考虑把代码推送到 GitHub 上，这样即使本地代码丢了，也能从 GitHub 上把代码拉下来，防止之前的劳动成果付诸东流。

他明确说本片不演示 GitHub 的使用，「否则视频会有些冗长」，让大家自己找材料看。但在 CH7 讲三条原则时，他把「同步到远端仓库」又提了一遍——说明在他心里这属于「条件允许就做」的加强项，不是必选项。

Codex 做完之后，UP 主打开终端验证：进入「马克阅读」文件夹，执行 git status。「可以看到正常返回了，也没有报错，这就代表当前目录确实已经被 Git 接管了。」

这一节的可复制要点
  • 不用自己敲 git init，让 AI 做，然后自己用 git status 验证——这就是全片「AI 干活 + 人验证」的最小示范，后面每一步都是这个模式的放大版。
  • 「验证」这个动作在第一分钟就出现了，不是等到最后才做。

本节小结

  • 建项目：专门目录 + Codex 本地项目。
  • 第一条指令不是写代码，而是把目录纳入版本控制。
  • 验证靠人：git status 无报错 = 目录已被 Git 接管。

思考题（整理者补充）

  1. 为什么 UP 主把「初始化 Git」放在写第一行代码之前？如果放到后面会损失什么？
  2. 你的项目里，除了 Git 之外还有别的「可回滚保障」吗？

3.2AGENTS.md：给 AI 的项目说明书，两条硬规矩

04:28 – 06:26

环境搭建的第二件事，也是整个流程里最关键的一步配置：创建 AGENTS.md 文件。

「创建一个 AGENTS.md 文件，写入下面这些内容，最后提交一个 commit。」 —— 第 2 条指令（04:28 前后）；文件内容也一起贴进对话框

发完指令后，UP 主解释了AGENTS.md 的作用：

AGENTS.md 是干什么的
  • 它相当于给 Codex 写的项目说明书。
  • 每次你开启一轮新的会话，Codex 就会优先读取里面的内容，从而快速了解当前的项目背景和开发规范。

他在文件里写了两条必须遵守的规定。这两条是理解后文所有行为的钥匙——尤其是 CH6 的「写完自测」。

规矩内容UP 主的解释
规矩一每次改动后必须创建 git commit以便后续追踪和回滚。你可以大致理解为：Codex 每完成一个功能，都要顺手帮我们保存一个版本快照。后面如果哪一步改出了问题，就可以非常方便地找到之前正常的版本直接退回去，不用担心代码越改越乱。
规矩二每次改动后必须编写或更新测试，并在交付给用户前确保所有测试和验收全部通过我们不希望 Codex 写完代码就直接交差，而是希望它自己先跑一遍、测一遍，发现问题就继续修一修，直到它能够确认当前的改动基本没有问题了，再来告诉我们「完成了」。这样就能提前帮我们挡掉不少比较明显的 bug，节省我们的时间。
这两条规矩的设计意图
  • 规矩一是给「改坏」买的保险——它不提高 AI 一次做对的概率，但保证做错时可以低成本撤销。
  • 规矩二是把「自测」从人的习惯变成 AI 的义务——这是全片反复强调的「给 AI 自测能力」的规则来源。
  • 两条都不是「让 AI 更聪明」，而是让 AI 的工作可回滚、可验证。这正是 UP 主整片的方法论底色。

验证方式同样朴素：回到访达（macOS 文件管理器）看一眼，「可以看到文件确实是创建好了，内容也跟我们要求的是一模一样的」。

至此环境搭建完成。UP 主的总结只有一句话：「其实总结下来也就两件事情：一个是 Git，另外一个是 AGENTS.md。」接下来就可以正式进入产品设计环节。

本节小结

  • AGENTS.md = 每轮新会话优先读取的「项目说明书」，承载项目背景与开发规范。
  • 两条规矩分别管可回滚（每次改动必 commit）与可验证（每次改动必更新测试并跑通）。
  • 环境搭建 = Git + AGENTS.md，二者是全片唯一一次性的投入。

思考题（整理者补充）

  1. 如果只能在自己的 AGENTS.md 里写两条规矩，你会写哪两条？为什么？
  2. 规矩二要求「交付前确保所有测试和验收全部通过」——「验收」由谁定义？这会不会又回到「人来写测试」？
CHAPTER 04

产品方案设计

06:26 – 14:43　·　4 节　·　8 分 17 秒（全片最长）

4.1先跟 AI 对齐 MVP 边界

06:26 – 08:06

知道自己要做一个电子书阅读器，但具体要做成什么样子，「其实大家心里可能都还没有一个非常确切的答案」。UP 主的做法是：先跟 AI 讨论产品的设计。

「我想做一个电子书阅读器，打算先从 MVP 版本开始，你觉得这一版做哪些功能比较合适呢？」 —— 产品讨论的第 1 条指令（06:44 前后）

他预判了观众会问「MVP 是什么」，顺手给出定义：MVP 是 Minimal Viable Product 的缩写，中文一般叫做最小可用产品。含义是「第一版只做最核心、最必要的功能，先把产品的主流程跑通，其他功能以后可以慢慢加」。

为什么先做 MVP
  • 好处是「可以用比较低的成本快速验证产品方向」。
  • 反例：「你想如果一开始的时候，就把功能铺的太大，后面发现方向不对的话，很多工作可能就白做了。」
  • 所以本片的路径是：先把最基本的体验做出来，确定没问题后，再逐步往上加功能。

AI 随后给出一批功能建议（导入 EPUB、目录与章节、三种主题、书签等），一场「砍需求」就此开始。

存疑标注 UP 主口播为 Minimal Viable Product，通行拼写是 Minimum Viable Product。这是口播习惯而非事实错误，本讲义保留原话并在此加注。

本节小结

  • 产品设计从一句开放式提问开始，让 AI 先提案，而不是自己先写完需求再交给 AI。
  • MVP = 最小可用产品，目的是低成本验证方向，避免「功能铺太大」的返工。

思考题（整理者补充）

  1. 你的上一个项目，MVP 的边界是你定的还是AI 定的？结果如何？
  2. 「先把主流程跑通」——如果你现在做的产品就是主流程，你怎么判断它已经「跑通」？

4.2逐条砍需求：从 EPUB 一路砍到 TXT

08:06 – 10:19

这一节是全片信息密度最高的演示之一。UP 主的操作习惯很值得学：看完 AI 的回答再统一回复，不急着一条一条提交——「好，这个时候不要着急提交，因为我们还没有看完整个回答 […] 有问题直接追加到输入框里面，最后一起提交」。

他砍了五刀，每一刀都给了具体理由：

对象裁决UP 主的理由（大意）
导入格式EPUB → TXTEPUB 是很常见的电子书格式，支持它没问题，但「可能还是稍微有一些复杂度」。既然做最小可用版本，希望一开始越简单越好。
目录与章节去掉只做 TXT 的话「基本上也就没有什么目录和章节可言了 […] 即使有的话，那也不是能够通过固定方法解析到的」。
主题三种 → 一种「一开始不用支持这么多，就先做明亮主题就好了，护眼和深色可以先不做。」
书签不做「其实我们也不需要，因为它们不是必要功能。」
总纲收口「总之我们先做最基本的功能，其余的功能后面再迭代。」

最后一刀最容易被忽略，但可能是最有用的：他砍完之后反问 AI 一句——「你觉得前面这些想法有没有什么问题呢？」AI 随即给出了几条补充，UP 主的反应是「可以的，这些我都赞同」：

补充项内容说明
文件编码仅支持 UTF-8AI 建议第一版就只支持 UTF-8
阅读方式仅纵向滚动第一版先不做分页
大文件给出提示载入大文件需要给出一些提示
额外产出推迟清单AI 还给出了「可以推迟的功能列表」

「到这里，其实我们对第一版要做什么、暂时不做什么，已经有了一个比较明确的共识。」

这一节的方法论
  • 批注式对话，而不是逐条往返：边看边把意见追加进输入框，最后一起提交——省掉了大量往返轮次。
  • AI 是提案方，人是裁决方：功能清单由 AI 起头，但「砍到多小」是人决定的。
  • 砍完要回问一句：既让 AI 把异议说出来，也顺手拿到了编码、滚动方式这些自己没想到的工程细节。

本节小结

  • 砍需求不是「嫌多」，每一条都要有具体理由（太复杂 / 概念不存在 / 非必要）。
  • 砍完之后主动反问，把 AI 从执行者拉回评审者——这一步换来了 UTF-8、纵向滚动、大文件提示三条真正的工程建议。
  • 共识落地为一句可执行的边界：「只做最基本的功能，其余后面再迭代」。

思考题（整理者补充）

  1. 「砍掉 EPUB 只留 TXT」这个决定，牺牲了哪些可能性？换来了什么？
  2. 如果 AI 在第一步就把「编码、滚动方式、大文件提示」也提出来，你还会砍得这么干脆吗？

4.3出产品设计文档，但「不用太详细」

10:16 – 11:26

共识谈完，接下来要把它固化下来：整理成一份产品设计文档，当作后续开发的提纲。

为什么必须有这份文档
  • 「这样无论后面是做技术方案，还是让 AI 写代码，大家都有一个统一的依据。」
  • 「简单来说，这份文档就是先把 MVP 的边界给定下来。」

发指令的时候，UP 主特意停下来提醒大家注意他的措辞：

「我同意你的建议，接下来帮我整理一份产品设计文档，不用太详细，把整体方向和主要功能梳理出来就可以。」 —— 出文档的指令（10:34 前后）
为什么要说「不用太详细」
  • 他的理由很直接：「否则字太多了，我们看起来也累，差不多就行了。」
  • 底线：「我们只需要保证大体方向跟我们想的一致就行。如果真的有什么细节跟我们预期的不太一样，后面再迭代就好了。」
  • 「我觉得这样更方便一些。」

这是一个反直觉的建议：很多人以为文档要越细越好。UP 主的逻辑是——这份文档的读者首先是「接下来要读它的 AI 和你自己」，过细的文档既增加阅读成本，又容易让人误以为「写得这么细一定对」。所以他只要「方向 + 主要功能」，细节留给迭代。

文档写完，「好像是没什么问题，那就这样吧」——产品设计方案基本确认。

本节小结

  • 产品设计文档的唯一职责是钉死 MVP 边界，为后续技术方案与编码提供统一依据。
  • 刻意的「不用太详细」是一种成本控制：降低阅读负担，把细节留给迭代。

思考题（整理者补充）

  1. 你写过的需求文档里，有多少内容是 AI 根本不需要的？
  2. 「不用太详细」和「必须说清边界」如何共存？哪些内容属于「必须说清」的那一类？

4.4demo 要不要做：看后端实现成本

11:26 – 14:43

产品设计的最后，有些时候 UP 主还会再做一个环节：让 AI 画一个 demo。这一节把 demo 是什么、有什么好处、以及「什么时候值得做」讲透了——而这一期的电子书阅读器，他最后并没有做。

概念含义说明
demo可实际操作的前端页面「你可以把它理解成一个可以实际操作的前端页面」
前端看得见、点得到的界面「就是指我们看得见点得到的界面」
后端真正处理数据的逻辑「它指的是背后真正处理数据、执行功能的那些逻辑」
做 demo 时只做前端后端暂时不实现，里面的数据一般也都是直接模拟的

他用自己准备的一个「个人知识库」demo 做示范（特意说明这个 demo 跟本期的阅读器没关系，只是拿来解释 demo 长什么样）：

这个 demo 的形态
  • 它其实就是一个 HTML 文件，直接打开就行。
  • 左边是文档列表，中间系统给出了一些推荐问题。
  • 点击一个推荐问题，它就开始回答；回答完毕之后点「引用文件」，右边就会展示回答所引用的原文。
  • 但「这里面只有前端页面是真的，这个回答和相关的这些示例文件，其实都是模拟的，因为后端逻辑还没有实现」。

「它的主要目的就是为了让用户体验一下整个界面的交互和操作流程到底顺不顺手。如果哪里感觉不对，就可以继续让 AI 修改这个 demo，直到整体体验比较符合我们的预期为止。」

做 demo 有两个好处：

  1. 提前验证产品设计。「很多东西光靠文字其实很难想象。真正把页面画出来、亲自操作一下之后，你可能就会发现一些之前没有想到的问题。」发现设计不合理，就继续修改 demo，同时把对应的产品设计文档一起调整。
  2. 让后面的产品实现更精确。demo 可以非常直观地告诉 AI「我最终想要的产品大概就是这个样子」——「这个是文字描述很难做到的」。后面实现时把产品设计文档和 demo 一起交给 AI，它既知道要做哪些功能，也知道界面和交互应该怎么还原，做出来的东西一般会更加接近预期。

那到底什么时候适合做 demo？UP 主给了一个非常干脆的判断标准：

判断标准：这个产品的后端实现成本
  • 后端成本高 → 先做 demo。例：个人知识库。「因为这里面会涉及到文档处理、搜索、检索策略、模型 demo 等等很多的后端逻辑。在这种情况下，我更愿意先做一个 demo，把界面和交互确定下来。」
  • 后端成本低 → 直接做产品。例：本期的电子书阅读器。「毕竟就是一个看书软件，导入 TXT 文件就可以了，没有什么太复杂的逻辑。这个时候如果还专门做一遍 demo，可能反而有些重复劳动，还不如直接把产品给做出来。等真正跑起来之后，哪里不顺手，我们直接在完整的产品上面继续调整就可以了。」

如果需要做 demo，指令也很简单：

「帮我做一个 demo，不用实现真实的后端功能，数据模拟一下就行。我主要是想看看整体界面和操作流程是否合理。」 —— demo 指令模板（14:12 前后）；不满意就继续让 AI 改，直到符合预期

「不过就像前面所说的，我们这个电子书阅读器比较简单，没有太大必要专门做一遍 demo，所以这里我也就不发这条指令了。大家在自己的项目里面，可以根据实际情况决定要不要加这一步。」

本节小结

  • demo = 只有前端、数据模拟的「可操作原型」，用来验证界面与交互。
  • 两个价值：提前暴露设计问题、给 AI 一个比文字更精确的目标。
  • 判断标准只有一个：后端实现成本。贵 → 做；便宜 → 直接做产品，做 demo 反而重复劳动。

思考题（整理者补充）

  1. 用「后端实现成本」这个单一标准来判断，有什么盲区？（提示：考虑界面复杂度高但后端很简单的产品。）
  2. 如果决定做 demo，你会把 demo 和产品设计文档中的哪些部分保持同步？

5.1技术栈讨论：Electron 与 Tauri

14:43 – 16:40

技术方案可以直接在当前会话后面继续追问，也可以创建一个新的会话——「这两种方式都是可以的」。

UP 主先讨论了「要不要新开会话」，因为它牵出一个常见顾虑。

上下文会不会越聊越坏？
  • 顾虑：在当前会话继续追问，上下文越记越多，对大模型的效果可能就会有一定程度的影响。
  • UP 主承认：「确实有这种可能性。」
  • 但他的体会是：现在的顶级模型对长上下文的驾驭能力越来越强了，再加上对应的上下文压缩机制，正常使用的话一般不用过于担心上下文的问题。
  • 他的实测：「我甚至经常在一个会话里面连续跑几个小时，都没有感觉到有什么太大的问题。」
  • 但他仍然选择新开：「不过为了稳妥一点，也为了让后面的技术方案讨论更为聚焦，我们这里还是新开一个会话。」

这个选择本身很有信息量：他不是因为「上下文一定会坏」才新开，而是因为新开会话能让话题更聚焦。也就是说，在他这里新开会话是一个「组织话题」的动作，而不是「防止模型退化」的补救措施。

做法和产品设计同构：先跟 AI 讨论可能的技术设计方向，让它给建议。他给了一个很实用的场景——你可能听说 Electron 非常适合做这件事，但你对它没那么熟、拿不定主意，「这个时候你就可以把你的想法跟 AI 说一下，让它帮你看看 Electron 合不合适」。

「在这个目录下面有一份产品设计文档，请你读一遍这个产品设计文档，然后告诉我用什么技术站设计这个产品比较合适。不用给出过于详细的设计，我们就先探讨一下。我听说 Electron 还可以，你怎么看呢？」 —— 技术栈讨论的指令（15:51 前后）

这句指令里其实有四个动作，每一个都值得单独拎出来：

  1. 指向已有文档——把上下文交给它，而不是重述需求。
  2. 要技术栈建议——要的是方向，不是完整设计。
  3. 明确说「不用过于详细」——和 CH4 的措辞习惯一致，控成本。
  4. 把自己的猜测抛出去让它评估——「我听说 Electron 还可以，你怎么看呢？」要的是判断，不是选项列表。

AI 的回答：Electron 非常合适、会优先采用，给出了建议的技术栈，同时也给出了 Electron 的缺点，以及另外一个可能的选项 Tauri。最后收口出这套架构：Electron + React + TypeScript + Vite + Electron Forge。

这条链路的形状值得记
  • 人抛出一个候选 → AI 评估并主动补出备选 → AI 把讨论收口成一套可执行的组合。
  • UP 主在这里坦承「我也不是特别懂这块」（说于 CH5.2）——这恰好说明这一步要的不是人的技术判断力，而是让 AI 把选项摆齐、再由人拍板。
勘误提示 转写把「技术栈」误识别为「技术站」，「Tauri」误识别为「Tori」。本讲义已按勘误表修正，详见附录 A。

本节小结

  • 新开会话的理由是话题聚焦，不是「防止上下文退化」；UP 主认为顶级模型的长上下文能力已基本够用。
  • 讨论技术栈的指令结构：给上下文 → 要方向 → 限详细度 → 抛出自己的猜测要评估。
  • 最终技术栈：Electron + React + TypeScript + Vite + Electron Forge；备选 Tauri 未被采用。

6.1装 Computer Use 与 Chrome 插件：先给 AI 眼睛

17:22 – 18:14

「在正式编写代码之前，我先提一句——我们最好让 AI 拥有自行验证结果的能力。」这是 CH3 那条「规矩二」的落地条件：规矩要求它自测，那就得先给它能测的工具。

如果用的是 Codex，他建议至少安装两个插件：

  1. Computer Use —— 可以用来操作电脑。
  2. Chrome —— 可以用来查看 Chrome 页面。

「有了这两个插件，大部分的功能都是可以交给 AI 来验证的，包括我们现在做的这个电子书阅读器也是同样的道理。」如果用别的编程 Agent，「那可以自行查找下对应的插件或者是 skill」。

不给验证环境的后果
  • AI 只会写、不会验——「很容易就会写出一堆 bug」，毕竟它没法验证。
  • 人被迫下场当测试员：「来来回回帮 AI 找 bug，极其浪费时间」（这句在 CH7 原则二里被再次点名）。
  • 所以这一步省下的时间，会在后面的来回沟通里成倍还回去。
「给 AI 一个能够验证的环境是一个非常重要的事情，否则 AI 很容易就会写出一堆 bug——毕竟它没法验证嘛。如果人写代码没法验证的话，那估计也会有一堆 bug。」 —— UP 主原话（17:51 前后）

最后那句把人机放在同一把尺子上，是本片最锋利的类比之一：问题不在于「AI 不靠谱」，而在于任何写代码的主体，没有验证手段都必然产 bug。

这一步的定位
  • 它不是「可选优化」，而是让 AGENTS.md 里那条测试要求真正能被执行的前提。
  • 换句话说：规矩是写给人看的，插件是写给 AI 用的——两者缺一，自测都会退化成「AI 声称自己测过了」。

本节小结

  • 动手前必做：把「验证」也交给 AI，而不只是把「写」交给 AI。
  • Codex 下用 Computer Use（操作电脑）+ Chrome（查看页面）；其它 Agent 找对应插件/skill。
  • 论证方式：不是「AI 不靠谱所以要自测」，而是「没有验证手段的主体都必然产 bug，人也不例外」。

思考题（整理者补充）

  1. 你目前给 AI 的「验证手段」覆盖了哪些环节？哪些还完全靠自己手动测？
  2. 「让 AI 能操作电脑」和「让 AI 能看页面」，哪个对你当前项目的价值更大？

处理姿势：人不下场 debug
  • 报错不慌，也不用自己去读堆栈——把「看到的画面」描述清楚，剩下的交给 AI。

7.1五步流程：第一步一次性，后四步可循环

20:23 – 21:41

「我们简单回顾一下刚才的整体流程，一共是分为五步。」

步骤名称UP 主的描述
第一步环境搭建比如初始化 Git 版本控制、写一个基本的 AGENTS.md 等等
第二步产品设计明确要做什么、不做什么。这里我们会跟 AI 探讨产品方案，并在某些情况下出一份 demo
第三步技术设计主要是确定技术方案，尤其是技术栈和架构，以便确保整体方向没有问题、设计符合我们的要求
第四步产品实现不仅让 AI 实现代码，还要给 AI 自测的能力，让它写完代码之后能够自己测试，把明显的问题全部修掉。这一般需要我们安装类似 Computer Use 或者是 Chrome 的插件
第五步人工验证主要是我们亲自上手体验，发现问题就让 AI 修改，一直到完全符合预期为止
最关键的结构判断
  • 「你看，这里面除了第一步环境搭建是一次性的，后面的四步其实就是我们开发每一个新功能时的标准流程。」
  • 举例：后续想给阅读器加一个全文搜索功能，同样走这个流程——先做产品设计（确定搜索入口该放在哪里、结果该怎么展示），再出技术方案（文本怎么索引、搜索怎么实现），接着让 AI 完成开发和自测，最后我们再亲自验证。

这个「一次性 + 循环」的结构很重要：它说明了第五步里哪些是固定成本（①④⑤），哪些是可以裁剪的（②③）。这正好是下一节的铺垫。

本节小结

  • 五步：环境搭建 → 产品设计 → 技术设计 → 产品实现 → 人工验证。
  • 第一步只做一次；后四步是「每加一个新功能都要重跑」的循环。
  • 这个结构直接决定了后面「哪些环节可以省」的答案。

思考题（整理者补充）

  1. 用这个五步框架复盘你最近的一个需求，实际走了哪几步？跳过了哪几步？
  2. 「环境搭建是一次性的」——如果团队换了工具或规范，这个前提还成立吗？

7.2参与度取舍：简单不重要 vs 复杂重要

21:41 – 23:13

「当然这几个步骤并不是死板的流程。」UP 主接着给出全片最重要的一句判据：

「具体要做到什么程度，取决于你想对最终结果保留多少掌控力。」 —— UP 主原话（21:44 前后）
两个可以整章跳过的环节

  • 如果你也不关心代码具体怎么实现 → 技术方案同样也可以不用关心，让 AI 自己决定。
  • UP 主的评价：「这么做其实并没有什么太大问题。」
代价是什么
  • 「只是意味着你把更多的决策权交给了 AI。」
  • 「这样的话你对最终结果的掌控自然就会少一些，做出来的东西可能也就没有那么贴合你的预期。」

所以这本质上是一种取舍，UP 主把它讲得非常对称：

参与度收益代价
参与得多对最终结果把控更强需要投入的时间和精力也更多
参与得少开发过程更省事更快结果与预期出现偏差的可能性也更高

怎么定这个度？「这个度其实没有一个特别固定的标准。我一般会根据需求的复杂度和重要性来判断。」他给了两种情况：

情况走法说明
简单且不重要跳过 ② ③「我一般会忽略产品设计和技术设计这两个环节。搭好环境发出指令之后，我会直接让 AI 实现，实现完后我做验证，验证完了之后这个需求就结束了。整个流程会非常快。」
复杂而且重要走完五步「我则会参与到产品设计和技术设计的环节中来，走完这完整的五个环节，尽可能的保证最终产品的质量。」

「所以这里并没有一个固定的标准。说到底，还是在开发效率和结果的可控性之间做取舍。」

本节小结

  • 可裁剪的只有 ② 产品设计与 ③ 技术设计；①④⑤ 在两种走法里都存在。
  • 判据：需求的复杂度和重要性（等价于「你想保留多少掌控力」）。
  • 本质是一场权衡：开发效率 ↔ 结果可控性。

思考题（整理者补充）

  1. 你手上的需求，「简单不重要 / 复杂重要」这个二分法够用吗？有没有第三类？
  2. 如果跳过 ③ 技术设计，风险会在什么阶段暴露？

7.3三条不能省的原则

23:13 – 24:32

「尽管流程可以根据需求灵活调整，但有三个原则我建议大家尽量坚持。」这是全片最该抄下来的三句话。

原则一 · 必须有版本管理工具
  • 比如你可以用最流行的 Git 来管理代码。
  • 「AI 写代码不可能每次都完全正确，有时候甚至会在修改的过程中把原本能够正常运行的功能改坏。」
  • 用了 Git 之后，每完成一个功能都可以保存一个对应的版本，后面一旦出了问题，就能很方便地回到之前正常的状态。
  • 另外如果条件允许，也建议把代码同步到 GitHub 之类的远端仓库——这样即使本地代码不小心丢了，也能够从远端恢复。
原则二 · 必须给 AI 自测的能力
  • 「很多人只是让 AI 写代码，但不给它验证的环境。」
  • 结果是「自己就沦为了测试员，来来回回帮 AI 找 bug，极其浪费时间」。
  • 正确做法：「我们应该把相关的工具和插件开放给 AI，让它自己写完自己测，这样交付出来的代码质量就会高很多。」
原则三 · 必须进行人工验证
  • 「AI 自测再充分，也不可能把所有的问题都覆盖到。」
  • 容易被漏掉的是：「像交互体验，或者是一些不容易想到的边界情况。」
  • 所以「产品到底好不好用、是不是我们真正想要的，最终还是要自己试一遍才知道」。

本节小结（全片核心）

「真正不能省的就是这三件事情」：

  • 用 Git 搭建好环境
  • 让 AI 具备自测能力
  • 最后还一定要人工验证
  • 至于产品设计和技术设计要做得多细，「大家看情况决定就好」。
与前文的对应关系
  • 原则一 = CH3 的规矩一（每次改动必须 commit）。
  • 原则二 = CH3 的规矩二 + CH6 的两个插件。
  • 原则三 = CH6.3 那次「上来就报错」。
  • 三条原则在前面的演示里都已经出现过一次——这一章只是把它们从操作里抽出来命名。

思考题（整理者补充）

  1. 三条原则里，你哪一条做得最差？具体差在哪个动作上？
  2. 如果团队协作，这三条原则里哪一条最需要变成硬性规范？
