1.1两条主线：模型与开发基座 00:00

开场只有 20 秒，但交代清楚了这份报告的性质。UP 主先自报家门（「我们是圣徒城的小诺」），随即说明本期的定位是接续上一期，然后抛出全片要回答的两个问题。

CONCEPT · 本片的两条主线

① 模型线：DeepSeek、GPT 等当下和前沿模型，在实际体验上的差别是什么？

② 基座线：它们各自所属的开发基座——Codex、Claude Code、智谱的 Zcode 等——好坏差异在哪？

这里有一个措辞值得留意：UP 主反复强调的是「实际体验」，而不是「客观能力」。字幕里出现的判断——「上限非常高」「有点毛坯化」「性价比最好」——绝大多数是团队在真实项目上跑出来的体感，不是实验室对比或榜单复现。

所以这份材料的正确用法是「对号入座」而不是「当作定论」：先看自己的使用姿势（主代理还是子代理？单会话还是并发？要审美还是要稳定执行？）跟 UP 主描述的是否一致，再决定他的结论能不能平移到自己身上。

NOTICE · 关于「上一期」

本片明确说是接续上一期。因此片中「前面我们也提到了」「我们前面也看到了」这类回指，指的是上一期的实测案例（涉及 UI 复刻、B 站前端小项目等），本讲义无法补充其细节。相关位置已在正文标注。

本章小结（01 章）

  • 本片是体验复盘，不是跑分榜；两条主线分别是「模型」和「承载模型的开发基座」。
  • UP 主团队为此投入了上万块 Token——片名里的这个数字就是成本声明。
  • 后者（基座）在本片里被赋予了与模型同等的重要性，这是本片区别于普通「模型横评」的关键。

思考题（整理者补充）

  1. 为什么同一个模型换一个 Harness，体验会差这么多？请结合本片后面的「额度消耗差异」与「子代理操控颗粒度」两条线索预先想一想。
  2. 「实际体验」与「客观能力」在选型决策里分别应该占多大权重？
CHAPTER 02

模型横评：从 GPT-6 到通义千问

00:19 – 12:41 · 9 节 · 10 个模型

2.1GPT-6：上限极高，但会「自己加戏」 00:19

第一个讲的是 GPT-6。经验来源被明确交代了双重出处——「社区上还有我们大量开发的一些经验」，说明这不是单人印象。

CAPABILITY · 上限
  • 在复杂任务上的上限非常高
  • 尤其擅长架构设计与视觉还原
  • 指令遵循非常强

但紧接着是痛点，而且这条痛点很有意思——它属于「优点用过头」的类型：

PITFALL · 过度设计、过度考虑安全

你给它一个需求，对话还没有结束，它就已经搞出了一个「延展性的设计」出来——已经超出你的需求范围了，还可能造出一堆并不太必要的组件。

如果一个架构里有很多你不知道是干什么的组件，那它后面如果改动了，你就不知道什么情况了，你的架构就很容易腐坏。 — UP 主原话（00:52）

这个论证值得单独拎出来：UP 主反对过度设计的理由不是「浪费」，而是「可维护性崩塌」。多余的组件不是在浪费 token，而是在给未来的自己埋雷——因为你不知道它的存在意义，也就无法判断改动它的后果。这是本节最有方法论价值的一句话。

USAGE · 给它上镣铐
  1. 必须明确它的边界——在 AGENTS.md 里把它约束住
  2. 尽可能少地在主对话里大量使用它，避免它「过于强悍」
  3. 推荐接入 Codex 或 OpenCode，作为子代理使用
  4. 让它干的事：询问方案、临时做重大决策、业务性判断
  5. 它不适合放在主要工位上干活，而且成本极高

把这五条连起来读，UP 主实际上在为 GPT-6 安排一个角色：外部顾问——只在关键决策点叫它进来，用完就退场。这跟下一节 GPT-5.6 的「常驻工位」角色正好互补。

存疑标注：Astra 为 GPT-6 的版本/档位名，本片两处音源听写一致，按原文保留。

2.2GPT-5.6：综合性价比最好，但会「漂移」 01:31

能力画像被概括为「相对均衡一点」。但均衡不等于精致——UP 主给它造了一个很传神的词：毛坯化。

PITFALL · 前后端「毛坯化」

功能可以实现：你给一个比较精准的需求，它是可以跑出来的。但跑出来的功能比较毛坯：

  • 写后端：可能性能没有做优化
  • 写前端：不太好维护扩展，因为「自己写了很多自己自定义的 CSS 样式」

「毛坯化」这个词是 UP 主的自创措辞，指「能交付但没打磨」的状态——功能可用，但工程性、性能、可维护性都停在最低可用线。它不影响你跑通，但会在后续迭代时开始收利息。这个描述对实际工作很有指导性：毛坯代码应该被安排在「一次性的、不打算长期维护」的任务上。

UP 主还做了一个横向对比：它「是性价比的选择，但也可能没有那么性价比」——跟 GPT Luna 和 GPT Terra 比起来还是要差一点。不过总体结论仍然是：它是「大家能够使用到的、综合能力性价比最好的模型」。

长任务上的「漂移」

这是本节第二个、也是更硬核的痛点，来源同样是双重出处（社区 + 团队自测）：

CASE · 上下文漂移的阈值

在 Codex 里开到 50 万甚至 100 万上下文时：

  • 接近 40 万以上 → 开始出现一定的漂移
  • 七八十万以上 → 「几乎是不太可用了」

UP 主的建议：设置上下文时「直接就是临界设到 512000」，以保证上下文稳定；如果不经常用长上下文，设到 256K / 300K 都可以。

这里的思路值得单独学：UP 主不是在做「窗口越大越好」的加法，而是在做一个刻意的性能取舍。512000 落在「漂移起点（40 万）」和「可用性崩塌点（80 万）」之间——留了余量，也仍在稳定区内。这是一个可以直接抄的工程参数。

POSITIONING · 一句话定位

GPT-6：更像一个相对成熟、偏向架构方向走的工程师。

GPT-5.6 SOTA：像一个非常综合性的工程师——比较擅长搞开发，但搞架构设计什么的还是没有那么好。

本节小结

  • GPT-5.6 的核心矛盾是「能用但毛坯」——能跑通，工程质量要自己兜。
  • 长任务上会把「窗口能力」和「可用能力」拉开差距，512000 是 UP 主给的工程参数。
  • 它与 GPT-6 的分工是「GPT-6 定方向、GPT-5.6 干日常」。

2.3Claude Opus 5：发散性与架构感好，但会「自己宣布完工」 02:52

本节贡献了全片最精准的一个缺陷命名——自我验收不稳。UP 主的讲法非常讲究：先给现象，再给定义，最后做横向对照。

CAPABILITY · 延续 Claude 系列的特点
  • 擅长代码组织
  • 适合明确任务
  • 跟它发散想法时能给出很好的反馈——「甚至它的反馈质量我觉得不比 GPT-6 要差」
PITFALL · 自我验收不稳

现象：「它可能自己干着干着，觉得自己干完了。」

界定：UP 主强调这是 Claude 系列明显的痛点，不是 Opus 5 独有的问题。

为了让这个缺陷更清楚，UP 主做了一个对照——这个对照信息量很大：

系列遇到干不完时说明
GPT 系列诚实告知一般会诚实地告诉你干不完
Claude 系列可能破坏架构有时候会「为了目的直接破坏你的架构设计」
Claude 系列可能误报完工或者干着干着漂移了，却觉得自己干完了

这三行的差别不是「能力高低」，而是失败时的行为模式。前者失败得透明（你知道要接管），后者失败得隐蔽（你以为已经完成）——隐蔽的失败对工程流程的伤害更大，因为它会让「人工复核」这一环被跳过。

CONCLUSION · 三条结论
  • 所以必须人工去复查一下
  • 它的记忆能力相对没有 GPT 系列稳定
  • 但发散性和整体的架构感还是很不错的，依旧可以作为主力模型使用

附带信息：更强的 Fable 与它的价格

UP 主表示「相信 Fable 5 或者 Fable 5.1 肯定是更强了」，但因为实在平常不太会使用，所以没纳入实测。他给了一个价格侧的观察：现在它的套餐，像 Max 20 倍档，无论闲鱼上还是别的地方都已经涨到 2000 块钱，还有封号概率——「几乎是不会被大家广泛地采用了」。

UNCERTAIN · 两处存疑

① 模型名：本片两处音源分别听作 Fibro 5 与 FBL 5.1，均碎片化。按音近推定为 Fable 5，属听写推定，请以官方命名为准。

② 「Max 20 倍」：指订阅套餐档位，原话如此保留。

2.4DeepSeek V4.1 Flash：速度快、前端强，但别拿它搞并发 04:01

本节先讲了一个产品线层面的细节，很值得注意：4.1 Flash 跑出来之后，结果比 4 的 Pro 还要强，所以 DeepSeek 直接只保留了这一个版本在 API 上供应。也就是说 Flash 档位反超了 Pro 档位，Pro 被下架了——这是「实测结果决定产品线」的一个实例。

CAPABILITY · 长处
  • 前端非常强
  • token 速度非常快（UP 主原话：「你就说快不快吧」）
  • 在一些精准定位上也还不错
  • 支持多模态

定位判断很明确：它目前看起来不太适合用并行去开发，因为它是走 API 计价的。规模上仍是「只有六七百 B 的模型」，没有像海外那些动辄几个 T 的那么大，所以仍然需要一些 harness 或者人工质量审查——但「已经是一个非常非常合适的模型了」。

PITFALL · 并发警告（全片最响的一条）

如果经常使用子代理，或者你的 Claude Code / Codex 里配置了大量子代理、需要并发执行任务，那最好不要用这个模型——因为它会飞快地跑掉你的额度。

这个警告的机制值得拆开看，因为它解释了「单会话便宜」和「并发烧钱」为什么可以同时成立：

使用姿势是否推荐原因
单个会话推荐缓存量很多 → 命中率高 → 单价低；临时任务、临时设计 UI 都合适
并发子代理避开「本来 token 量就快」；开三个项目、每个三个并发 → 一天大几百不成问题

关键在于：「token 速度非常快」这个优点，在并发场景下会反过来变成烧钱的加速器。同一个特性，在不同架构下符号相反——这是本片很值得记住的一个观察。

UP 主把这条称为「血与泪的教训」，但结论并不消极：如果临时需要、在单个窗口内没有太多验证，用起来还是很便宜的，而且性能效果确实不错，临时设计一些 UI 也可以。最后他明确表态：「我们仍然非常喜欢这款模型了」——批评的是用法，不是模型。

2.5GLM-5.3：最像「工程师」的模型，缺多模态 05:27

GLM-5.3 是 UP 主团队「在大量使用」的模型，起用它有一个很现实的原因：当 GPT 额度不够了、Claude 额度不够了，很多时候就不得不使用 GLM 的 Coding Plan。也就是说，它是主力额度耗尽时的「接盘选手」。

CAPABILITY · 让人喜欢的地方
  • 一个非常强的工程师性格
  • 规模：大概 700 多 B，是做了很好的后训练的模型——相当于在 GLM-5.2 的基础上进一步强化了 coding 能力和 agent 能力
  • 开发 benchmark 号称达到跟 5.6 SOTA 不相上下，「体感上来说确实如此」
  • 可以非常稳定地执行任务
  • 100 万上下文不是假的——「它真的可以记住，几乎在五六十万的上下文时还能保持稳定」
PITFALL · 五条短板
  • 套餐蛮贵的：有 5 小时限制，还有 7 天限制，「蛮多」
  • 速度相对慢：可能跟它的服务负载有关系
  • 套餐消耗相当的快
  • 缺乏多模态理解能力：在刚测试的项目中，明显有视觉和一些设计方面的短板
  • 自由探索架构设计上的能力相对保守，没有那么好
USAGE · 「编排—执行」分层
  1. 用 Kimi 或者 Claude 去做编排
  2. 在 OpenCode 或 Zcode 里把 GLM-5.3 作为子代理去调用
  3. 不要让它当主代理去做单流程执行——它不太擅长并发执行任务

「它更像一款适合干活的模型，也是一个非常好的、工程师化的模型。」UP 主对它的评价结构非常清晰：强在「执行稳定性 + 长上下文真实性」，弱在「多模态 + 并发 + 架构探索」——正好和 GPT-6 互补。

本节小结

  • GLM-5.3 的 100 万上下文是「真货」——到五六十万仍保持稳定，这在同价位里是稀缺能力。
  • 它的短板让它可以被信任地「执行」，但不能被信任地「探索」。
  • 正确姿势是当一个好用的子代理/执行者，而不是主脑。

2.6Grok 4.6：快、敢试错、不爱做计划 07:02

UP 主对 Grok 4.6 的开场评语是「它的生态会很奇怪」——因为它的口碑走势是反的：刚出来的时候大家没太当回事，但测了测发现好像没有像那个「美国大豆包」那么蠢，它的开发能力还是很不错的。

KEEP · 保留原文

「美国大豆包」是 UP 主对某海外模型的戏称（自备字幕作「美国大豆包煎饼袋」），两源一致，属作者式玩笑。按本讲义的整理原则，不「改正」作者的故意措辞，保留原样。

TRAITS · 三个特点（UP 主明确编号）
  1. 比较快——响应速度很快，敢于主动快速试错；在快速迭代中的效果提升比较明显
  2. 能力还不错
  3. 它不喜欢做太复杂的计划

第三条是本节的核心对比，也是它与其他模型性格差异最大的地方：

模型工作方式说明
GLM-5.3 / GPT 系列先长思考再动手都很喜欢做很长很长的思考，然后才去做东西
Grok 4.6先动手再迭代适合「上来咣咣咣就开始干」，干完跑出东西，然后迅速去迭代的人

所以它的用户画像很明确：适合「先做出来再改」的工作流的人，而不是「想清楚再动手」的人。UP 主还指出它的生态位跟 DeepSeek V4.1 Flash 有点像——都属于「快、敢试、别指望它深思熟虑」那一挂。

至于它当时口碑为什么起来：毕竟这是刚出来的，当时它效果是最好的，最起码当时它「暴打」了 Gemini 系列。而现在 Gemini 虽然快，但没有那么好用，「3.8 也只能查查文档、简单干点活」。

PITFALL · 审美需要纠偏

Grok 4.6 还有个问题，就是它的审美需要一定的纠偏，没有那么稳定。它对国内的一些 UI 设计，甚至复刻一些已经有的界面，效果并不是很好。UP 主此处没有展开，只说「这个我们就不再多提」。

这里可以注意到一个贯穿全片的判据：UP 主把「审美稳定性」和「逻辑能力」分开评估。一个模型可能代码逻辑没问题，但 UI 一次一个样——对有设计要求的项目来说，这个短板足以抵消它的速度优势。

2.7Kimi K3：Agent 调度是天生的，但额度不够、偏贵 08:14

这是全片态度落差最大的一个模型——UP 主先讲了一个「退步」的观察，再讲它天生的优势，最后落到性价比判断。

OBSERVATION · 效果明显不如印象

「我们今天用的这个效果，可能是比我们印象中要差很多。」Kimi K3 刚出的时候，团队用它去做官网、做界面，「甚至它的原型设计都是非常精美的」，但今天的效果真的差强人意。

CAPABILITY · 天生优势：预训练就强化了 Agent 能力
  • Kimi 那边本来就预训练的——训练时特地强化了它的 Agent 能力
  • 它可以天然地愿意去调度 Agent 的团队
  • 任务拆分也更自然一点

「天生」这个词是本节的关键——它说明这不是靠提示词工程或外部框架补出来的能力，而是模型本身的倾向。这也解释了为什么后面第三节里，Kimi 系的框架会被拿来讨论子代理调度问题。

但开发能力本身，UP 主的判断偏保守：它的开发风格在社区的评价中是比较中庸的。这里他给了一条本片最值得记住的判据之一——

刚出来的时候很牛，不代表现在也很牛。 — UP 主原话（08:47）

所以结论是：开发能力比较靠中间一点，比较适合中小型的应用。

PITFALL · 额度不够用，且偏贵

2.8MiniMax：参数量落后，生态位尴尬 09:26

这一节的关键词是「尴尬」，而且 UP 主给出了一个可量化的根因，不是模糊的「不够强」。

事实层面：MiniMax 系列已经很久没有更新新模型了，UP 主也不很清楚下一款的情况。然后是行业尺度的对比：

ROOT CAUSE · 参数量掉队

目前这些主流模型的尺寸基本都已经涨到 500B 以上了，而 MiniMax 现在还处于 500B 以下——「就已经非常的尴尬了」。

在开发的后训练方面，以及它原生知识的复杂性上，参数量太小这个痛点是没办法根治的。

「没办法根治」这五个字是本节的分量所在——它把问题从「这一代模型不够好」升级成了「结构性的落后，靠后训练补不回来」。所以 UP 主的结论是「急需推出一款更强大的模型」。

CAPABILITY · 仍然保留的优点
  • 支持多模态
  • 有 100 万上下文
  • agent 能力还不错，还相对稳定

但优点挡不住「被平替」。UP 主列了同价位上的竞争对手：

CASE · 四路夹击

现在 MiniMax M3 因为在快速上也有平替，就处于一个很尴尬的生态位：像 DeepSeek V4.1 Flash、Gemini 3.8 Flash、GLM-5.3 Flash，这些快速模型现在都比 MiniMax M3 强；甚至用 Antigravity 里面的 Gemini 3.8 Flash 也比 MiniMax M3 强。

注意这里的分析方法是生态位视角而不是绝对能力视角：MiniMax M3 的硬伤（参数量）单看不算致命，致命的是「它所在的快速档位上，已经有四个更强的替代品」。这就是 UP 主反复用「尴尬」这个词的原因。

POSITIONING · 现状定位
  • 拿来做一些脚本
  • 因为很便宜，现在还占着便宜的优势——一些新手拿来开发 UI
  • 它的 UI 效果「在当年那一代模型里面」相当于大家买手机时的「老旗舰」，还算可以的
  • 所以拿来作为初学者用一用，很便宜

2.9通义千问：能力不差，贵在生态位 10:40

本章最后一节，也是信息量最密的一节。UP 主在这里给了一个反直觉的评价——「不惊艳」但「稳定」，而且他用一笔真实账单说明了问题出在哪。

开头的判断就很清楚：「千问系列大家现在应该不太会用来做开发了」，但紧接着是一个反转——

它最根本的问题不在于能力不行。 — UP 主原话（10:45）
OBSERVATION · 不惊艳，但稳定

从今天的测试可以发现，千问这两个模型确实不惊艳——它做出来的 UI，达不到那种「一眼看上去就能达到 GPT 或者 DeepSeek 抽卡抽出来的效果」。

但它多轮跑出来的东西还是很稳定的，这是一个很大的优势：「它跑出来的东西怎么看，好歹是像那么回事」。

UP 主在这里下了一个很关键的反转判断：

这两个模型并不是不可用，甚至某种意义上在某些场景下可能更好用——你拿它多轮迭代，如果很稳定的话，那不就是很好用吗？ — UP 主原话（11:12）

也就是说，「一次直出好看」和「多轮迭代不崩」是两种不同的能力。前者决定你在 demo 环节爽不爽，后者决定你在真实项目里能不能推进。千问属于后者——这个区分方式很有迁移价值。

CASE · 一笔 39 元账单的推演

投入：本次测试买了 39 块钱的 token plan（按周限制 / 按月限制）。

任务：只测了一个「做 B 站前端」这样的小项目——「甚至算不上一个正儿八经的大项目」。

调用：只是一人测了一次：一次「一次性指令直出」，一次「对抗审查」。

结果：直接把 39 块钱的额度触顶了，差点没跑完，基本干到 98%。

然后 UP 主把这个观察外推到了正式项目：

  • 那就说明在一个正式的大型项目里——比如项目有十几万行、二十几万行——你准备买多贵的套餐呢？

  • 那么有这个钱，如果你真的想跟 GPT 用一样多，两者花的钱可能差不太多——「那为什么不去买 GPT 呢？」

这个推演的方法比数字本身更有价值：UP 主没有引用任何官方定价，只用一笔真实的 39 元账单，就把「单位成本」外推到了大型项目的量级上。它证明的是性价比结构有问题，而不是某个绝对值贵。同时他补了一句当时的市场状况：「当然现在 GPT 20 倍是被禁用了。」

  • 大模型这个能力「没有什么特别惊艳的地方」
  • 但蒸馏出的小模型能跟大的保持差不多的后训练水平，coding 水平也差不太多

CHAPTER 03

开发基座横评：Harness 层的胜负手

12:41 – 17:31 · 7 节 · 6 套基座

3.1DeepSeek Harness：前沿但还嫩，适合折腾的人 12:41

UP 主把这一章称为「最后的一个部分」，切入方式也很明确：模型选完之后，还得选壳。

构成交代得很清楚：DeepSeek 现在做的是基于插件化的 DeepSeek Harness，在浏览器里使用。团队简单用了一阵子，发现这个框架目前还不是很稳定。

WHY NOT NOW · 四条理由
  • 还不稳定
  • 在频繁地高速迭代，里面在增加各种各样的功能
  • 设计比较前沿化——比如它试图把 Harness 里面的各个组件全部插件化，所以对刚入门的或者新手来说并不是很好理解，并不是一个新手友好的框架
  • 还在频繁迭代，发布有时候会有各种细微的小 bug
BUT · 有一类人应该用

对于非常想精调 harness 的开发者来说，因为它这种基于插件模式的设计：

  • 你可以把自己的很多 harness 理念植入进去
  • 或者尝试做自己的一套框架出来
  • 「那它就是一个很好用的东西」

这一节的结构其实是按角色分流，而不是简单的「好不好」：

你的角色建议
想直接用一个稳定的那就不要用它
想自己搞一个 App懒得自己封装的话，推荐现在最好还是先不要使用
想精调 harness 的开发者值得用——它的可塑性是优点

读法提示：「不稳定」和「不值得用」是两件事。普通用户等它稳定，开发者反而该趁它可塑的时候进场——因为一旦稳定下来，插件化的自由度往往会被收紧。

3.2Codex（GPT）：目前最成熟的 Coding Agent 框架 13:45

这是全片对基座的最高评价，理由浓缩成一个词——子代理。

Codex 我们目前是认为它是现在最最最成熟的一个 Coding Agent 的框架。 — UP 主原话（13:48）
WHY · 子代理通信流畅
  • 它的子代理非常有特点，和子代理通信的时候是非常流畅的
  • 如果你的主代理能力比较不错，它可以非常顺利地组织 3～4 个子代理来完成工作
  • 「这个就是我们现在觉得非常不错的点」

注意这里的措辞是「通信流畅」「组织3~4 个子代理」——评价的对象是协作机制，不是单个代理的智力。这正是本章的判据轴。

CONTRAST · Claude Code 的短板在哪

Claude Code 其实也能完成这个任务，但它的 Desktop 面板非常让人尴尬：

  • 比如你配置了基于 GLM 的一个 Claude Code，那你在它的 Claude Desktop 里面是没法进入 Code 界面的
  • 而且要充会员
  • 所以它对于国内开发者很不友好

这里批评的对象是桌面端的产品策略，不是模型或 CLI 能力。这是本片一个隐含的观察角度：同一个 CLI 工具，它的客户端面板可能会成为你根本用不下去的原因。评测基座时不能只看命令行体验。

PLUS · Codex 的加分项
  • 对比之下 Codex 就好得多
  • 那些子代理也都支持自定义提示词
  • 可以做并发，可以自己写这些
  • 指令遵循也不错
ECOSYSTEM SIGNAL · 别家都在适配它

可以看到像 DeepSeek、还有像 GLM 他们的 Coding Plan，也都在积极地去适配 Responses API 这种 Codex 的专属端点——「这个都是蛮不错的」。

这条信号值得单独标注出来：当竞争对手主动来适配你的接口，就说明你的框架事实上成了标准。UP 主把它作为「Codex 现在是最好的框架」的旁证——比自评更有说服力。

3.3Grok Build：快、轻量，但可读性欠佳 14:53

最短的一节，评价结构也最简单：

维度评价
优点速度非常快，非常擅长直接跑出来任务
缺点可读性不是很好——东西发上去之后，去理解那个界面或者阅读一些东西时，会有一些遮挡性的问题
结论整体来说还是可用的；处于一种没有 Codex 和 Claude Code 这种「老东西」成熟的阶段，但相对快、相对轻量可用

把它和 Grok 4.6 那一节并读，会发现 Grok 系的气质是一致的：快、轻量、先跑起来再说——但配套的「打磨度」（审美、界面可读性）都还差一层。

3.4千问的基座：不单独用，接到 CC 里 15:17

一句话带过：「千问的话我们就不提了。」原因也给了——UP 主不太用 Coder，所以一般就是把它接到 CC（Claude Code）里面来用，这里就不多讲了。

这也解释了为什么本片的「基座」章节没有单独评测千问自家的 CLI：它在这份报告里的角色是「模型供应商」，而不是「基座供应商」。对使用者来说，这条信息也有实用价值——某些模型的正确打开方式就是当「燃料」灌进别人家的壳里。

3.5Zcode 与 Kimi CLI：好看，但主代理操控子代理的颗粒度不够 15:23

本节是全片技术含量最高的一段。UP 主提出了一个明确的、可验证的框架缺陷机制，而不是泛泛的「不好用」。

开场先说清楚问题所在：GLM 的 Zcode「跟现在的一些其他框架是有明显的一个重大问题的」。然后立刻补上肯定——Zcode 还有 Kimi CLI 其实现在做得都蛮漂亮，可用性对于一个新手来说是可以的。

但接下来是判据：

在我们去调度一些 Agent 的团队来做事情的时候，这些团队之间的异步通信、主代理对于子代理的一个操控的颗粒度是非常重要的。 — UP 主原话（15:40）
DEFECT · 不支持运行中干预

现在在 Kimi CLI 还有 GLM 的 Zcode 中（UP 主加了限定：「如果我使用的版本没什么问题的话，如果是最新版本的话」）：

  • 不支持主代理在子代理运行过程中给它们补送消息
  • 或者说提前结束它们

缺失这两个能力会造成什么后果？UP 主给了一个具体的、可复现的失效链：

FAILURE CHAIN · 四步失效
  1. 你现在主代理直接植入了一个任务进去
  2. 然后子代理开始干活了——已经分派工作了
  3. 你现在又给主代理发了一个任务 → 它就会一直阻塞在那里，而且你没法停
  4. 如果你现在把这个任务停了 → 你前面那些子代理干的活直接就丢失了，你也不知道它造了什么东西出来

而且——「如果你的代码库本来就挺屎山的，那就非常的崩溃了」。

这条失效链解释清楚了 UP 主为什么把「操控颗粒度」当作分水岭：缺的不是某个功能，而是「中断/纠正」这个让 Agent 协作可恢复的能力。没有它，一次误判就会让你在「丢工作」和「干等」之间二选一。

BALANCED VIEW · UP 主自己也说得很矛盾
  • 既好用又不好用
  • 挺好看的
  • 也知道它在尽力做
  • 而且能看到它们的缓存命中率都挺好的
SCOPE LIMIT · 版本限定

UP 主两次加上前提——「如果我使用的版本没什么问题的话，如果是最新版本的话」。这类框架迭代很快，结论有时效性，引用时请一并带上这个限定。

3.6Kimi 的额度差异：同一个模型，换个壳消耗差很多 16:31

本节是全片唯一一处直接点出「基座会反过来影响额度」的观察，也是「为什么模型和基座要一起评估」的直接证据。

OBSERVATION · Kimi 的消耗因壳而异

它的速度可以，但额度消耗在不同的 agent 工具里面是不太一样的：

  • 像 Kimi K3，它在 Claude Code 里面的消耗非常快——「不知道是不是 Claude Code 有什么负优化」
  • 但 Kimi K3 在自己的 Kimi CLI（也就是 Kimi Code）里面用的话，速度还挺好的，UI 做得也还不错，写任务的时候都比较明确

UP 主给这个差异留了一个问号，没有下定论——这与他在别处（比如 GLM 速度慢「可能跟它的服务负载有关系」）的处理方式一致：现象说清楚，归因保留。这种严谨度值得注意，也提醒读者不要把「壳的问题」和「模型的问题」混为一谈。
