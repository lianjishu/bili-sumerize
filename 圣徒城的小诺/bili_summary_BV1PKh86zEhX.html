02

模型横评：从 GPT-6 到通义千问

00:19 – 12:41 · 9 节 · 10 个模型

这 12 分钟是全片的重心。UP 主按「上限 → 痛点 → 该拿它干什么」的固定套路逐个过模型，而且几乎不给满分——每个模型都能说出一个明确的、会让实际开发踩坑的性格缺陷。

2.1GPT-6：上限极高，但会「自己加戏」

00:19 – 01:30

这是全片第一个模型，也是 UP 主给出最高评价、同时给出最严厉使用限制的一个。

上限
  • 在复杂任务上的上限非常高
  • 尤其擅长架构设计与视觉还原
  • 指令遵循非常强

这些经验来源被明确交代了双重出处：「社区上还有我们大量开发的一些经验」——不是单人体验。

痛点一 · 过度设计、过度考虑安全

你给它一个需求，对话还没有结束，它就已经搞出了一个「延展性的设计」出来——已经超出你的需求范围了，还可能造出一堆并不太必要的组件。

如果一个架构里有很多你不知道是干什么的组件，那它后面如果改动了，你就不知道什么情况了，你的架构就很容易腐坏。

— UP 主原话（00:52）

这个论证值得单独拎出来：UP 主反对过度设计的理由不是「浪费」，而是「可维护性崩塌」。多余的组件不是在浪费 token，而是在给未来的自己埋雷——因为你不知道它的存在意义，也就无法判断改动它的后果。

用法 · 给它上镣铐
  1. 必须明确它的边界——在 AGENTS.md 里把它约束住
  2. 尽可能少地在主对话里大量使用它，避免它「过于强悍」
  3. 推荐接入 Codex 或 OpenCode，作为子代理使用
  4. 让它干的事：询问方案、临时做重大决策、业务性判断
定位

它不适合放在主要工位上干活，而且成本极高。正确的用法是把它当「外部顾问」——只在关键决策点叫它进来，用完就退场。

2.2GPT-5.6：综合性价比最好，但会「漂移」

01:31 – 02:50

如果说 GPT-6 是「上限最高但要看着用」，GPT-5.6 SOTA 就是那个「能天天用但会慢慢跑偏」的选手。

能力画像被 UP 主概括为「相对均衡一点」。但均衡不等于精致：

痛点一 · 前后端「毛坯化」
  • 功能可以实现：你给一个比较精准的需求，它是可以跑出来的
  • 但跑出来的功能比较毛坯：写后端可能性能没做优化；写前端则不太好维护扩展，因为「自己写了很多自己自定义的 CSS 样式」
关于「毛坯化」：这是 UP 主的自创措辞，指「能交付但没打磨」的状态——功能可用，但工程性、性能、可维护性都停在最低可用线。它不影响跑通，但会在后续迭代时开始收利息。

UP 主接着做了一个横向对比：它「是性价比的选择，但也可能没有那么性价比」——跟 GPT Luna 和 GPT Terra 比起来还是要差一点。不过总体结论仍然是：它是大家能够使用到的、综合能力性价比最好的模型。

痛点二 · 长任务上的上下文漂移

来源同样是「社区上包括我们自己的一些使用体验」——双重出处。在 Codex 里开到 50 万甚至 100 万上下文时：

  • 接近 40 万以上 时开始出现一定漂移
  • 七八十万以上 时「几乎是不太可用了」
一句话定位
  • GPT-6：更像一个相对成熟、偏向架构方向走的工程师
  • GPT-5.6 SOTA：像一个非常综合性的工程师——比较擅长搞开发，但搞架构设计什么的还是没有那么好

2.3Claude Opus 5：发散性与架构感好，但会「自己宣布完工」

02:52 – 04:00

本节贡献了全片最精准的一个缺陷命名——「自我验收不稳」。

延续 Claude 系列的特点
  • 擅长代码组织
  • 适合明确任务
  • 跟它发散想法时，它可以很好地给你更多反馈——「甚至它的反馈质量我觉得不比 GPT-6 要差」
痛点 · 自我验收不稳

UP 主先给现象再给定义：「什么是自我验收不稳呢？就是它可能自己干着干着觉得自己干完了。」

而且他强调这是 Claude 系列明显的痛点，不是 Opus 5 独有的。

为了让这个缺陷更清楚，UP 主做了一个对照——这个对照很有信息量：

GPT 系列遇到干不完
一般会诚实地告诉你干不完
Claude 系列遇到干不完
有时候会「为了目的直接破坏你的架构设计」
或者
干着干着漂移了，却觉得自己干完了
结论
  • 所以必须人工去复查一下
  • 它的记忆能力相对没有 GPT 系列稳定
  • 但发散性和整体的架构感还是很不错的
  • 依旧可以作为主力模型使用

关于更强的 Fable 5 / Fable 5.1

UP 主表示「相信 Fable 5 或者 Fable 5.1 肯定是更强了」，但因为实在是平常不太会使用，所以没纳入实测。他给了一个价格侧的观察：

价格与可得性

现在它的套餐，像 Max 20 倍档，无论闲鱼上还是别的地方都已经涨到 2000 块钱，还有封号概率——「几乎是不会被大家广泛地采用了」。

存疑标注：模型名在本片两处音源中分别被听作 Fibro 5 与 FBL 5.1，均碎片化。按音近推定为 Fable 5，文中已按此转写，但仍属听写推定，请以官方命名为准。「Max 20 倍」指订阅套餐档位，为原话。

2.4DeepSeek V4.1 Flash：速度快、前端强，但别拿它搞并发

04:01 – 05:26

本节的另一个看点：UP 主讲了产品线本身的一次「自我淘汰」。

首先是模型迭代的一个细节——4.1 Flash 跑出来之后，结果比 4 的 Pro 还要强，所以 DeepSeek 直接只保留了这一个版本在 API 上供应。也就是说 Flash 档位反超了 Pro 档位，Pro 被下架了。

长处
  • 前端非常强
  • token 速度非常快——「你就说快不快吧」
  • 在一些精准定位上也还不错
  • 仍需要 harness 或者人工质量审查，但「已经是一个非常非常合适的模型了」

UP 主对它的定位判断很明确：它目前看起来不太适合大家用并行去开发，因为它是走 API 计价的。同时他给了个诚实的规模说明——它仍然是一个只有六七百 B 的模型，「没有像海外那些那么庞大（几个 T）」，前端需要抽卡。

并发警告（全片最响的一条）

如果经常使用子代理，或者你的 Claude Code / Codex 里面配置了大量子代理、需要并发执行任务，那最好不要用这个模型。

因为它会飞快地跑掉你的额度。

结尾的态度

尽管如此，「我们仍然非常喜欢这款模型了」——批评的是用法，不是模型。

2.5GLM-5.3：最像「工程师」的模型，缺多模态

05:27 – 07:01

GLM-5.3 是 UP 主团队「在大量使用」的模型，起用它有一个很现实的原因。

使用场景被交代得很直白：当 GPT 额度不够了、Claude 额度不够了，很多时候就不得不使用 GLM 的 Coding Plan。也就是说，它是团队在主力额度耗尽时的「接盘选手」。

让人喜欢的地方
  • 一个非常强的工程师性格
  • 规模：大概 700 多 B，是做了很好的后训练的模型——相当于在 GLM-5.2 的基础上进一步强化了 coding 能力和 agent 能力
  • 开发 benchmark 号称可以达到跟 5.6 SOTA 不相上下，「体感上来说确实如此」
  • 可以非常稳定地执行任务
  • 100 万上下文不是假的——「它真的可以记住，几乎在五六十万的上下文时还能保持稳定」
短板（三条 + 一条架构层面的）
  • 套餐蛮贵的：有 5 小时限制，还有 7 天限制，「蛮多」
  • 速度相对慢：可能跟它的服务负载有关系
  • 套餐消耗相当快
  • 缺乏多模态理解能力：在刚测试的项目中，GLM-5.3 有明显的视觉和一些设计方面的短板
  • 自由探索架构设计上的能力相对保守，没有那么好
UP 主给的用法 · 「编排—执行」分层
  1. 用 Kimi 或者 Claude 去做编排
  2. 在 OpenCode 或 Zcode 里把 GLM-5.3 作为子代理去调用
  3. 不要让它当主代理去做单流程执行——它有点不太擅长并发执行任务
定位

它更像一款适合干活的模型，也是一个非常好的、工程师化的模型。UP 主对它的评价结构很清晰：强在「执行稳定性 + 长上下文真实性」，弱在「多模态 + 并发 + 架构探索」。

2.6Grok 4.6：快、敢试错、不爱做计划

07:02 – 08:13

UP 主对 Grok 4.6 的开场评语是「它的生态会很奇怪」——因为它的口碑走势是反的。

刚出来的时候大家没太当回事，但测了测发现好像没有像那个「美国大豆包」那么蠢，开发能力还是很不错的。

保留原文：「美国大豆包」是 UP 主对某海外模型的戏称（自备字幕作「美国大豆包煎饼袋」），两源一致，属作者式玩笑。按本笔记的整理原则，不「改正」作者的故意措辞，保留原样。
三个特点（UP 主明确编号）
  • 第一，比较快——响应速度很快，敢于主动快速试错；在快速迭代中的效果提升比较明显
  • 第二，能力还不错
  • 第三，它不喜欢做太复杂的计划

第三条是本节的核心对比：

GLM-5.3、GPT 系列
都很喜欢做很长很长的思考，然后才去做东西
Grok 4.6
适合「上来咣咣咣就开始干」，干完之后跑出来一个东西，然后迅速去迭代的人

UP 主还指出它的生态位跟 DeepSeek V4.1 Flash 有点像——都属于「快、敢试、别指望它深思熟虑」那一挂。至于为什么当时它口碑起来：毕竟这是刚出来的，当时它效果是最好的，最起码当时它「暴打」了 Gemini 系列。而现在 Gemini 虽然快，但没有那么好用，「3.8 也只能查查文档、简单干点活」。

保留 · 审美需要纠偏

Grok 4.6 还有个问题，就是它的审美需要一定的纠偏——没有那么稳定。它对国内的一些 UI 设计，甚至复刻一些已经有的界面，效果并不是很好。UP 主此处没有展开，只说「这个我们就不再多提」。

2.7Kimi K3：Agent 调度是天生的，但额度不够、偏贵

08:14 – 09:25

这是全片态度落差最大的一个模型——UP 主先讲了一个「退步」的观察，再讲它天生的优势，最后落到性价比判断。

观察 · 效果明显不如印象

「我们今天用的这个效果，可能是比我们印象中要差很多。」Kimi K3 刚出的时候，团队用它去做官网、做界面，「甚至它的原型设计都是非常精美的」，但今天的效果真的差强人意。

天生优势 · 预训练时就强化了 Agent 能力
  • Kimi 那边本来就预训练的——训练时特地强化了它的 Agent 能力
  • 它可以天然地愿意去调度 Agent 的团队
  • 任务拆分也更自然一点
  • 「所以它在这个方面的能力是比较强的」

但开发能力本身，UP 主的判断偏保守：它的开发风格在社区的评价中是比较中庸的。这里他给了一条很值得记住的判据——

刚出来的时候很牛，不代表现在也很牛。

— UP 主原话（08:47）

所以结论是：它的开发能力比较靠中间一点，比较适合中小型的应用。

痛点 · 额度不够用，且偏贵

「它的额度不是很多，这也是一个重点。」Kimi 现在偏贵，原因链条是：模型尺寸太大 → 算力消耗太大 → 平台订阅太贵。

就算买最贵的那一档套餐，如果负责的项目比较重、规模比较大、需要循环迭代，额度也不够用。

三种用法叠加，额度直接见底
  • 想用网页端
  • 又想用开发侧
  • 有时候还想搞一个什么「龙虾」之类的玩一玩

「那基本上就不够用了。」

保留原文：「龙虾」两源一致，但所指不明——可能是某工具或玩法的昵称，本笔记无法确定，保留原话并加注。
结论

「所以说它现在的性价比不是很好。」而且——如果现在还有「降智」的情况，就没有那么再推荐给大家了。

2.8MiniMax：参数量落后，生态位尴尬

09:26 – 10:39

这一节的关键词是「尴尬」，而且 UP 主给出了一个可量化的根因。

事实上，MiniMax 系列已经很久没有更新新模型了，UP 主也不很清楚下一款的情况。然后他给了一个行业尺度的对比：

根因 · 参数量掉队

目前这些主流模型的尺寸基本都已经涨到 500B 以上了，而 MiniMax 现在还处于 500B 以下——「就已经非常的尴尬了」。

在开发的后训练方面，以及它原生知识的复杂性上，参数量太小这个痛点是没办法根治的。

仍然保留的优点
  • 支持多模态
  • 有 100 万上下文
  • agent 能力还不错，还相对稳定

UP 主特别提到 MiniMax 也做了自己的 code 平台，但认为急需推出一款更强大的模型。

现状定位
  • 拿来做一些脚本
  • 因为很便宜，现在还占着便宜的优势——一些新手拿来开发 UI
  • 它的 UI 效果「在当年那一代模型里面」相当于大家买手机时的「老旗舰」，还算可以的
  • 所以拿来作为初学者用一用，很便宜

2.9通义千问：能力不差，贵在生态位

10:40 – 12:40

本章最后一节，也是信息量最密的一节——UP 主在这里给了一个「不惊艳但稳定」的反直觉评价，并用一笔真实账单说明了问题出在哪。

不惊艳，但稳定

从今天的测试可以发现，千问这两个模型确实不惊艳——它做出来的 UI，达不到那种「一眼看上去就能达到 GPT 或者 DeepSeek 抽卡抽出来的效果」。

这两个模型并不是不可用，甚至某种意义上在某些场景下可能更好用——你拿它多轮迭代，如果很稳定的话，那不就是很好用吗？

开发基座横评：Harness 层的胜负手

12:41 – 17:31 · 7 节 · 6 套基座

UP 主说这是「最后的一个部分」，也把全片的技术判断上了一个台阶：模型选谁只是一半，另一半是用什么壳去承载它。这一章反复出现同一个判据——主代理对子代理的操控颗粒度。

3.1DeepSeek Harness：前沿但还嫩，适合折腾的人

12:41 – 13:44

第一个讲的是 DeepSeek 系的框架，UP 主的结论是「现在先别用」——但理由不是它差，而是它太新。

构成交代得很清楚：DeepSeek 现在做的是基于插件化的 DeepSeek Harness，在浏览器里使用。团队简单用了一阵子，发现这个框架目前还不是很稳定。

为什么不建议现在用 · 四条
  • 还不稳定
  • 在频繁地高速迭代，里面在增加各种各样的功能
  • 设计比较前沿化——比如它试图把 Harness 里面的各个组件全部插件化，所以对刚入门的或者新手来说并不是很好理解，并不是一个新手友好的框架
  • 还在频繁迭代，发布有时候会有各种细微的小 bug

UP 主给出的适用判断也很干脆：

想直接用一个稳定的
那就不要用它
想自己去搞一个 App
如果你懒得自己封装，推荐现在最好还是先不要使用 DeepSeek Harness
但有一类人应该用 · 开发者

对于非常想精调 harness 的开发者来说，因为它这种基于插件模式的设计：

  • 你可以把自己的很多 harness 理念植入进去
  • 或者尝试做自己的一套框架出来
  • 「那它就是一个很好用的东西」
读法提示：「不稳定」和「不值得用」是两件事。UP 主这一节的结构其实是按角色分流——普通用户等它稳定，开发者反而该趁它可塑的时候进场。

3.2Codex（GPT）：目前最成熟的 Coding Agent 框架

13:45 – 14:52

这是全片对基座的最高评价，理由浓缩成一个词——子代理。

Codex 我们目前是认为它是现在最最最成熟的一个 Coding Agent 的框架。

— UP 主原话（13:48）
为什么 · 子代理通信流畅
  • 它的子代理非常有特点，和子代理通信的时候是非常流畅的
  • 如果你的主代理能力比较不错，它可以非常顺利地组织 3～4 个子代理来完成工作
  • 「这个就是我们现在觉得非常不错的点」
对照 · Claude Code 的短板在哪

Claude Code 其实也能完成这个任务，但它的 Desktop 面板非常让人尴尬：

  • 比如你配置了基于 GLM 的一个 Claude Code，那你在它的 Claude Desktop 里面是没法进入 Code 界面的
  • 而且要充会员
  • 所以它对于国内开发者很不友好

注意这里的批评对象是桌面端的产品策略，不是模型或 CLI 能力。这也是本片一个隐含的观察角度：同一个 CLI 工具，它的客户端面板可能会成为你根本用不下去的原因。

Codex 的加分项
  • 对比之下 Codex 就好得多
  • 那些子代理也都支持自定义提示词
  • 可以做并发，可以自己写这些
  • 指令遵循也不错
生态信号 · 别家都在适配它

可以看到像 DeepSeek、还有像 GLM 他们的 Coding Plan，也都在积极地去适配 Responses API 这种 Codex 的专属端点——「这个都是蛮不错的」。

这条信号值得单独标注：当竞争对手主动来适配你的接口，就说明你的框架事实上成了标准。UP 主把它作为「Codex 现在是最好的框架」的旁证。

缺点

3.5Zcode 与 Kimi CLI：好看，但主代理操控子代理的颗粒度不够

15:23 – 16:30

本节是全片技术含量最高的一段，UP 主提出了一个明确的、可验证的框架缺陷机制。

开场先说清楚：GLM 的 Zcode「跟现在的一些其他框架是有明显的一个重大问题的」。然后立刻补上肯定——Zcode 还有 Kimi CLI 其实现在做得都蛮漂亮，可用性对于一个新手来说是可以的。

但接下来是判据：

在我们去调度一些 Agent 的团队来做事情的时候，这些团队之间的异步通信、主代理对于子代理的一个操控的颗粒度是非常重要的。

— UP 主原话（15:40）
缺陷 · 不支持运行中干预

现在在 Kimi CLI 还有 GLM 的 Zcode 中（UP 主加了限定：「如果我使用的版本没什么问题的话，如果是最新版本的话」）：

  • 不支持主代理在子代理运行过程中给它们补送消息
  • 或者说提前结束它们
两面的评价（UP 主自己也说得很矛盾）
  • 既好用又不好用
  • 挺好看的
  • 也知道它在尽力做
  • 而且能看到它们的缓存命中率都挺好的
版本限定：UP 主两次加上前提——「如果我使用的版本没什么问题的话，如果是最新版本的话」。这类框架迭代很快，结论有时效性，引用时请一并带上这个限定。

3.6Kimi 的额度差异：同一个模型，换个壳消耗差很多

Kimi 速度可以，但有个问题
