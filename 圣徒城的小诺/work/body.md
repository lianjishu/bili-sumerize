# 02 模型横评

## 2.1 GPT-6：上限极高，但会「自己加戏」

（00:19）针对 GPT-6，UP 主总结了社区经验与自己和团队的大量开发经验。

**上限非常高**：复杂任务上尤其突出——架构设计、视觉还原，指令遵循也很强。

**痛点一：容易过度设计、过度考虑安全。**
（00:40）你给它一个需求，对话还没结束，它就已经搞出一个「延展性的设计」出来，已经超出你的需求范围了；
还可能造出一堆并不太必要的组件。（00:52）大家都知道的，如果一个架构里有很多你不知道是干什么的组件，
后面一旦改动，你就不知道是什么情况了，架构很容易腐坏。

**用法：必须明确边界。**
（01:02）使用 GPT-6 Astra 时必须明确它的边界，必须约束在 `AGENTS.md` 里面；
或者尽可能少地在主对话里大量使用它——避免它「过于强悍」。
（01:12）而且它的成本极高。所以目前推荐把它接到 Codex 或 OpenCode 里，作为**子代理**使用：
向它询问方案、让它临时做重大决策、做业务性的判断，这样是比较好的；它不适合放在主要工位上干。
> 注：`Astra` 为 GPT-6 的版本/档位名，两源听写一致。

## 2.2 GPT-5.6：综合性价比最好，但会「漂移」

（01:31）GPT 系列还有一个 GPT-5.6（SOTA）。它的能力相对均衡一点。

**毛坯化**：（01:35）做前端和后端项目有点「毛坯化」——功能可以实现，你给一个比较精准的需求它就能跑出来，
但跑出来的功能比较毛坯：写后端可能性能没做优化，写前端则不太好维护扩展，自己写了很多自定义的 CSS 样式。
（01:52）所以它是性价比的选择；但也没有那么性价比——跟 GPT Luna 和 GPT Terra 比起来还是要差一点。
（01:59）不过总体来说，它是大家能使用到的、综合能力性价比最好的模型。

**漂移问题**：（02:04）在长任务上，社区反馈加上自己团队的使用体验，它会出现漂移。
（02:11）比如你经常在 Codex 里开到 50 万甚至 100 万上下文，它差不多在接近 40 万以上时开始有一定漂移，
七八十万以上几乎就不太可用了。
（02:21）**建议**：设置上下文时直接临界设到 `512000`，这样能保证上下文稳定；
如果不经常用长上下文，设到 256K、300K 都可以。

**一句话定位**：（02:37）GPT-6 更像一个相对成熟、偏向架构方向走的工程师；
GPT-5.6 SOTA 则像一个非常综合性的工程师——比较擅长搞开发，搞架构设计什么的还是没有那么好。

## 2.3 Claude Opus 5：发散性与架构感好，但会「自己宣布完工」

（02:52）第三个讲 Claude Opus 5。

**延续了 Claude 系列的明显特点**：（02:58）擅长代码组织，适合明确任务；
你跟它发散一些想法，它可以很好地给你更多反馈，甚至反馈质量不比 GPT-6 差。

**痛点：自我验收不稳。**
（03:12）它在开发上第一是有点**自我验收不稳**。（03:16）就是它可能自己干着干着觉得自己干完了——
这其实是 Claude 系列明显的一个痛点。
（03:22）比如 GPT 系列干不完，一般会诚实地告诉你干不完；但 Claude 有时候会为了目的直接破坏你的架构设计，
或者干着干着漂移了，却觉得自己干完了。（03:33）这是 UP 主在 Claude Opus 5 上发现的问题。
（03:35）所以**必须人工去复查一下**。
（03:37）它的记忆能力相对没有 GPT 系列稳定，但发散性和整体的架构感还是很不错的，依旧可以作为主力模型使用。

**关于 Fable**：（03:46）UP 主相信 Claude Fable 5 或 Fable 5.1 肯定是更强了，但因为平常实在不太会使用；
（03:52）现在它的套餐，像 Max 20 倍档，无论闲鱼上还是别的地方都已经涨到 2000 块钱，还有封号概率，
几乎不会被大家广泛采用了。
> 注：模型名听写为 `Fibro 5 / FBL 5.1`，音近 Fable，此处按 Fable 转写，属**听写推定**。
> 注：「Max 20 倍」指订阅套餐档位，原话如此。

## 2.4 DeepSeek V4.1 Flash：速度快、前端强，但别拿它搞并发

（04:01）接下来是 DeepSeek V4.1 Flash，这是 DeepSeek 新出的模型。
（04:07）因为 4.1 的 Flash 跑出来之后发现结果比 4 的 Pro 还要强，所以直接只保留了这一个版本在 API 上供应。

**长处**：（04:14）它目前看起来不太适合大家用并行去开发——因为它是走 API 计价的。
虽然实测它确实在前端上非常强，token 速度非常快，在一些精准定位上也还不错。
（04:28）前端需要抽卡、后端你需要……因为它仍然是一个只有六七百 B 的模型，
没有像海外那些那么庞大（几个 T），它仍然需要一些 harness 或者人工质量审查。
（04:38）但它已经是一个非常非常合适的模型了——毕竟速度够快，质量还不错，那就很好了。

**并发警告**：（04:45）如果大家经常使用子代理，或者你的 Claude Code、Codex、Claude Code 里面配置了大量子代理、
需要并发执行任务，那**最好不要用这个模型**，因为它会飞快地跑掉你的额度。
（04:58）本来 token 量就快，虽然说在单个会话下它的缓存量很多，
但你如果同时开三个项目、每个里面开三个并发，一天跑个大几百、一两百块钱是没问题的。
（05:10）**血与泪的教训**：如果临时需要，在单个窗口内、没有太多验证的话，用起来还是很便宜的，
而且性能效果确实不错，临时设计一些 UI 也可以，毕竟还支持多模态。
（05:23）但如果搞并发就不是很合适了。尽管如此，UP 主仍然非常喜欢这款模型。

## 2.5 GLM-5.3：最像「工程师」的模型，缺多模态

（05:27）GLM-5.3 也是团队在大量使用的一款模型。（05:31）因为当 GPT 额度不够、Claude 额度不够时，
很多时候就不得不使用 GLM 的 Coding Plan。

**缺点先行**：（05:39）第一个是它蛮贵的，套餐有 5 小时限制还有 7 天限制，蛮多。
（05:50）它也有比较让人喜欢的地方：是一个非常强的**工程师性格**，大概是一个 700 多 B、
做了很好的后训练的模型——相当于在 GLM-5.2 的基础上进一步强化了 coding 能力和 agent 能力。
（06:01）它开发的 benchmark 说可以达到跟 5.6 SOTA 不相上下，体感上确实如此。
（06:07）它可以非常稳定地执行任务；那个 100 万上下文不是假的，真的可以记住——
几乎在五六十万的上下文时还能保持稳定。

**短板**：（06:18）第一，速度相对慢，可能跟服务负载有关系；
（06:24）第二，套餐消耗相当快。（06:28）而且它**缺乏多模态理解能力**——在 UP 主刚测试的项目中，
GLM-5.3 就有明显的视觉和一些设计方面的短板。
（06:37）它在自由探索架构设计上的能力也相对保守，没有那么好。

**定位**：（06:41）所以 UP 主认为 GLM-5.3 更像一款**适合干活的模型**：用 Kimi 去做编排、用 Claude 去做编排，
然后在 OpenCode 或者 Zcode 里把它作为**子代理**去调用。
（06:52）如果让它作为主代理、单流程去执行的话，它有点不太擅长并发执行任务。
（06:59）但它是一个非常好的、工程师化的模型。

## 2.6 Grok 4.6：快、敢试错、不爱做计划

（07:02）Grok 4.6，它的生态会很奇怪：刚出来的时候大家没太当回事，
（07:07）但测了测发现好像没有像那个「美国大豆包」那么蠢；它的开发能力还是很不错的。
（07:13）它响应速度很快，敢于主动快速试错——在快速迭代中的效果提升比较明显。
> 注：「美国大豆包」为 UP 主对某海外模型的戏称，原话如此，保留不做「改正」。

（07:23）这个模型的特点：第一比较快，第二能力还不错，
（07:27）第三，它**不喜欢做太复杂的计划**。像 GLM-5.3、还有 GPT 系列，它们都很喜欢做很长很长的思考再动手；
（07:36）但 Grok 适合什么样的人呢？就是你非常喜欢上来「咣咣咣」就开始干，干完之后跑出来一个东西，然后迅速迭代。
（07:44）它跟 DeepSeek V4.1 Flash 的生态位有点像。
（07:46）毕竟这是刚出来的，当时它效果是最好的，最起码当时它「暴打」了 Gemini 系列。
（07:53）Gemini 现在虽然快，但没有那么好用，3.8 也只能查查文档、简单干点活。

**一点保留**：（07:59）Grok 4.6 还有个问题，就是它的**审美需要一定的纠偏**，没有那么稳定。
（08:05）它对国内的一些 UI 设计，甚至复刻一些已有的界面，效果并不是很好。

## 2.7 Kimi K3：Agent 调度是天生优势，但额度不够、偏贵

（08:14）Kimi K3 需要特别提一下：（08:17）UP 主这次用的效果可能比印象中差很多。
（08:21）Kimi K3 刚出的时候用它去做一些官网、做界面，甚至原型设计都非常精美；但今天的效果真的差强人意。

**天生优势**：（08:28）Kimi 那边本来就预训练的——训练的时候特地强化了它的 Agent 能力，
（08:33）它可以天然地愿意去调度 Agent 的团队，任务拆分也更自然一点。所以它在这个方面的能力是比较强的。

**开发能力中庸**：（08:41）它的开发风格在社区评价中比较中庸。（08:45）因为现在出了很多更新的模型，
刚出来的时候很牛不代表现在也很牛。（08:50）它的开发能力比较靠中间一点，比较适合中小型应用。

**贵**：（08:55）它的额度不是很多，这也是一个重点。Kimi 现在就偏贵了，因为模型尺寸太大、算力消耗太大，
平台订阅太贵。（09:04）你就算买最贵的那一档套餐，如果负责的项目比较重、规模比较大、需要循环迭代，
额度也不够用。（09:12）尤其你又想用网页端，又想用开发侧，有时候还想搞一个什么「龙虾」之类的玩一玩，
那基本上就不够用了。
> 注：「龙虾」两源一致，但所指不明，保留原话。

（09:20）所以它现在的性价比不是很好。（09:22）现在看来如果还降智的话，就没有那么再推荐给大家了。

## 2.8 MiniMax：参数量落后，生态位尴尬

（09:26）MiniMax 系列已经很久没有更新新模型了，UP 主也不很清楚它下一款模型的情况。
（09:33）但目前看起来，这些主流模型的尺寸基本都已经涨到 **500B 以上**了，
MiniMax 现在还处于 500B 以下，就已经非常尴尬了。

**仍保留的优点**：（09:41）它仍然保持着几个优秀的特点——支持多模态、有 100 万上下文、
agent 能力还不错、还相对稳定。
（09:49）但在开发的后训练方面，以及原生知识的复杂性上，参数量太小这个痛点是没办法根治的。
（09:56）所以 MiniMax 后面急需推出一款更强大的模型。

**平替挤压**：（09:59）现在 MiniMax M3 更多时候因为它在上（响应）速度上也有平替，就处于一个很尴尬的生态位：
（10:06）像 DeepSeek V4.1 Flash、还有 Gemini 3.8 Flash、GLM-5.3 Flash，这些快速模型现在都比 MiniMax M3 强；
（10:13）甚至用 Antigravity 里面的 Gemini 3.8 Flash 也比 MiniMax M3 强。

**还剩下什么**：（10:18）所以它就很尴尬。现在就是拿来做一些脚本，或者因为它很便宜——
（10:23）现在还占着便宜的优势，就是一些新手拿来开发一些 UI。
（10:28）毕竟它的 UI 效果在当年那一代模型里，就相当于大家买手机里的「老旗舰」，还算可以的。
（10:35）所以拿来作为初学者用一用，很便宜。目前处于这样一个情况。

## 2.9 通义千问：能力不差，贵在生态位

（10:40）接下来是通义千问系列。（10:42）其实大家现在应该不太会用它来做开发了，
但它最根本的问题不在于能力不行。

（10:45）从今天的测试可以发现，千问这两个模型确实不惊艳。（10:50）为什么说不惊艳？
（10:52）可以看到它们俩做出来的 UI，都没有那种「我可以简单过一下」的水平。
（10:57）千问 3.8 一次性做出来的 UI，达不到那种一眼看上去就能达到 GPT 或者 DeepSeek 抽卡抽出来的效果。
（11:05）但它**多轮跑出来的东西还是很稳定的**，这是一个很大的优势——它跑出来的东西怎么看，好歹像那么回事。

（11:12）所以这两个模型并不是不可用，甚至某种意义上在某些场景下可能更好用：
你拿它多轮迭代，如果很稳定的话，那不就是很好用吗？

**问题出在贵**：（11:23）它的那个 token plan。（11:25）UP 主本次测试买了 39 块钱的 token plan，
（11:30）仅测了一个做 B 站前端这样的小项目——甚至算不上一个正儿八经的大项目，
（11:36）只是一人测了一次，测一次「一次性指令直出」，还有测一次「对抗审查」，
（11:42）就直接把 39 块钱的额度触顶了，差点没跑完，基本干到 98% 了。
（11:48）那就说明在一个正式的大型项目里——比如项目有十几万行、二十几万行——你准备买多贵的套餐呢？
（11:55）它是直接按周限制、按月限制这样算的，你基本上很快就会干掉一周的限额。
（12:01）那么有这个钱，它可能跟 GPT 的额度……如果你真的想跟 GPT 用一样多，两者花的钱可能差不太多，
（12:09）那为什么不去买 GPT 呢？（12:11）当然现在 GPT 20 倍是被禁用了。

**小模型的亮点**：（12:14）所以千问的生态位就比较尴尬。（12:16）但它的小模型像千问 3.8 27B，
仍然是非常有优势的。（12:20）虽然说大的能力没有什么特别惊艳的地方，
（12:23）但蒸馏出的小模型能跟大的保持差不多的后训练水平，或者 coding 水平差不太多，那就很离谱了。
（12:31）毕竟很朴素——某种时候在小参数上那是非常强的，**朴素且稳定**。这是 UP 主的一个发现。
> 注：小模型参数量的听写两源不一致（Whisper 作 27B，自备字幕作 2107B），此处按 27B 转写并标注**存疑**。
> 注：「GPT 20 倍」指订阅档位，原话如此。

# 03 开发基座横评

（12:41）接下来讲一些**开发基座**，这也是最后一个部分。

## 3.1 DeepSeek Harness：前沿但还嫩，适合折腾的人

（12:48）第一个是 DeepSeek 系。（12:50）DeepSeek 现在做的是基于插件化的 **DeepSeek Harness**。
（12:53）团队简单用了一阵子，发现这个框架目前还不是很稳定。（12:57）它是在浏览器里使用的。

**建议先别用**：（13:00）如果大家更喜欢自己去搞一个 App，如果你懒得自己封装，
（13:05）UP 主推荐现在最好还是先不要使用 DeepSeek Harness。
（13:08）因为它第一还不稳定，在频繁地高速迭代，里面在增加各种各样的功能；
（13:13）而且它的设计比较前沿化——比如它试图把 Harness 里面的各个组件全部插件化。
（13:19）所以对刚入门的或者新手来说，它并不是很好理解，并不是一个新手友好的框架。
（13:25）而且它还在频繁迭代，发布有时候会有各种细微的小 bug。
（13:29）所以如果想直接用一个稳定的，那就不要用它了。

**但对开发者是好东西**：（13:32）但对于非常想精调 harness 的开发者来说，
（13:35）因为它这种基于插件模式的设计，你可以把自己的很多 harness 理念植入进去，
（13:40）或者尝试做自己的一套框架出来——那它就是一个很好用的东西。

## 3.2 Codex（GPT）：目前最成熟的 Coding Agent 框架

（13:45）接下来讲 GPT，它是 Codex。（13:48）UP 主目前认为它是现在**最最最成熟的 Coding Agent 框架**。

**为什么**：（13:54）因为它的子代理非常有特点，它和子代理通信的时候非常流畅。
（13:58）如果你的主代理能力比较不错，它可以非常顺利地组织 3～4 个子代理来完成工作。
（14:06）这是 UP 主现在觉得非常不错的点。

**与 Claude Code 的对比**：（14:09）像 Claude Code 其实也能完成这个任务，
（14:12）但它的 Desktop 面板非常让人尴尬。
（14:18）比如你配置了基于 GLM 的一个 Claude Code，那你在它的 Claude Desktop 里面是没法进入 Code 界面的，
（14:28）而且要充会员。（14:29）所以它对于国内开发者很不友好。

**Codex 的优势**：（14:32）但 Codex 就好得多。（14:34）而且 Codex 现在那些子代理也都支持自定义提示词，
可以做并发，可以自己去写这些，而且指令遵循也不错。（14:41）所以 Codex 现在是最好的框架了。
（14:44）也可以看到像 DeepSeek、还有像 GLM 他们的 Coding Plan，
（14:47）也都在积极地去适配 Responses API 这种 Codex 的专属端点，这个都是蛮不错的。

## 3.3 Grok Build：快、轻量，但可读性欠佳
