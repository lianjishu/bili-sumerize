引言

00:00 – 15:03

这一章是过渡，也是整讲的地基。讲师先把上一讲的 data dependency graph 接过来，讲清「软件工程为什么诞生」；然后提出两个贯穿全课的问题：软件它不软（它是容不下任何细微差错的逻辑制品），以及你们为什么只能从最底下开始学。最后落到今天的主题——从 intent 到 spec 的阶段，也就是需求与架构。

1.1接着上一讲的依赖图往下走

00:00

开场复习上一讲：Royce 那篇老论文里的设想是 intent → specification → implementation，然后还需要维护，生命周期没有结束。讲师强调这一路向下的过程看起来像瀑布，但本质是一张依赖网络。

这条链上的三类依赖
  • 在 intent / 需求阶段，你得到的是对软件的认识，这些认识会逐渐进入 specification 的空间，并形成依赖关系
  • 在实现阶段，你会产生模块、函数、代码、测试——各种 artifact，它们之间又有直接与间接的 data dependency
  • 合起来就是一张错综交错的网络，这才是软件工程的真正起点

所以 Royce 的批判逻辑就很清楚了：如果后面某处发现错了，这个错误会回溯到前面某个更早的决定。而那个决定一旦被证明不合理，它「污染」到的所有下游部分都会失效，需要重做——这就是返工成本的来源。

顺着这条线，讲师一口气点出了软件工程的全部内容：怎么做需求分析、怎么做系统设计、怎么做实现，以及用什么方法——包括「有人文关怀」的方法（比如 checklist、怎么管产品经理的人），也包括「技术化」的方法（怎么写测试、能不能做自动化测试与自动化分析）。

1.2traceability 与 UML 的由来

02:30

讲师接着讲了一个「pre-AI 时代的有趣尝试」。出发点很朴素：人很难对齐，人和人很难对齐；而且如果不写文档、只剩一份代码，出了错你甚至不知道该追溯到过去的哪个时刻。

于是在那个年代，软件工程提出了一个非常重要的概念：traceability（可追踪性）。

traceability 想要达到的理想状态
  • 每一个测试用例、每一个代码片段，都能 trace 回一个过去做过的设计
  • 于是「整个系统里到底发生了什么」可以被维护起来
  • 改它会影响谁？改设计会影响哪些测试用例？这些问题都可以被回答

讲师说，如果想要表达这种关系，最理想的是有一个结构化的、有语意的语言来描述它——于是就有了 UML。它的野心是「对齐整个世界上面的软件工程实践」。讲师对此的评价很克制但很肯定：这当然都是有智慧的。

观察点

这一节其实是在给第 2 章埋伏笔。讲师讲 traceability 与 UML 时用的是「曾经的做法」，而第 2 章会让 GPT 现场生成一份带编号 ID、带语义关联的需求说明书——也就是说，AI 用一个下午把 pre-AI 时代要用一整套方法论才能做到的事情做了。讲师不说破，但这条对照线非常清楚。

1.3软件它不软

03:30

这一节是全章最有画面感的一段。讲师问：什么东西是软的？教室里的椅背就是软的——你对它施加压力，它扁下去；你松开，它弹回来；下次坐，它还是好的。

但软件完全不同。它是纯粹的逻辑制品，容不下任何细微的差错。

他用的那个例子：一个 bit 的翻转
  • 你写了一个程序：从 stdin 读入一个 n，然后循环从输入里读 n 个元素
  • 假设这个软件跑在卫星上，一束宇宙射线打中内存，把 n=1 的最高位（符号位）翻成了 1
  • 于是 n 突然变成一个巨大无比的数，程序开始无限地从输入里读数
  • 表现出来就是「卡住了」，或者读了成千上万个元素之后产生 memory error

讲师承认这是个极端例子，但他紧接着举了一个更日常的：现在的数据中心里，随着制程越来越先进，高密度指令在热噪声下可能产生 silent error——同一条指令在这台机器和那台机器上执行，结果就不一样；甚至可能是制造时就有的缺陷，要跑一段时间才暴露。

结论很清楚：软件被认为是人类智慧的集成体，但它同时又承载着来自客户的全部需求。这种「既要求绝对精确，又必须应对开放的物理世界」的张力，就是软件工程困难的本质原因。今天的教务系统就是后者——讲师今天要花时间讲它应该怎么设计、怎么防止它堆积成「史山」。

1.4你们只能从最底下开始学

06:00

讲师提出了一个关于教学的观察：软件工程是关乎整个软件生命周期的学科，但学生被迫只能从最底下开始学。

理由是一段很有说服力的因果链：

为什么必须从最底下开始
  1. 如果你不理解代码是什么、写不出代码
  2. 没有体会过「码农开发软件的痛苦」，那你不可能做好一个产品经理
  3. 因为你无法判断「这件事能不能做到」、「这件事要花多少成本」——这些判断全靠一手经验
  4. 所以你必须先学一门最基础的语言（哪怕它已经过时、没人用了），然后在这个基础上不断累积新知识
  5. 知道世界曾经怎么失败过、新的语言是为什么被创造出来的，才能一点一点往上走

而今天要讲的「需求 / 产品 / 架构」，正是这条链的最上层——从 intent 到 spec 的阶段。讲师说，这恰恰是决定一个软件系统从零开始走向哪里的最关键部分。

1.5为什么先讲版本管理

07:30

讲师解释了一下课程的编排逻辑：前面几讲先讲版本管理，是因为你总是要在一个空的软件上出发。你做 lab、做项目、做任何东西，起点都是「空的」。

先讲清楚「从空的地方出发，软件怎么往后走」，接下来就要把控软件执行的方向——讲师用了一个很好的比喻：

你的船到底是往东南西北哪一个方向开。你一开始的方向选了以后，对后面的影响是非常大的。

讲师解释为什么接下来要讲需求与架构（约 07:45 处）

他也坦白了教学上的一个困难：像需求、产品设计这种题目很难讲，因为你们不会去见真正的客户。所以今天只能用两种方式：借用真实案例，或者把概念本身讲清楚。他选择的是教务系统——一个他每天都在用、而且是真实存在的案例。

讲师还顺便提了一个现状：学校里做软件工程研究的人不少（他提到 CSRank 上按 ECSE 文章数排名靠前），但大部分集中在和编码相关、和 implementation 相关的问题上。有些人会说「traceability 很重要，我们能不能训练一个模型直接从数据里推导出来」——讲师的态度是「那也许 GPT-6 就可以做到」，但因此他更要讲一讲上游这件事。

1.6做 MVP 时会踩的技术债

09:00

讲师给了一个自己的现状描述，很能说明 AI 时代的变化：我现在让 AI 生成代码，只要把边界划定清楚，我其实真的已经不看它的实现了。他甚至预告一会儿要展示 GPT-6 昨天写的代码——那个实现已经超越人类能够理解的范畴了，但 somehow 它是对的。

于是他提出了一个实践公式：把边界划定清楚 + 知道怎么做好的 validation = 可以把 agent swarm 铺开来做实现，而且还能有一定的质量保证。剩下的、真正决定软件能走多远的，就在上游。

做 MVP 时最容易踩的三个坑
  • 技术的决定会污染后续所有需求：同样一个 MVP 需求，加几个字的 prompt 就能得到完全不同的 MVP。你说「用 client-server」，它就会先去选数据库、设计存储；你说「做成 CLI」，它可能只依赖一个命令行的库
  • 写下的文件会进入 agent 的上下文：一旦 db.ts 这种文件被写出来，后面每一个新需求都会带上这整段历史——这就是技术债（technical debt）
  • AI 不会主动打日志：讲师说得很直接——如果你不明确要求，它会生成一个没有任何日志的软件系统，而这也是一种技术债（第 7 节就是他自己被这件事坑到的现场）

这段其实是整讲的隐含主线：MVP 是必要的（它能让你快速走通 intent→spec→implementation 的一个切片），但 MVP 的每一步都会留下不可逆的技术债。后面第 4 章讲的 Event Sourcing，就是「如何从一开始就避免背上最贵的那笔债」。

1.7一次真实的直播翻车

14:00

这一节是意外，但讲师把它讲成了一个教学案例。直播中他的设备突然全部失灵。

我的系统 UI 还在正常工作，我的 OBS 还在正常推流，但是我不知道发生什么，因为我所有的设备都不能用了。我鼠标键盘都没有用了，我插上一个新的鼠标也没有用。

讲师描述直播翻车现场（约 14:17 处）

注意这个现场的特征：界面还在动，推流还在跑，但输入设备全死了。讲师说，这恰好是一个软件工程实践问题——出了问题你要去看日志。而这正 imply 了：你写软件时必须输出足够多的日志。

观察点

讲师把这个事故和上一节的「技术债」接了起来：AI 也不会主动给你打日志。所以这个翻车现场同时说明了两件事——第一，日志是排障的唯一入口；第二，日志这件事必须在写代码的时候就要求，事后补不上。UP 在章节标题里写的「后半音频翻车」，指的就是这一段：约 12:00–14:30 的音频有明显空档，笔记如实标注、不做臆测。

02

需求工程

15:03 – 44:28

这一章用南京大学教务系统做主线案例，把「需求工程」讲成了一个关于失控的故事：需求不断叠加、每加一条就固化一次设计、最终系统里充满无法解释的不一致。讲师的结论很锋利——需求永远不可能说清楚，而且它本身还会变，所以你一旦做了需求分析，就等于背上了技术债。同时他也演示了 AI 在这里能做到什么程度。

2.1曾经为什么很难讲需求工程

15:03

讲师坦白了这门课的长期困境：曾经需求工程很难讲，因为学生不会去见真正的客户，也做不了需求级别的软件系统。

他给出了原因：从你刚入学学编程语言，到毕业的时候，你的能力增长不足以让你面对一个真正的软件客户。买你软件的人要签合同、要验收，而你给不出承诺。

但讲师说，现在这件事变了。

AI 之前
只有极少量的精英独立开发者，经过几年开源社区洗礼后觉得自己可以独立了，会有一些付费用户
现在
独立开发者爆炸式增长，而付费用户「瑟瑟发抖」——因为供给端的能力突然变得很充裕
反差
过去是「你不敢去跟学校签 20 万的合同」，现在是「AI 敢，你也可以跟着敢」

讲师说，所以今天有底气拿一个真实的、他自己每天都在用的系统来讲需求——不是编的案例，是真的。

2.2教务系统：史诗级的需求爆炸

16:03

讲师现场登录教务系统，一边点一边讲。他称之为「史诗级的需求爆炸」——这个系统功能极多，而且很多是「曾经肯定没有、后来被加进去的」。

现场演示中出现的那些功能
  • 一个 AI 搜索框：可以问「仙林教学楼的灯一直没解决，我应该打电话给谁」。讲师说这是个「史诗级的更新」，以前没有
  • 教师课表 / 教学任务 / 学生名单 / 教学周历 / 课程与大纲 / 教材选用：一层套一层，每一层还有下拉框选学年学期
  • 助教管理：还细分了「普通教学班助教」与「慕课助教」，是疫情时期加的需求
  • 期末考试签到表：在非期末时段点击会弹窗告诉你「无法打印」

讲师顺手挑了几个毛病，而且都是有代表性的：

现场抓到的三类问题
  • 隐私边界不清：学生名单里能直接看到电话号码，讲师说这「显然是一个比较糟糕的 feature」
  • 没有审计：他用 AI 生成的 slop 直接把教学周历填满，没有任何人来审计他填的内容
  • 状态与操作不匹配：点「新增助教」弹「请在可维护时段内操作」——已经不能申请了，但界面还在那里

讲师还讲了一个关于需求如何「叠加」的经典例子：疫情之前没有慕课功能；疫情时领导说「要给老师加慕课」；加完之后又需要「慕课的助教」；而慕课助教不能当成普通教学班的助教处理——于是就有了这个「史诗级的 bug」。每一层需求都是在上一层的假设上长出来的。

他最后给了一个很狠的成本对比：这个系统肯定花了很多钱，而这些钱某种程度上还不如变成 token 的补贴发给大家——因为如果用一个 agent 去找「仙林教学楼的灯该找谁」，可能只需要一毛钱两毛钱。

观察点

讲师在这里其实提出了一个关于「业务系统」的尖锐判断：当一个系统已经积累了这么多功能，它本身就已经进入了泥潭。不是因为它做得不好，而是因为需求这种「不断叠加」的生长方式，注定会把系统推向无法理解的状态。这个判断会在第 4 章被形式化。

2.3让 GPT 生成一份需求说明书

23:00

讲师说他做了一件「Agent 敢就行」的事：让 GPT 去探索这个教务系统里和教师相关的功能，产出一份需求说明书。结果是一份正式的《南京大学本科教学服务平台需求说明书》。

讲师对这个结果的评价很有意思：GPT 是懂软件工程的。证据是它的目录结构。

这份自动生成的需求说明书长什么样
  • 有调研方法、证据、边界这类前置说明（不是一上来就堆功能）
  • 有业务目标、成功标准（也就是验收依据）
  • 有详细用例规约、功能需求目录（把每个需求点编号、标出角色与业务目标）
  • 有验收场景与需求清单

讲师自己也承认，从熟悉这个系统的人看来，一份已经做好的系统上再生成这么多东西「就完全是 slop」。但他还是给了公正评价：如果你要做一个真正的工程、面对的是客户，那么「一个术语」就很重要——因为客户/实现方在看不懂的时候可以去查术语，从而完成对齐。

2.4从需求文档到可运行的假系统

30:00

接下来是这一章最震撼的演示。讲师又做了一件事：

我让 GPT 起一个 subagent，然后这个 subagent 不要看任何其他的教务系统，只根据这个需求说明书来实现一个假的教务系统。

讲师描述这次实验（约 30:20 处）

关键在于那个约束：不许看真实系统，只能看需求文档。这是对「需求文档是否充分」的一次真正的验收测试。

结果让讲师「突然又有信心了」——做出来的假系统和他刚才看的真系统「挺像的」，功能上（返回全部教学任务、我的教学任务、本科教材管理、编辑记录、保存记录）都能对上。

演示中的几个细节
  • GPT 给功能起名字很文雅：比如「软件工程实践者的研究方法」这类命名，讲师说「他认为在我的教务系统里面，他起的挺文雅的」
  • 它有前端校验：讲师输入一个非法值（比如负数的缺课次数），前端直接拒绝
  • 但它没做业务语义的校验：讲师记录了一个超过总课时数的缺课次数，系统没有阻止他。讲师点评：「这个其实也不合理，因为这个数字已经超过了所有学习上课次数的总和」

讲师由此给出了这一章最重要的一句结论：

这一节的核心判断

当你的需求是清楚的、当你的需求文档已经写到那个程度的时候，那么编码的事情、traceability 的事情、测试的事情，其实 AI 都能帮你搞定了。你只需要一份需求。

2.5和客户沟通要的是同理心

讲师从演示切回到方法论，讲了一件他认为工科学生最缺的东西：同理心。

他给了一个非常具体的用户画像，而这个画像是这一节的核心：

那个教务员可能是本科学历，然后今年已经 53 岁，还有两年就要退休了——一个优雅的女士。那她在她上大学的时候，可能甚至都没有操作过电脑。

讲师描述真实用户（约 33:30 处）

所以要设计一个教务系统，既要为她设计，也要为年轻人设计。讲师明确说这「完全是另外的一个问题」，不是这门课的重点，但它是做需求时的普遍现实。

工科学生常见的三种错位
  • 假设所有人都会写程序：以自己为原型设计界面，忘了用户不会
  • 追求技术上的最优：你的想法总是「最好的数据库、最高的性能」，但用户只是想字大一点、点鼠标时不要手滑到边上那个按钮
  • 不敢承认自己是外行：你作为一个毛头小伙、本科生，不知道教务员到底想要什么，那你做出来的需求很有可能就是有偏差的

讲师由此引出了「行业壁垒」这件事：一个有 20 年行业经验的公司，它有很多领域知识——它知道教务员想要什么，对学位授予的流程比你清楚，所以知道这个流程应该怎么变成需求文档列表。这就是行业壁垒，也是它的价值。

2.6需求永远不可能说清楚

35:00

这一节把整章的论证收成了一个「定律」。讲师说，软件从空项目开始的时候，没有任何东西是漂移的；但一旦你写出了一个需求列表，AI（或者人类）就立刻给你实现了一版——于是你就背上了技术债。

需求的两条铁律
  • 第一，你永远不可能真的把用户的需求说清楚——不是能力问题，是本质问题
  • 第二，需求不是一成不变的——它会被外部世界改掉，而不是被你说得更清楚

讲师说：「因为我们的定律是，需求永远不可能说清楚。」这句话是下一节那个离散数学案例的引子——那个例子专门用来展示第二律（需求会变）如何摧毁一个原本合理的设计。

2.7离散数学拆课：一条需求引出的连锁反应

36:00

讲师讲了一个真实发生的事：学院把离散数学拆成了上下学期两门课。（他还提到「软院好像还是一门离散数学课」，所以问题更复杂了。）这个教学上的决定，在教务系统里引发了一串连锁反应。

讲师还讲了一个更微妙的点：最后系统中不会出现的东西，还是可以操作的。因为总会有人遇到特例（比如已经读到大六、马上要毕业、而春季又不开那门课），这时唯一的解法就是 override——打电话给工程师改数据库。而这恰恰是系统开始积累「无法解释的不一致」的起点。

2.8我改一个负一，系统就 500 了

42:00

这一节是第 2 章最有画面感的实验。讲师回忆 2018 年他第一次用教师端教务系统，发现可以给学生设置缺课次数，觉得很新鲜。但他立刻提出了一个设计质疑：

他对「缺课次数」这个 feature 的质疑
  • 这个需求不该存在于教务系统里：同学缺课就缺课了，你留证据用签到表、点名表扫描一下就行，不需要在系统里建这个字段
  • 而且学生手册里已经写明了：无故缺课达到多少次就可以除名，这套规则的执行不依赖这个字段

然后他做了一次尝试——他自己形容是「试着绕过了前端的校验」，把一个同学的缺课次数从 0 改成了负 1。他的判断是「这好像也不是什么有害的操作」。结果：

立马所有的只要能够选出这位同学的那个选课记录的页面，就全部 crash 了，直接 500。

讲师描述实验结果（约 42:00 处）

最后他只好打电话给教务，第二天工程师登录数据库把那个负一的记录修掉了。讲师用这个例子做了双重论证：

这个实验说明的两件事
  • 关于代码：一个没有意义的负值可以让整条查询链崩掉——说明系统对「状态空间」的约束没有定义清楚
  • 关于需求：真实系统的需求就是这样的——它是在一个混乱的、不断叠加的生态里长出来的，不是设计出来的

讲师随后把这一章收在一句很有分量的话上：Agentic AI 时代做 MVP 没问题、而且前所未有的容易，你优先实现最重要的功能，看到一个产品马上就知道哪里设计错了，这时候修改的成本是比较低的——但这也给你产生了一个「驾驭 AI 的错觉」。

因为 AI 确实可以往后修，迭代三个版本都行；但一旦这个系统在真实世界里运行得足够久（比如计算机系改成计算机学院、离散数学拆成两门），你原来的设计不起作用的时候，你就面临麻烦了。这就是软件工程里那个著名的论断——There is no silver bullet（没有银弹）。

本章小结
  • 需求工程是软件工程的上游，AI 时代它的权重更大了：需求清楚，编码/traceability/测试都能交给 AI
  • 但需求有两条铁律：说不清楚、而且会变。所以一旦做需求分析就背上了技术债
  • 技术债的核心机制：早期决策固化了假设，后来的需求必须靠改设计来容纳，于是系统长成史山
  • MVP 能让你低成本试错，但它给你「驾驭 AI 的错觉」——真实系统跑久了，no silver bullet 就会现形
03

无处不在的架构

44:28 – 72:32

讲师先反驳一个流行印象：架构不是玄学，也不是只有大系统才有的东西。它的本质就一件事——控制复杂性。然后他用三个尺度的例子把这件事讲穿：十行的非递归汉诺塔、两千行的 Excel 二维码生成器，以及在两者之间反复出现的那条主线——把问题抽象成一层中间表示，而不是直接硬写。

3.1架构就是控制复杂性

44:28

讲师从上一章的技术债接过来：解决它的方式是架构。他先纠正了一个误解。

关于架构的三个常见误解与纠正
  • 误解：架构很高大上、有玄学。纠正：不是的。从你第一次设计任何代码、任何系统的时候，无论它多小，它里面都有架构思维
  • 误解：先做个 MVP 就行，架构以后再说。纠正：MVP 那个 AI 生成的 slop 已经不能算 MVP 了，它已经是一个小型产品原型，维护它会变得非常困难
  • 误解：架构是需求都定完之后的下一步。纠正：架构和需求是连在一起的——你没有需求就不用谈架构了

讲师给出的定义很干脆：架构本质上就是「怎么样去控制一个东西的复杂性」。而当代码稍微有一点规模，你就可以开始考虑「这个复杂性应该怎么分解」。

他随即用两个小例子说明架构无处不在：

两个「小到不能再小」的架构
  1. 写 OJ 时的 main：read input → parse input → process input → write output。这四步的切分本身就是一种分解复杂性的方式
  2. 命令行程序的 argv 处理：这是操作系统和进程之间的约定，它会传过来一个 vector of arguments。你会写 string compare 吗？不会——你会用 getopt，配一个 switch-case 和一个 while 循环

讲师特别强调了 getopt 这个例子的价值：argv 本身是非常复杂的东西（支持长参数、短参数、POSIX 标准）。而 getopt 这个架构的作用，就是把这份复杂性隔开。你因此学会了一种「parser 的架构模式」。

讲师在这里讲了段很不客气的话

他说他很讨厌那种「语言律师」式的授课方式。举例：你要求讲 C++ 的 lambda，老教师的回应是「我讲了呀」——然后他讲的只是 [](){} 的语法，没有讲这个特性应该怎么用。「这个讲了和没讲有什么区别呢？」

所以讲师的方法是：你看到的每一个东西，都要往后想一层——它为什么长这样，它在解决什么复杂性。getopt 的价值不在于它是个函数，而在于它把「一个复杂的字符串」变成「一个简单的 parse state」，从而是一种抵抗需求变化的方式。

3.2十行的架构：非递归汉诺塔

51:00

讲师用一个十行的题目来说明「架构关乎你对需求掌握到什么程度」。这个题目是：写一个非递归的汉诺塔。他说他以前问过刚保研的研究生，能不能写出来——研究生摇头。所以它成了一个课堂例子。

讲师给同一个 prompt 试了多个模型，结果各不相同，而这正好展示了「架构品位的差异」。

同一个 prompt，不同模型的四种反应
  • GPT-6「我不做人类了」：它说「你写不出来是因为你的数学不如我好」，然后找到了汉诺塔的数学性质——盘子移动方向等于 (n + 二进制末尾 0 的个数) 之类的关系，写出了极度优化的代码。讲师说「它应该是对的，但你看不明白」
  • DeepSeek 写得更有人感：它写了一个非常优雅、非常干净的架构，用显式的栈保存「还要继续执行的任务」，每次都执行栈顶的任务。这是标准解法
  • 豆包选对了方案但代码有瑕疵：思路和 DeepSeek 基本一致，但实现上有问题
  • CSDN 上的博客：讲师搜到的第一个非递归汉诺塔代码比 AI Slop 问题还严重（他甚至怀疑那些「高质量」的样子是 AI 营造出来的）。他的评价是：与其看这个，「你还不如跟 AI 学」

在展示完这些之后，讲师给出了他自己的解法思路，这段是这一节的核心。

讲师还特别回应了「为什么大家写不出来」这个问题：大家写不出来的时候，是因为对「递归」这件事理解得不够深。而他课上讲过的一个技巧是——任意程序都可以翻译成递归与非递归两种等价形式，你只要能写出 C 语言的解释器，把任何代码做这个转换「就没有任何难度」。

3.3同一个汉诺塔的四种表达

56:00

讲师把上面的分析收了尾，把四种代码放在一起做了一次「架构水平的横向对比」。

GPT-6
「一切都是数学规律」——从数学性质直接推出移动序列。跳出了问题，但也跳出了「给人读」这件事
DeepSeek
「递归是栈、递归是栈」——它在语料里学到了这个反复出现的表述，于是做了一个正确的、可读的实现
讲师自己
「你们对编程语言世界的理解，投射成了递归与非递归的区别」——再往外走了一步，把它还原成语义层面的等价
CSDN 那份
「这个就属于是训练还没有收敛的」——讲师用这句话很客气地评价了那份质量堪忧的代码

讲师由此得出结论：你在任何一个小的地方，都能看出架构水平的高低。而这句话正是这一章标题「无处不在的架构」的注脚——它不是只有大系统才有的东西，十行代码就能看出差别。

3.4架构能力从哪来

58:00

在进入两千行的例子之前，讲师先回答了那个必然会被问到的问题：架构的能力从哪来？

从你学过的每一个东西上来。如果它是好的、它是优雅的，它促进了你对这个问题的思考。

讲师回答架构能力的来源（约 58:00 处）

他给了一句很凝练的表述：压缩就是智能。你把一个问题压缩了，你就得到了那个 first principle——而有了第一性原理，你就能从它去推导应该怎么做。

架构能力的三类来源
  • 学校里的学习：那些「好的、优雅的」知识，它们促进了你的思考方式
  • 社会上的积累：你必须和「除了教科书、除了做题之外的人」打交道，才能知道一个马上就要退休的、优雅的教务老师是怎么看待教务系统的
  • 共情能力：这是讲师反复强调的——你的想法总是「最好的数据库、最高的性能」，但她只是想要那个字大一点、点鼠标时不要手滑到边上那个按钮

讲师把这条线和第 2 章的「同理心」接上了：架构的好坏有一部分取决于你知不知道用户真正在意什么。而这一点，靠刷题刷不出来。

3.5两千行的架构：Excel 生成二维码

59:00

讲师换到另一个量级：两千行。他在课上讲过一个例子——用 Excel 生成二维码：把一个长字符串编码成能直接扫描的二维码，全部在 Excel 里完成（第一个 sheet 放输入，其他单元格做计算，最后打出一个 01 矩阵）。

讲师要求用软件工程的概念重新理解这个问题。他先说了一个反直觉的判断：

这个需求看起来非常明确
  • 需求就是「Excel 的一个单元格」：有输入的单元格、有输出的单元格
  • 它是一个非常 deterministic 的任务——没有任何模糊之处
  • 但即便如此，它里面仍然有架构的考虑

讲师先演示了 AI 在这个任务上的表现，并提出了一个很有意思的观察：agent 对自己的能力边界是有估计的。

用两个任务对比 agent 的「自知之明」
  1. 简单任务：两个 sheet，第二个是学生实验成绩，第一个是期末考试成绩，要求写一个公式把学号对应的实验成绩拉过来。这在它能力范围内，「就会一把戳」
  2. 困难任务：二维码生成。「显然超出他的能力范围，他还是会分成……试图去分解这个问题，但他也会做价格（代价评估）」
  3. 讲师的结论：至少今天的模型，在做架构这件事上稍稍是有一些落后的

如果直接把二维码算法硬写成 Excel 公式会怎样？讲师给了一个很形象的类比：那个公式会变得极其冗长——「就好比让你们用 brainfuck 去实现一个 non-trivial 的程序」，写出来就会是一团无法阅读的东西。

观察点

这里有个很值得注意的现象：讲师说 AI 在这种任务上会「overreact」——他给了一个非常明确的问题（从字符串到二维码），AI 还要去读文件。同时他也指出，二维码本身是完全有规范的（版本、纠错等级、掩码、数据编码、纠错码），AI 给的实现非常短、也很正确，真正难的是把它塞进 Excel 的约束里。所以问题不在算法，在「目标语言」。

3.6需求看起来明确，其实全是坑

62:00

讲师接着推翻了「这个需求很明确」这个前提，举了三个具体的坑。

三个具体的坑
  • Excel 版本在演化：查找学号对应的成绩，以前是 VLOOKUP，后来微软终于受不了，推出了 XLOOKUP（Extended Lookup）。所以「用哪个版本的语法」是一个真实的选择
  • 兼容性 vs 简洁性的取舍：你到底是要兼容旧版本标准（这样发给教务老师她也能打开），还是要做一个只有自己用、一次性用完就扔的（那就可以用最新语法、写最简单的公式）？这到底是哪个呢
  • 布局会变：如果最后对二维码放的位置不满意，想整体往右移一格——如果所有单元格都是硬编码的，就立即崩溃

讲师用「改版本」这个场景把代价讲得很清楚：如果 AI 给你 webcode 了一个用 Excel 2023 公式的代码，你突然说「不行，要改成 2019、甚至 2003」——全完蛋。你的设计和实现就会从头回到原点，重新再做一遍。

他说，对于一个 2000 行的项目，重做是 OK 的；但如果这个 2000 行的东西已经嵌入到一个巨大无比的教育系统里，和别的部分产生了关联，那就只能「加人、加钱」。讲师对此的评价是：这显然就是一个架构没有设计好的结果。

观察点

这一节是全章最实用的一段：它在说明「需求明确」这件事本身是幻觉。真正让需求变模糊的不是客户说不清，而是实现所依赖的外部环境在变（Excel 版本、布局、使用场景）。所以架构的价值，是让这些变化不需要重写——这就直接引出了下一节的中间语言。

3.7造一门中间语言

67:00

讲师开始给解法。他的推理链是这一章最漂亮的部分：

讲师给了一个很实在的建议：这个中间语言的设计可以让大语言模型去做——你让模型生成「这个语言的二维码计算逻辑」，然后先把它翻译成 Python 去验证公式对不对；等公式写对了，再去生成 Excel。

他还举了表达式树的例子（(E或 A B)、(Xof E)），说你们都写过表达式求值的程序，所以这个中间语言「显然很容易翻译成 Python，你直接把它打包就行了」——递归地处理左右子树，根据节点类型拼起来。而要翻译成 Excel，只需要要求每个节点都有一条渲染成 Excel 公式的规则。

3.8一份中间语言，两种执行方式

71:00

讲师把这个架构总结成了一句口号式的话，也是这一章的收尾。

一份中间语言，两种执行方式。构造一次，我的架构就在这里。

讲师总结这个架构（约 71:00 处）

他把架构画成一张很简单的图：LLM 翻译成中间语言 → 一条路用来验证（Python）→ 一条路用来交付（Excel）。这个结构带来的好处是连锁的：

有了中间语言之后，还能长出什么
  • 优化：如果某处生成的代码太长、性能不好，可以写「改写规则」，把一个程序从一种形态改写成另一种形态（例如把循环里不变的变量计算提到循环外——编译器会自动做，你也可以手动做，还可以让大模型去优化它）
  • Profile 驱动优化：你在计算机系统课上学到的 profiling guided optimization 也接得上了——先知道性能瓶颈在哪，再用 profile 去指导代码应该写成什么样
  • 版本迁移：将来 Excel 版本变了，无非就是把一些算子换一个实现方式

讲师在这里做了最后一次呼应：「这就是我们刚才在第一个最小的例子里讲 getopt 时说的」——写一个命令行工具，第一件事是 getopt，得到一个 parse state，再从 parse state 出发做下一步。和这里的设计一模一样。

他还留了一段给未来：现在 AI Infra 也在做类似的事，人类有很多领域知识，所以在他们领域里有非常多好的设计——这些都是非常值得学习的。

本章小结
  • 架构的本质只有一件事：控制复杂性；它在十行代码里就能看出来
  • 架构关乎你对需求的掌握程度——你对问题的理解层次决定了代码的形状（汉诺塔从「数学性质」到「标准栈」到「形式语义」是三档理解）
  • 「需求明确」是幻觉：真正让需求变模糊的是实现所依赖的外部环境在变
  • 核心手法只有一条：先把输入规整成一个中间表示，再从中间表示出发做后面的事（getopt、表达式树、中间语言都是同一个模式）

4.2一切都是状态机

76:00

讲师开始讲这套架构背后的「第一性原理」。他的推理起点是这句：

我们的软件是物理世界过程在信息世界里面的投影。然后我们的物理世界是有状态的——Everything is a state machine。我自己也是一个 state machine。

讲师给出 CRUD 架构的第一性原理（约 76:50 处）

于是软件系统很容易被建模成 state transition system（状态迁移系统）：有一个状态，加上一组把状态从 A 变成 B 的操作。而这个「状态」通常就用数据库来持久化。

学生
一张表：学号、姓名、院系……
学院
一张表：院系编号、名称……
选课
一张表：学生 × 课程 × 学期……
共同点
各种各样的东西都可以用二维的表来表示——这就是数据库课上讲的东西

讲师还顺带解释了这个范式为什么「看起来完全正确」：在任何一个时间点上，这个状态都代表了「南大现在有哪些学生、谁选了哪些课、有哪些老师」。前后端分离之后，你在浏览器里打开教务系统，看到的就是这个状态的一个投影。这一切非常经典、非常一致、没有任何错误。

4.3数据库为什么要消除冗余

77:00

讲师花了一点时间复习数据库范式，因为这是后面「历史丢失」论证的基础。

他说数据库要求你消除表里所有的冗余，把数据库 factor 成 normal form（范式）。举例：另外一张表要引用一个学生时，尽量不要用姓名来引用——因为会重名，而且就算不重名也会有别的麻烦。更好的做法是去掉姓名列，只放一个学生 ID，这个 ID 相当于一个链接，指向学生信息。

讲师用「改名」这件事解释范式的价值
  • 在中国，学生改名字是合法的——「不要笑，这件事情在中国是合法的」
  • 如果用的是分解/引用的方式，改名字只需要改一处，再记一个曾用名
  • 但如果存了两份名字，那对不起，你要知道这两个地方都要修改——这就是一个很大的代价

讲师把范式的本质讲成一句话：铲除冗余的 dependency——「我一个地方改了以后，我不会需要改另外一个地方」。这是一个非常干净的定义，也为后面「为什么 CRUD 会死」埋下了伏笔：范式解决的是同一时刻的一致性，它完全不管时间上的一致性。

4.4CRUD 丢掉的是历史

79:00

这一节是全片的理论核心。讲师先承认 CRUD 在它自己的假设下是「一个非常经典的价格（架构），没有任何的错误」，然后话锋一转：

但是如果我们想一想教务系统为什么不适合这样的一个 CRUD 的架构？就是因为当前的状态里面，当我看这个当前状态的时候，我看到的是一片祥和的景象。但是这个当前状态所有的历史，它丢掉了。

讲师论证 CRUD 为什么不适合教务系统（约 79:51 处）

他给了一个极其具体的例子来说明「历史丢掉」意味着什么。

那个例子：一个「是否允许毕业」的字段
  • 学生表里有一个列，叫「是否允许毕业」
  • 这个值是由很多其他状态算出来的——每当你修了一个学分、毕业设计状态发生变化，系统就要重新计算一次
  • 它是教务员、辅导员的核心需求：要能导出「现在还没法毕业的学生」名单，然后一个一个谈话
  • 问题在于：这个计算过程依赖的是历史上的计算 dependency，而它们随着当前状态一起没有了

于是就有了那两句话——这是全片被讲得最重的一段：

你知道这个学生可以毕业，但是你不知道他为什么可以毕业。你知道他不能毕业，你不知道他为什么不能毕业。

讲师点出 CRUD 的核心缺失（约 82:11 处）

讲师接着把这套推理推行到底：计算的过程丢掉，而软件又是现实物理过程的一个有损投影——那么结果就是，物理世界里所有建模不了的东西，全部需要通过其他途径来解决。

「其他途径」长什么样（讲师举的三个真实场景）
  1. 政策更新了：领导批准了新的培养计划，但新的数据还没导入系统。学期已经开始了，你已经在用新计划上课，而系统里没有
  2. 教室不能用：第一周整片教学楼在修，教务系统没有建模「教室不可用」这件事，最后靠手改重新安排教室
  3. 不一致堆积：随着时间积累，系统里会有大量不一致的数据，最终变成无法解释的黑洞——「明明这个同学没有交学费、应该毕不了业的，为什么他能毕业呢？」

讲师由此给出了这一章的判词：「所以你们在面对这种需求的时候，CRUD 就会死。」而这恰恰解释了为什么 ERP 这类系统（包括教务系统）的设计实现维护，到今天为止都是一门手艺活。

4.5计算机系改成计算机学院

85:00

讲师用「院系调整」这个真实事件，把 CRUD 的困境演示到了极致。他说南大院系发生调整的时候，教务系统就瑟瑟发抖了——因为 CRUD 是一个 single point of truth，所有的事实都在这一个地方。

问题看起来极简单：把 department 表里「计算机系」的 name 改成「计算机学院」吗？要，还是不要？

两个选择都是错的
  • 如果改：你把这个 object 改了，现在确实是计算机学院了——但你的毕业记录会变成「2011 年毕业于南京大学计算机学院」。这与事实不符，因为 2011 年的时候还没有计算机学院。系统给校友打印证明的时候就会生成错误的信息
  • 如果不改：也很麻烦。因为现在所有的 department 都指向学生的 department ID，还是得把它改过来——于是你需要做一次数据库迁移：创建一个新对象，并且要想清楚新旧对象之间的关联关系

讲师由此把问题上升到范式层面：

CRUD 成立的前提

如果你假设这个世界的投影是不变的，CRUD 当然是一个完美的架构。但只要需求的假设发生在摧毁性变化，那么你每次都要涉及一次数据库迁移 + 业务逻辑重写。代码可以重写，但是你的历史消失了。

而做数据库迁移最可怕的地方在于：你必须考虑历史上所有可能发生的情况，而且这个数据库里已经有很多不一致了——你很难写出一个规则来迁移。更糟的是，你还要冒着「迁移完了之后数据库就坏掉了」的风险。讲师用第 2 章那个负一的例子做了类比：在测试环境做一次迁移，和把一个真实学校里所有数据都做一次迁移，难度是完全不一样的。

4.6一门手艺活的三十年

88:00

讲师在这里切换了视角，从「批判」转向「理解」。他说自己调侃教务系统做得不好，但反过来想——它作为一个软件工程的实践者，可能在这家公司 2000 年成立的时候，唯一的选择就是参考一个已有的企业架构来做教育系统，抢占教育市场的第一桶金。

它把东西做出来了，它就是 CRUD 的。而它一旦背上这个技术债，就要在中国大学教育改革几十年的时间里不断地扛下所有。讲师说：这是一门手艺活。

然后他讲了一个自己的故事，很能说明这门手艺的性质。

他读 PhD 时隔壁组的故事
  1. 他们隔壁的软件工程组，接了学校研究生院教务系统的订单，大概二三十万——在定制化软件里算是比较小的订单
  2. 他的室友就在那个组里，而讲师当时经常跟他抬杠，说这个 CRUD 架构以后会面临各种各样的问题
  3. 果然在那几年，研究生发生巨大扩招，多了很多培养类型，压力也大、经常有调整——这都是他们做需求设计时始料未及的
  4. 最后那个系统彻底变成了史山，然后就不存在了，统一变成公司维护的那个系统

讲师给了公司一个公允的评价：它们还是有一些领域知识，知道这些系统应该怎么「把 13 给浮起来」（把遗留系统用起来）。这再次呼应了第 2 章的「行业壁垒」——需求这件事，光有技术是不够的。

4.7存状态、存操作、存 delta

89:20

讲师开始给解法。他的起点是：「如果我要重做一个教务系统的架构，我就会看到这个 single point of truth 太危险了」——因为它一旦出现任何不一致，你都不知道该怎么把它拿出来。

然后他想到数据结构课上讲过的一种很神奇的东西：persistent data structure——它可以得到这个数据结构的所有历史。这就引出了这一讲最重要的一个洞察。

讲师把这条线落到了具体操作上：如果你想设计一个更好的架构，最好是先把干的所有事情都先记下来——今天张三退学了，今天张三又复学了。

他特别强调了一点：你的逻辑是不能减少的。即便你用记录日志的方式，比如「复学」这件事之前没有考虑过，你依然要为它写一个逻辑。但是——因为事实是不可篡改的、你世界里所有的东西都是对事实的投影，你就有底气了一些，你就不怕错了。你不再像前面那样，做一个数据库迁移的时候手在抖。

4.8你就发明了 Event Sourcing

94:00

讲师把前面那套推理收到一个命名上。

然后祝贺你，你就发明了一个叫 Event Sourcing 的非常经典的设计模式。它可以从历史事件生成状态，而不是直接维护这个 CRUD 的状态。

讲师给这套设计命名（约 95:03 处）

他随即演示了这套设计如何优雅地解决第 5 节那个「计算机系改成计算机学院」的难题：

用历史事件处理院系调整
  • 你可以在某一个时刻插入一个事件，叫 院系调整
  • 查一个过去的人时，你查到的是他过去的版本（比如 2007 年入学、2011 年毕业，那时都是计算机系）
  • 想看较新的信息时，你看到的是 计算机系在 2024 年改为计算机学院 这个事件之后的投影
  • 于是你可以裁出和事实相关的历史，把它 replay 得到此刻要的状态——既可以查询过去，也可以查询现在

讲师也主动回应了必然会被问到的性能问题：「你马上会反应过来，哦是不是会有性能问题？因为要大量 replay。」他的回答是：这都不是很大的问题——我们总可以用快照、缓存各种各样的优化技巧。这是一个 tradeoff，但如果你从一开始就做 Event Sourcing 的设计，很多事情根本不会发生。

他还顺带点了两个相关但不相同的概念：CQRS（Command Query Responsibility Segregation）和 event sourcing 是独立的；还有 domain driven design 这类 buzzword。讲师的态度很一致：

其实你们都不需要……你只要回到最初的 first principle。

讲师对流行词的态度（约 96:31 处）

4.9不需要流行词，回到第一性原理

96:00

讲师在这一节把整讲的方法论收成了一句可操作的话。

面对五十万行的系统该怎么做

你要设计一个 50 万行教育系统的时候，我们跳出这个问题，看到教育系统根源的问题在哪里，你就能做一个正确的架构设计——哪怕你没有听说过这些（流行词），你也能做一个正确的架构设计。

这段话的分量在于它的顺序：讲师没有先讲 Event Sourcing、再讲它解决什么问题；他是先讲清楚 CRUD 为什么会在教务场景下失败，再从失败反推出解法，最后才发现「哦，这个东西有个名字叫 Event Sourcing」。这个顺序本身就是方法论——先有第一性原理，后有名词。

观察点

把整讲串起来看，讲师其实一直在做同一件事：先还原问题的本质，再评价已有方案的适用边界。第 2 章对需求这样（说不清 + 会变）、第 3 章对架构这样（控制复杂性 + 中间表示）、第 4 章对数据库范式也这样（解决的是同时刻一致性，不管时间上的一致性）。这种「追问前提」的习惯，是这一讲最值得带走的东西。

4.10结尾：跳出问题看问题

96:30

讲师用第 3 章就提出过的那句话作为全片的收尾——它同时也是这一讲的方法论旗帜。

架构就一件事：跳出问题，看问题。

讲师在结尾对架构的总结（约 96:40 处）

这句话在这一讲里被验证了四次：

「跳出问题看问题」在四处的应用
  1. 十行汉诺塔：不跳出去，你只能写出一道算法题的答案；跳出去，你能看见「递归 ↔ 非递归」背后的形式语义
  2. 两千行二维码：不跳出去，你只会在 Excel 里硬拼公式；跳出去，你看到的是「Python 与 Excel 之间缺一座桥」
  3. 五十万行教务系统：不跳出去，你只会讨论「用哪个框架」；跳出去，你看到的是「这个系统的根源问题是历史被投影丢掉了」
  4. 需求本身：不跳出去，你会试图把需求一次说清楚；跳出去，你会承认它说不清且会变，然后用一个能容纳变化的架构来兜住它

讲师最后没有再做总结，因为这一整章就是结论。全片在「跳出问题看问题」这六个字上收束——而下一讲（需求和架构 (2)）将继续沿着这条线，从「需求与架构」走向具体的落地。

本章小结
  • AI 交出的教务系统架构有软件工程直觉（乐观锁、幂等、事务、审计、横向扩展），但顶层范式是 CRUD
  • CRUD 的第一性原理是「一切都是状态机 + 一个当前状态」，它只保证同时刻一致性，不管时间上的一致性
  • CRUD 的根本缺陷：知道结果，不知道原因——「你知道他不能毕业，你不知道他为什么不能毕业」
  • 解法是从第一性原理推出的：先把发生过的事实全部记下来，让所有展示都是对事实的投影（＝ Event Sourcing）
  • 最后落到方法：架构就一件事——跳出问题，看问题

  • 「JX / 教务系统 / 教肤系统 / 交付系统」→ 教务系统（讲师口语混说，全文统一）
