这一章是过渡，也是整讲的地基。讲师先把上一讲的 data dependency graph 接过来，讲清「软件工程为什么诞生」；然后提出两个贯穿全课的问题：软件它不软（它是容不下任何细微差错的逻辑制品），以及你们为什么只能从最底下开始学。最后落到今天的主题——从 intent 到 spec 的阶段，也就是需求与架构。

1.1接着上一讲的依赖图往下走

00:00

开场复习上一讲：Royce 那篇老论文里的设想是 intent → specification → implementation，然后还需要维护，生命周期没有结束。讲师强调这一路向下的过程看起来像瀑布，但本质是一张依赖网络。

这条链上的三类依赖
  • 在 intent / 需求阶段，你得到的是对软件的认识，这些认识会逐渐进入 specification 的空间，并形成依赖关系
  • 在实现阶段，你会产生模块、函数、代码、测试——各种 artifact，它们之间又有直接与间接的 data dependency
  • 合起来就是一张错综交错的网络，这才是软件工程的真正起点

所以 Royce 的批判逻辑就很清楚了：如果后面某处发现错了，这个错误会回溯到前面某个更早的决定。而那个决定一旦被证明不合理，它「污染」到的所有下游部分都会失效，需要重做——这就是返工成本的来源。

顺着这条线，讲师一口气点出了软件工程的全部内容：怎么做需求分析、怎么做系统设计、怎么做实现，以及用什么方法——包括「有人文关怀」的方法（比如 checklist、怎么管产品经理的人），也包括「技术化」的方法（怎么写测试、能不能做自动化测试与自动化分析）。

1.2traceability 与 UML 的由来

02:30

讲师接着讲了一个「pre-AI 时代的有趣尝试」。出发点很朴素：人很难对齐，人和人很难对齐；而且如果不写文档、只剩一份代码，出了错你甚至不知道该追溯到过去的哪个时刻。

于是在那个年代，软件工程提出了一个非常重要的概念：traceability（可追踪性）。

traceability 想要达到的理想状态
  • 每一个测试用例、每一个代码片段，都能 trace 回一个过去做过的设计
  • 于是「整个系统里到底发生了什么」可以被维护起来
  • 改它会影响谁？改设计会影响哪些测试用例？这些问题都可以被回答

讲师说，如果想要表达这种关系，最理想的是有一个结构化的、有语意的语言来描述它——于是就有了 UML。它的野心是「对齐整个世界上面的软件工程实践」。讲师对此的评价很克制但很肯定：这当然都是有智慧的。

观察点

这一节其实是在给第 2 章埋伏笔。讲师讲 traceability 与 UML 时用的是「曾经的做法」，而第 2 章会让 GPT 现场生成一份带编号 ID、带语义关联的需求说明书——也就是说，AI 用一个下午把 pre-AI 时代要用一整套方法论才能做到的事情做了。讲师不说破，但这条对照线非常清楚。

1.3软件它不软

03:30

这一节是全章最有画面感的一段。讲师问：什么东西是软的？教室里的椅背就是软的——你对它施加压力，它扁下去；你松开，它弹回来；下次坐，它还是好的。

但软件完全不同。它是纯粹的逻辑制品，容不下任何细微的差错。

他用的那个例子：一个 bit 的翻转
  • 你写了一个程序：从 stdin 读入一个 n，然后循环从输入里读 n 个元素
  • 假设这个软件跑在卫星上，一束宇宙射线打中内存，把 n=1 的最高位（符号位）翻成了 1
  • 于是 n 突然变成一个巨大无比的数，程序开始无限地从输入里读数
  • 表现出来就是「卡住了」，或者读了成千上万个元素之后产生 memory error

讲师承认这是个极端例子，但他紧接着举了一个更日常的：现在的数据中心里，随着制程越来越先进，高密度指令在热噪声下可能产生 silent error——同一条指令在这台机器和那台机器上执行，结果就不一样；甚至可能是制造时就有的缺陷，要跑一段时间才暴露。

结论很清楚：软件被认为是人类智慧的集成体，但它同时又承载着来自客户的全部需求。这种「既要求绝对精确，又必须应对开放的物理世界」的张力，就是软件工程困难的本质原因。今天的教务系统就是后者——讲师今天要花时间讲它应该怎么设计、怎么防止它堆积成「史山」。

1.4你们只能从最底下开始学

06:00

讲师提出了一个关于教学的观察：软件工程是关乎整个软件生命周期的学科，但学生被迫只能从最底下开始学。

理由是一段很有说服力的因果链：

为什么必须从最底下开始
  1. 如果你不理解代码是什么、写不出代码
  2. 没有体会过「码农开发软件的痛苦」，那你不可能做好一个产品经理
  3. 因为你无法判断「这件事能不能做到」、「这件事要花多少成本」——这些判断全靠一手经验
  4. 所以你必须先学一门最基础的语言（哪怕它已经过时、没人用了），然后在这个基础上不断累积新知识
  5. 知道世界曾经怎么失败过、新的语言是为什么被创造出来的，才能一点一点往上走

而今天要讲的「需求 / 产品 / 架构」，正是这条链的最上层——从 intent 到 spec 的阶段。讲师说，这恰恰是决定一个软件系统从零开始走向哪里的最关键部分。

1.5为什么先讲版本管理

07:30

讲师解释了一下课程的编排逻辑：前面几讲先讲版本管理，是因为你总是要在一个空的软件上出发。你做 lab、做项目、做任何东西，起点都是「空的」。

先讲清楚「从空的地方出发，软件怎么往后走」，接下来就要把控软件执行的方向——讲师用了一个很好的比喻：

你的船到底是往东南西北哪一个方向开。你一开始的方向选了以后，对后面的影响是非常大的。

讲师解释为什么接下来要讲需求与架构（约 07:45 处）

他也坦白了教学上的一个困难：像需求、产品设计这种题目很难讲，因为你们不会去见真正的客户。所以今天只能用两种方式：借用真实案例，或者把概念本身讲清楚。他选择的是教务系统——一个他每天都在用、而且是真实存在的案例。

讲师还顺便提了一个现状：学校里做软件工程研究的人不少（他提到 CSRank 上按 ECSE 文章数排名靠前），但大部分集中在和编码相关、和 implementation 相关的问题上。有些人会说「traceability 很重要，我们能不能训练一个模型直接从数据里推导出来」——讲师的态度是「那也许 GPT-6 就可以做到」，但因此他更要讲一讲上游这件事。

1.6做 MVP 时会踩的技术债

09:00

讲师给了一个自己的现状描述，很能说明 AI 时代的变化：我现在让 AI 生成代码，只要把边界划定清楚，我其实真的已经不看它的实现了。他甚至预告一会儿要展示 GPT-6 昨天写的代码——那个实现已经超越人类能够理解的范畴了，但 somehow 它是对的。

于是他提出了一个实践公式：把边界划定清楚 + 知道怎么做好的 validation = 可以把 agent swarm 铺开来做实现，而且还能有一定的质量保证。剩下的、真正决定软件能走多远的，就在上游。

做 MVP 时最容易踩的三个坑
  • 技术的决定会污染后续所有需求：同样一个 MVP 需求，加几个字的 prompt 就能得到完全不同的 MVP。你说「用 client-server」，它就会先去选数据库、设计存储；你说「做成 CLI」，它可能只依赖一个命令行的库
  • 写下的文件会进入 agent 的上下文：一旦 db.ts 这种文件被写出来，后面每一个新需求都会带上这整段历史——这就是技术债（technical debt）
  • AI 不会主动打日志：讲师说得很直接——如果你不明确要求，它会生成一个没有任何日志的软件系统，而这也是一种技术债（第 7 节就是他自己被这件事坑到的现场）

这段其实是整讲的隐含主线：MVP 是必要的（它能让你快速走通 intent→spec→implementation 的一个切片），但 MVP 的每一步都会留下不可逆的技术债。后面第 4 章讲的 Event Sourcing，就是「如何从一开始就避免背上最贵的那笔债」。

1.7一次真实的直播翻车

14:00

这一节是意外，但讲师把它讲成了一个教学案例。直播中他的设备突然全部失灵。

我的系统 UI 还在正常工作，我的 OBS 还在正常推流，但是我不知道发生什么，因为我所有的设备都不能用了。我鼠标键盘都没有用了，我插上一个新的鼠标也没有用。

讲师描述直播翻车现场（约 14:17 处）

注意这个现场的特征：界面还在动，推流还在跑，但输入设备全死了。讲师说，这恰好是一个软件工程实践问题——出了问题你要去看日志。而这正 imply 了：你写软件时必须输出足够多的日志。

观察点

讲师把这个事故和上一节的「技术债」接了起来：AI 也不会主动给你打日志。所以这个翻车现场同时说明了两件事——第一，日志是排障的唯一入口；第二，日志这件事必须在写代码的时候就要求，事后补不上。UP 在章节标题里写的「后半音频翻车」，指的就是这一段：约 12:00–14:30 的音频有明显空档，笔记如实标注、不做臆测。

本章小结
  • Royce 那条链的真相是依赖网络而非流水线；返工成本 = 错误下游已完成的工作量
  • 软件工程是为了应对「软件不软」——它是逻辑制品，容不下任何细微差错，却又必须承载开放的客户需求
  • AI 时代上游更值钱：实现可以外包给 agent swarm，但边界与验证必须人来定
  • MVP 会留下技术债（尤其是「用数据库还是不用」这种早期决定），而日志是最容易被 AI 漏掉的那一笔
