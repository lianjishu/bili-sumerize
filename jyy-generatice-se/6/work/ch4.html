04

回到教务系统

72:32 – 96:50

最后一章回到五十万行的量级。讲师先分析了 AI 交出的那份教务系统架构——它确实有软件工程的直觉，但它本质上是一个 CRUD 架构。然后他从第一性原理出发，论证 CRUD 在教务场景下一定会死：因为它丢掉了历史。最后他一步步推出 Event Sourcing，并说了一句很提气的话——这些流行词你都不需要先学，你只要回到第一性原理。

4.1AI 交出的是一份什么架构

72:32

讲师先播放了 AI 生成教务系统时中间过程的一张截图，并说「当场我就发了一个小红书」。他先说了一下 GPT-6 的代码规模：一个 Monolithic（单体）53KB 的 TSX，加上一个 38KB 的 Services。讲师评价它「还是很有水准的」——虽然真的是单体，但这个东西能做对，真的蛮厉害的。

然后他做了一件很妙的实验：启动了另一个独立 session 去问「这个软件能维护吗」。答案很有意思——AI 说「能」：「现在只不过是把这个业务逻辑挤在几个大文件里，但是这个东西维护是完全没有问题的。」

4.2一切都是状态机

76:00

讲师开始讲这套架构背后的「第一性原理」。他的推理起点是这句：

我们的软件是物理世界过程在信息世界里面的投影。然后我们的物理世界是有状态的——Everything is a state machine。我自己也是一个 state machine。

讲师给出 CRUD 架构的第一性原理（约 76:50 处）

于是软件系统很容易被建模成 state transition system（状态迁移系统）：有一个状态，加上一组把状态从 A 变成 B 的操作。而这个「状态」通常就用数据库来持久化。

学生
一张表：学号、姓名、院系……
学院
一张表：院系编号、名称……
选课
一张表：学生 × 课程 × 学期……
共同点
各种各样的东西都可以用二维的表来表示——这就是数据库课上讲的东西

讲师还顺带解释了这个范式为什么「看起来完全正确」：在任何一个时间点上，这个状态都代表了「南大现在有哪些学生、谁选了哪些课、有哪些老师」。前后端分离之后，你在浏览器里打开教务系统，看到的就是这个状态的一个投影。这一切非常经典、非常一致、没有任何错误。

4.3数据库为什么要消除冗余

77:00

讲师花了一点时间复习数据库范式，因为这是后面「历史丢失」论证的基础。

他说数据库要求你消除表里所有的冗余，把数据库 factor 成 normal form（范式）。举例：另外一张表要引用一个学生时，尽量不要用姓名来引用——因为会重名，而且就算不重名也会有别的麻烦。更好的做法是去掉姓名列，只放一个学生 ID，这个 ID 相当于一个链接，指向学生信息。

讲师用「改名」这件事解释范式的价值
  • 在中国，学生改名字是合法的——「不要笑，这件事情在中国是合法的」
  • 如果用的是分解/引用的方式，改名字只需要改一处，再记一个曾用名
  • 但如果存了两份名字，那对不起，你要知道这两个地方都要修改——这就是一个很大的代价

讲师把范式的本质讲成一句话：铲除冗余的 dependency——「我一个地方改了以后，我不会需要改另外一个地方」。这是一个非常干净的定义，也为后面「为什么 CRUD 会死」埋下了伏笔：范式解决的是同一时刻的一致性，它完全不管时间上的一致性。

4.4CRUD 丢掉的是历史

79:00

这一节是全片的理论核心。讲师先承认 CRUD 在它自己的假设下是「一个非常经典的价格（架构），没有任何的错误」，然后话锋一转：

但是如果我们想一想教务系统为什么不适合这样的一个 CRUD 的架构？就是因为当前的状态里面，当我看这个当前状态的时候，我看到的是一片祥和的景象。但是这个当前状态所有的历史，它丢掉了。

讲师论证 CRUD 为什么不适合教务系统（约 79:51 处）

他给了一个极其具体的例子来说明「历史丢掉」意味着什么。

那个例子：一个「是否允许毕业」的字段
  • 学生表里有一个列，叫「是否允许毕业」
  • 这个值是由很多其他状态算出来的——每当你修了一个学分、毕业设计状态发生变化，系统就要重新计算一次
  • 它是教务员、辅导员的核心需求：要能导出「现在还没法毕业的学生」名单，然后一个一个谈话
  • 问题在于：这个计算过程依赖的是历史上的计算 dependency，而它们随着当前状态一起没有了

于是就有了那两句话——这是全片被讲得最重的一段：

你知道这个学生可以毕业，但是你不知道他为什么可以毕业。你知道他不能毕业，你不知道他为什么不能毕业。

讲师点出 CRUD 的核心缺失（约 82:11 处）

讲师接着把这套推理推行到底：计算的过程丢掉，而软件又是现实物理过程的一个有损投影——那么结果就是，物理世界里所有建模不了的东西，全部需要通过其他途径来解决。

「其他途径」长什么样（讲师举的三个真实场景）
  1. 政策更新了：领导批准了新的培养计划，但新的数据还没导入系统。学期已经开始了，你已经在用新计划上课，而系统里没有
  2. 教室不能用：第一周整片教学楼在修，教务系统没有建模「教室不可用」这件事，最后靠手改重新安排教室
  3. 不一致堆积：随着时间积累，系统里会有大量不一致的数据，最终变成无法解释的黑洞——「明明这个同学没有交学费、应该毕不了业的，为什么他能毕业呢？」

讲师由此给出了这一章的判词：「所以你们在面对这种需求的时候，CRUD 就会死。」而这恰恰解释了为什么 ERP 这类系统（包括教务系统）的设计实现维护，到今天为止都是一门手艺活。

4.5计算机系改成计算机学院

85:00

讲师用「院系调整」这个真实事件，把 CRUD 的困境演示到了极致。他说南大院系发生调整的时候，教务系统就瑟瑟发抖了——因为 CRUD 是一个 single point of truth，所有的事实都在这一个地方。

问题看起来极简单：把 department 表里「计算机系」的 name 改成「计算机学院」吗？要，还是不要？

两个选择都是错的
  • 如果改：你把这个 object 改了，现在确实是计算机学院了——但你的毕业记录会变成「2011 年毕业于南京大学计算机学院」。这与事实不符，因为 2011 年的时候还没有计算机学院。系统给校友打印证明的时候就会生成错误的信息
  • 如果不改：也很麻烦。因为现在所有的 department 都指向学生的 department ID，还是得把它改过来——于是你需要做一次数据库迁移：创建一个新对象，并且要想清楚新旧对象之间的关联关系

讲师由此把问题上升到范式层面：

CRUD 成立的前提

如果你假设这个世界的投影是不变的，CRUD 当然是一个完美的架构。但只要需求的假设发生在摧毁性变化，那么你每次都要涉及一次数据库迁移 + 业务逻辑重写。代码可以重写，但是你的历史消失了。

而做数据库迁移最可怕的地方在于：你必须考虑历史上所有可能发生的情况，而且这个数据库里已经有很多不一致了——你很难写出一个规则来迁移。更糟的是，你还要冒着「迁移完了之后数据库就坏掉了」的风险。讲师用第 2 章那个负一的例子做了类比：在测试环境做一次迁移，和把一个真实学校里所有数据都做一次迁移，难度是完全不一样的。

4.6一门手艺活的三十年

88:00

讲师在这里切换了视角，从「批判」转向「理解」。他说自己调侃教务系统做得不好，但反过来想——它作为一个软件工程的实践者，可能在这家公司 2000 年成立的时候，唯一的选择就是参考一个已有的企业架构来做教育系统，抢占教育市场的第一桶金。

它把东西做出来了，它就是 CRUD 的。而它一旦背上这个技术债，就要在中国大学教育改革几十年的时间里不断地扛下所有。讲师说：这是一门手艺活。

然后他讲了一个自己的故事，很能说明这门手艺的性质。

他读 PhD 时隔壁组的故事
  1. 他们隔壁的软件工程组，接了学校研究生院教务系统的订单，大概二三十万——在定制化软件里算是比较小的订单
  2. 他的室友就在那个组里，而讲师当时经常跟他抬杠，说这个 CRUD 架构以后会面临各种各样的问题
  3. 果然在那几年，研究生发生巨大扩招，多了很多培养类型，压力也大、经常有调整——这都是他们做需求设计时始料未及的
  4. 最后那个系统彻底变成了史山，然后就不存在了，统一变成公司维护的那个系统

讲师给了公司一个公允的评价：它们还是有一些领域知识，知道这些系统应该怎么「把 13 给浮起来」（把遗留系统用起来）。这再次呼应了第 2 章的「行业壁垒」——需求这件事，光有技术是不够的。

4.7存状态、存操作、存 delta

89:20

讲师开始给解法。他的起点是：「如果我要重做一个教务系统的架构，我就会看到这个 single point of truth 太危险了」——因为它一旦出现任何不一致，你都不知道该怎么把它拿出来。

然后他想到数据结构课上讲过的一种很神奇的东西：persistent data structure——它可以得到这个数据结构的所有历史。这就引出了这一讲最重要的一个洞察。

讲师把这条线落到了具体操作上：如果你想设计一个更好的架构，最好是先把干的所有事情都先记下来——今天张三退学了，今天张三又复学了。

他特别强调了一点：你的逻辑是不能减少的。即便你用记录日志的方式，比如「复学」这件事之前没有考虑过，你依然要为它写一个逻辑。但是——因为事实是不可篡改的、你世界里所有的东西都是对事实的投影，你就有底气了一些，你就不怕错了。你不再像前面那样，做一个数据库迁移的时候手在抖。

4.8你就发明了 Event Sourcing

94:00

讲师把前面那套推理收到一个命名上。

然后祝贺你，你就发明了一个叫 Event Sourcing 的非常经典的设计模式。它可以从历史事件生成状态，而不是直接维护这个 CRUD 的状态。

讲师给这套设计命名（约 95:03 处）

他随即演示了这套设计如何优雅地解决第 5 节那个「计算机系改成计算机学院」的难题：

用历史事件处理院系调整
  • 你可以在某一个时刻插入一个事件，叫 院系调整
  • 查一个过去的人时，你查到的是他过去的版本（比如 2007 年入学、2011 年毕业，那时都是计算机系）
  • 想看较新的信息时，你看到的是 计算机系在 2024 年改为计算机学院 这个事件之后的投影
  • 于是你可以裁出和事实相关的历史，把它 replay 得到此刻要的状态——既可以查询过去，也可以查询现在

讲师也主动回应了必然会被问到的性能问题：「你马上会反应过来，哦是不是会有性能问题？因为要大量 replay。」他的回答是：这都不是很大的问题——我们总可以用快照、缓存各种各样的优化技巧。这是一个 tradeoff，但如果你从一开始就做 Event Sourcing 的设计，很多事情根本不会发生。

他还顺带点了两个相关但不相同的概念：CQRS（Command Query Responsibility Segregation）和 event sourcing 是独立的；还有 domain driven design 这类 buzzword。讲师的态度很一致：

其实你们都不需要……你只要回到最初的 first principle。

讲师对流行词的态度（约 96:31 处）

4.9不需要流行词，回到第一性原理

96:00

讲师在这一节把整讲的方法论收成了一句可操作的话。

面对五十万行的系统该怎么做

你要设计一个 50 万行教育系统的时候，我们跳出这个问题，看到教育系统根源的问题在哪里，你就能做一个正确的架构设计——哪怕你没有听说过这些（流行词），你也能做一个正确的架构设计。

这段话的分量在于它的顺序：讲师没有先讲 Event Sourcing、再讲它解决什么问题；他是先讲清楚 CRUD 为什么会在教务场景下失败，再从失败反推出解法，最后才发现「哦，这个东西有个名字叫 Event Sourcing」。这个顺序本身就是方法论——先有第一性原理，后有名词。

观察点

把整讲串起来看，讲师其实一直在做同一件事：先还原问题的本质，再评价已有方案的适用边界。第 2 章对需求这样（说不清 + 会变）、第 3 章对架构这样（控制复杂性 + 中间表示）、第 4 章对数据库范式也这样（解决的是同时刻一致性，不管时间上的一致性）。这种「追问前提」的习惯，是这一讲最值得带走的东西。

4.10结尾：跳出问题看问题

96:30

讲师用第 3 章就提出过的那句话作为全片的收尾——它同时也是这一讲的方法论旗帜。

架构就一件事：跳出问题，看问题。

讲师在结尾对架构的总结（约 96:40 处）

这句话在这一讲里被验证了四次：

「跳出问题看问题」在四处的应用
  1. 十行汉诺塔：不跳出去，你只能写出一道算法题的答案；跳出去，你能看见「递归 ↔ 非递归」背后的形式语义
  2. 两千行二维码：不跳出去，你只会在 Excel 里硬拼公式；跳出去，你看到的是「Python 与 Excel 之间缺一座桥」
  3. 五十万行教务系统：不跳出去，你只会讨论「用哪个框架」；跳出去，你看到的是「这个系统的根源问题是历史被投影丢掉了」
  4. 需求本身：不跳出去，你会试图把需求一次说清楚；跳出去，你会承认它说不清且会变，然后用一个能容纳变化的架构来兜住它

讲师最后没有再做总结，因为这一整章就是结论。全片在「跳出问题看问题」这六个字上收束——而下一讲（需求和架构 (2)）将继续沿着这条线，从「需求与架构」走向具体的落地。

本章小结
  • AI 交出的教务系统架构有软件工程直觉（乐观锁、幂等、事务、审计、横向扩展），但顶层范式是 CRUD
  • CRUD 的第一性原理是「一切都是状态机 + 一个当前状态」，它只保证同时刻一致性，不管时间上的一致性
  • CRUD 的根本缺陷：知道结果，不知道原因——「你知道他不能毕业，你不知道他为什么不能毕业」
  • 解法是从第一性原理推出的：先把发生过的事实全部记下来，让所有展示都是对事实的投影（＝ Event Sourcing）
  • 最后落到方法：架构就一件事——跳出问题，看问题
