03

无处不在的架构

44:28 – 72:32

讲师先反驳一个流行印象：架构不是玄学，也不是只有大系统才有的东西。它的本质就一件事——控制复杂性。然后他用三个尺度的例子把这件事讲穿：十行的非递归汉诺塔、两千行的 Excel 二维码生成器，以及在两者之间反复出现的那条主线——把问题抽象成一层中间表示，而不是直接硬写。

3.1架构就是控制复杂性

44:28

讲师从上一章的技术债接过来：解决它的方式是架构。他先纠正了一个误解。

关于架构的三个常见误解与纠正
  • 误解：架构很高大上、有玄学。纠正：不是的。从你第一次设计任何代码、任何系统的时候，无论它多小，它里面都有架构思维
  • 误解：先做个 MVP 就行，架构以后再说。纠正：MVP 那个 AI 生成的 slop 已经不能算 MVP 了，它已经是一个小型产品原型，维护它会变得非常困难
  • 误解：架构是需求都定完之后的下一步。纠正：架构和需求是连在一起的——你没有需求就不用谈架构了

讲师给出的定义很干脆：架构本质上就是「怎么样去控制一个东西的复杂性」。而当代码稍微有一点规模，你就可以开始考虑「这个复杂性应该怎么分解」。

他随即用两个小例子说明架构无处不在：

两个「小到不能再小」的架构
  1. 写 OJ 时的 main：read input → parse input → process input → write output。这四步的切分本身就是一种分解复杂性的方式
  2. 命令行程序的 argv 处理：这是操作系统和进程之间的约定，它会传过来一个 vector of arguments。你会写 string compare 吗？不会——你会用 getopt，配一个 switch-case 和一个 while 循环

讲师特别强调了 getopt 这个例子的价值：argv 本身是非常复杂的东西（支持长参数、短参数、POSIX 标准）。而 getopt 这个架构的作用，就是把这份复杂性隔开。你因此学会了一种「parser 的架构模式」。

讲师在这里讲了段很不客气的话

他说他很讨厌那种「语言律师」式的授课方式。举例：你要求讲 C++ 的 lambda，老教师的回应是「我讲了呀」——然后他讲的只是 [](){} 的语法，没有讲这个特性应该怎么用。「这个讲了和没讲有什么区别呢？」

所以讲师的方法是：你看到的每一个东西，都要往后想一层——它为什么长这样，它在解决什么复杂性。getopt 的价值不在于它是个函数，而在于它把「一个复杂的字符串」变成「一个简单的 parse state」，从而是一种抵抗需求变化的方式。

3.2十行的架构：非递归汉诺塔

51:00

讲师用一个十行的题目来说明「架构关乎你对需求掌握到什么程度」。这个题目是：写一个非递归的汉诺塔。他说他以前问过刚保研的研究生，能不能写出来——研究生摇头。所以它成了一个课堂例子。

讲师给同一个 prompt 试了多个模型，结果各不相同，而这正好展示了「架构品位的差异」。

同一个 prompt，不同模型的四种反应
  • GPT-6「我不做人类了」：它说「你写不出来是因为你的数学不如我好」，然后找到了汉诺塔的数学性质——盘子移动方向等于 (n + 二进制末尾 0 的个数) 之类的关系，写出了极度优化的代码。讲师说「它应该是对的，但你看不明白」
  • DeepSeek 写得更有人感：它写了一个非常优雅、非常干净的架构，用显式的栈保存「还要继续执行的任务」，每次都执行栈顶的任务。这是标准解法
  • 豆包选对了方案但代码有瑕疵：思路和 DeepSeek 基本一致，但实现上有问题
  • CSDN 上的博客：讲师搜到的第一个非递归汉诺塔代码比 AI Slop 问题还严重（他甚至怀疑那些「高质量」的样子是 AI 营造出来的）。他的评价是：与其看这个，「你还不如跟 AI 学」

在展示完这些之后，讲师给出了他自己的解法思路，这段是这一节的核心。

讲师还特别回应了「为什么大家写不出来」这个问题：大家写不出来的时候，是因为对「递归」这件事理解得不够深。而他课上讲过的一个技巧是——任意程序都可以翻译成递归与非递归两种等价形式，你只要能写出 C 语言的解释器，把任何代码做这个转换「就没有任何难度」。

3.3同一个汉诺塔的四种表达

56:00

讲师把上面的分析收了尾，把四种代码放在一起做了一次「架构水平的横向对比」。

GPT-6
「一切都是数学规律」——从数学性质直接推出移动序列。跳出了问题，但也跳出了「给人读」这件事
DeepSeek
「递归是栈、递归是栈」——它在语料里学到了这个反复出现的表述，于是做了一个正确的、可读的实现
讲师自己
「你们对编程语言世界的理解，投射成了递归与非递归的区别」——再往外走了一步，把它还原成语义层面的等价
CSDN 那份
「这个就属于是训练还没有收敛的」——讲师用这句话很客气地评价了那份质量堪忧的代码

讲师由此得出结论：你在任何一个小的地方，都能看出架构水平的高低。而这句话正是这一章标题「无处不在的架构」的注脚——它不是只有大系统才有的东西，十行代码就能看出差别。

3.4架构能力从哪来

58:00

在进入两千行的例子之前，讲师先回答了那个必然会被问到的问题：架构的能力从哪来？

从你学过的每一个东西上来。如果它是好的、它是优雅的，它促进了你对这个问题的思考。

讲师回答架构能力的来源（约 58:00 处）

他给了一句很凝练的表述：压缩就是智能。你把一个问题压缩了，你就得到了那个 first principle——而有了第一性原理，你就能从它去推导应该怎么做。

架构能力的三类来源
  • 学校里的学习：那些「好的、优雅的」知识，它们促进了你的思考方式
  • 社会上的积累：你必须和「除了教科书、除了做题之外的人」打交道，才能知道一个马上就要退休的、优雅的教务老师是怎么看待教务系统的
  • 共情能力：这是讲师反复强调的——你的想法总是「最好的数据库、最高的性能」，但她只是想要那个字大一点、点鼠标时不要手滑到边上那个按钮

讲师把这条线和第 2 章的「同理心」接上了：架构的好坏有一部分取决于你知不知道用户真正在意什么。而这一点，靠刷题刷不出来。

3.5两千行的架构：Excel 生成二维码

59:00

讲师换到另一个量级：两千行。他在课上讲过一个例子——用 Excel 生成二维码：把一个长字符串编码成能直接扫描的二维码，全部在 Excel 里完成（第一个 sheet 放输入，其他单元格做计算，最后打出一个 01 矩阵）。

讲师要求用软件工程的概念重新理解这个问题。他先说了一个反直觉的判断：

这个需求看起来非常明确
  • 需求就是「Excel 的一个单元格」：有输入的单元格、有输出的单元格
  • 它是一个非常 deterministic 的任务——没有任何模糊之处
  • 但即便如此，它里面仍然有架构的考虑

讲师先演示了 AI 在这个任务上的表现，并提出了一个很有意思的观察：agent 对自己的能力边界是有估计的。

用两个任务对比 agent 的「自知之明」
  1. 简单任务：两个 sheet，第二个是学生实验成绩，第一个是期末考试成绩，要求写一个公式把学号对应的实验成绩拉过来。这在它能力范围内，「就会一把戳」
  2. 困难任务：二维码生成。「显然超出他的能力范围，他还是会分成……试图去分解这个问题，但他也会做价格（代价评估）」
  3. 讲师的结论：至少今天的模型，在做架构这件事上稍稍是有一些落后的

如果直接把二维码算法硬写成 Excel 公式会怎样？讲师给了一个很形象的类比：那个公式会变得极其冗长——「就好比让你们用 brainfuck 去实现一个 non-trivial 的程序」，写出来就会是一团无法阅读的东西。

观察点

这里有个很值得注意的现象：讲师说 AI 在这种任务上会「overreact」——他给了一个非常明确的问题（从字符串到二维码），AI 还要去读文件。同时他也指出，二维码本身是完全有规范的（版本、纠错等级、掩码、数据编码、纠错码），AI 给的实现非常短、也很正确，真正难的是把它塞进 Excel 的约束里。所以问题不在算法，在「目标语言」。

3.6需求看起来明确，其实全是坑

62:00

讲师接着推翻了「这个需求很明确」这个前提，举了三个具体的坑。

三个具体的坑
  • Excel 版本在演化：查找学号对应的成绩，以前是 VLOOKUP，后来微软终于受不了，推出了 XLOOKUP（Extended Lookup）。所以「用哪个版本的语法」是一个真实的选择
  • 兼容性 vs 简洁性的取舍：你到底是要兼容旧版本标准（这样发给教务老师她也能打开），还是要做一个只有自己用、一次性用完就扔的（那就可以用最新语法、写最简单的公式）？这到底是哪个呢
  • 布局会变：如果最后对二维码放的位置不满意，想整体往右移一格——如果所有单元格都是硬编码的，就立即崩溃

讲师用「改版本」这个场景把代价讲得很清楚：如果 AI 给你 webcode 了一个用 Excel 2023 公式的代码，你突然说「不行，要改成 2019、甚至 2003」——全完蛋。你的设计和实现就会从头回到原点，重新再做一遍。

他说，对于一个 2000 行的项目，重做是 OK 的；但如果这个 2000 行的东西已经嵌入到一个巨大无比的教育系统里，和别的部分产生了关联，那就只能「加人、加钱」。讲师对此的评价是：这显然就是一个架构没有设计好的结果。

观察点

这一节是全章最实用的一段：它在说明「需求明确」这件事本身是幻觉。真正让需求变模糊的不是客户说不清，而是实现所依赖的外部环境在变（Excel 版本、布局、使用场景）。所以架构的价值，是让这些变化不需要重写——这就直接引出了下一节的中间语言。

3.7造一门中间语言

67:00

讲师开始给解法。他的推理链是这一章最漂亮的部分：

讲师给了一个很实在的建议：这个中间语言的设计可以让大语言模型去做——你让模型生成「这个语言的二维码计算逻辑」，然后先把它翻译成 Python 去验证公式对不对；等公式写对了，再去生成 Excel。

他还举了表达式树的例子（(E或 A B)、(Xof E)），说你们都写过表达式求值的程序，所以这个中间语言「显然很容易翻译成 Python，你直接把它打包就行了」——递归地处理左右子树，根据节点类型拼起来。而要翻译成 Excel，只需要要求每个节点都有一条渲染成 Excel 公式的规则。

3.8一份中间语言，两种执行方式

71:00

讲师把这个架构总结成了一句口号式的话，也是这一章的收尾。

一份中间语言，两种执行方式。构造一次，我的架构就在这里。

讲师总结这个架构（约 71:00 处）

他把架构画成一张很简单的图：LLM 翻译成中间语言 → 一条路用来验证（Python）→ 一条路用来交付（Excel）。这个结构带来的好处是连锁的：

有了中间语言之后，还能长出什么
  • 优化：如果某处生成的代码太长、性能不好，可以写「改写规则」，把一个程序从一种形态改写成另一种形态（例如把循环里不变的变量计算提到循环外——编译器会自动做，你也可以手动做，还可以让大模型去优化它）
  • Profile 驱动优化：你在计算机系统课上学到的 profiling guided optimization 也接得上了——先知道性能瓶颈在哪，再用 profile 去指导代码应该写成什么样
  • 版本迁移：将来 Excel 版本变了，无非就是把一些算子换一个实现方式

讲师在这里做了最后一次呼应：「这就是我们刚才在第一个最小的例子里讲 getopt 时说的」——写一个命令行工具，第一件事是 getopt，得到一个 parse state，再从 parse state 出发做下一步。和这里的设计一模一样。

他还留了一段给未来：现在 AI Infra 也在做类似的事，人类有很多领域知识，所以在他们领域里有非常多好的设计——这些都是非常值得学习的。

本章小结
  • 架构的本质只有一件事：控制复杂性；它在十行代码里就能看出来
  • 架构关乎你对需求的掌握程度——你对问题的理解层次决定了代码的形状（汉诺塔从「数学性质」到「标准栈」到「形式语义」是三档理解）
  • 「需求明确」是幻觉：真正让需求变模糊的是实现所依赖的外部环境在变
  • 核心手法只有一条：先把输入规整成一个中间表示，再从中间表示出发做后面的事（getopt、表达式树、中间语言都是同一个模式）
