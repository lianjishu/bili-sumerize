02

回到软件开发

17:37 – 39:01

新闻播完，回到正题。这一章回答的问题很朴素：现在我们有了这么强的模型，那「软件开发」这件事到底还剩下什么要做？讲师的答案是回到最初的三段式——intent、specification、implementation——然后指出：今天的答案就是 做 MVP，而且他用自己用 AI 驱动标签打印机和扫描仪的真实项目证明了这条路走得通。

2.1斩杀线一直在上移

17:37

讲师用「斩杀线」这个词描述一种不断上移的技能门槛：以前不会写 SQL 就会被淘汰，后来门槛变成不会用框架，再后来变成不会用 AI。这条线一直在往上走，不会停。

他的态度是：不要因为「这个技能以后可能没用」就不学。因为你判断不准哪一年会失效，而学的过程本身会给你可迁移的东西。这也是他为什么还要继续上课的原因——课本身也在被这条线追着改。

观察点

这不是安慰话。整门课的设计都建立在「斩杀线会上移」这个前提上：与其教一个五年后会过时的具体工具，不如教你面对新工具时怎么重新设计工作流。前面几讲重新设计版本管理系统，就是这套方法论的应用。

2.2intent、specification、implementation

19:00

这是整门课的老框架，讲师又拎出来讲了一遍，因为它解释了「为什么 AI 再强也还要有人」。

intent
你脑子里真正想要的东西。它是模糊的、不完整的、甚至在你说出来之前自己都不完全清楚的
specification
你用某种语言把 intent 写下来的结果。它是一次有损压缩——写下来的永远比想说的少
implementation
能运行的代码。它是对 specification 的又一次转换，同样有损

讲师强调：gap 不在「AI 写不出代码」这一段，而在前面两段。AI 已经能很可靠地把一份清晰的 spec 变成能跑的 implementation；问题是你很难把 intent 无损地变成 spec，也很容易以为自己写清楚了其实没有。

三段式最容易出错的三个位置
  • intent → spec：你脑子里其实有三个互相冲突的目标，写下来时只写了一个，另外两个被悄悄丢掉了
  • spec 的隐含假设：你写「用户点确认后保存」，但没写「如果没有登录怎么办」「如果网络断了怎么办」
  • spec → implementation 的歧义：一句话可以有一百种合理实现，AI 选了不是你心里的那一种——而且它看起来完全正确

2.3今天的答案：做 MVP

22:00

既然 gap 在前面两段，那解决办法就不是「把 spec 写得更全」，而是尽快把东西做出来，用真实反馈去修正 intent。这就是 MVP——minimum viable product，最小可行产品。

讲师在这句话上有个小口误：他先说成 minimum variable product，随即自己改口纠正成 viable。这个口误本身也挺说明问题——很多人心里的 MVP 确实变成了「变量最小的产品」，而不是「能验证想法的最小产品」。

MVP 在这门课里的准确含义
  • 它不是「少做一点功能」，而是用最小的代价换到最关键的反馈
  • 它验证的对象不是「功能能不能跑」，而是「你的 intent 对不对」
  • 所以 MVP 的选择标准不是「哪个容易做」，而是「哪个信息量最大」

接下来的几节，讲师用自己的真实项目来展示 MVP 是怎么跑的——而且这个项目正好是「AI 帮我造工具」，而非「AI 帮我写业务代码」。

2.4标签打印机与扫描仪：我的真实案例

25:00

讲师讲了他最近做的一个小项目：用 AI 驱动一台标签打印机和一台佳能扫描仪。这个项目的起点很具体——他有实际需求（打印标签、扫描文档），但厂商自带的软件极其难用，而且在跨平台上有各种限制。

他的做法不是去研究厂商那一大坨软件怎么用，而是把它整个屏蔽掉，自己从总线层重新做一遍抽象。

他实际做的事
  1. 在计算机总线上直接识别到设备，绕过厂商软件
  2. 把设备驱动抽象成最基本的三个动作：read / write / ioctl
  3. 在这之上再抽象一层：扫描仪提供 scan，打印机提供 print(image)
  4. 让上层代码只依赖这层接口，与具体设备实现完全解耦
  5. 用一个 AI agent 专门对付打印机，另一个专门对付扫描仪，两个并行推进

结果是：花了五个小时，把额度用完，做出了产品级的效果。这里「产品级」指的是——如果去掉厂商软件的存在，这个东西就是一个能用的产品。

观察点

这个案例的关键不在「AI 会写驱动」，而在于讲师选择了正确的抽象层。他没有让 AI 去「模仿厂商软件的用法」（那是最脏的一层），而是退到 read/write/ioctl 这种几十年不变的稳定接口上。抽象层的选择决定了这个项目能不能在五小时内做完。

2.5抽象：从 ioctl 到 print(image)

28:20

讲师把上一节的抽象过程画出来讲了一遍，这实际上是这一章最有方法论价值的一段。

讲师特别提醒了一点：这套抽象还有一个隐性收益。当他后来想换实现（比如从 LP 路径换成通用打印驱动）时，上层代码一行都不用改。这就是「接口与实现解耦」在真实项目里的兑现时刻。

2.6软件公司正在彻底消亡

31:00

由这个项目，讲师提出一个很大胆的判断：软件公司正在彻底消亡。他给出的理由是「驱动开发」这门生意的经济学被彻底改写了。

驱动开发为什么是一门要消失的生意
  • 开发一套驱动的人力成本极高——要养一批懂底层的人
  • 而且必须维护多个平台：Windows 一套、Mac 一套，各写一遍
  • 但用户愿意为驱动付的钱很低，因为它是中间件，用户感知不到
  • 于是这块业务一直是「成本高、收益低」——现在 AI 把成本那一侧几乎打到零

讲师的意思不是「公司会消失」，而是「靠卖中间件赚钱」这个模式会消失。当一个人用五小时就能做出产品级效果的驱动层，那这个市场就不再需要一家公司来专门做这件事。

2.7豆包手机：APP 沦为接口

34:00

讲师接着讲了一个观察：豆包手机（字节与手机厂商的合作形态）。他的判断是：APP 正在退化成 computer use 的接口——不再需要人去点那个精心设计的界面，而是让模型去点。

过去
APP 的价值在界面：把功能做成好看的按钮，人来点
现在
APP 的价值在可被调用的能力：模型能不能可靠地完成「点外卖」这件事
接口化
阿里千问这类助手开始把各家的服务整合进来，用户面对的不再是 APP 列表，而是一个对话框
组合
讲师提到 Jab 与豆包手机的搭配——模型 + 设备代理的组合形态

他还预告了下一个实验的要求：把 assistant 接到一个物理设备上。他举了一个电子墨水瓶的例子——有同学用 Claude Opus 4.6 去解包 APK、逆向出蓝牙协议，从而控制那个设备。这条路已经有人走通了。

观察点

从「AI 写驱动」到「AI 直接操控 APP」到「AI 逆向蓝牙协议控制硬件」，这三件事串起来是同一条线：软件的「界面」这一层正在被模型吃掉，剩下的价值全部沉淀到接口层。这对做产品的人是坏消息（界面优势没了），对做抽象的人是好消息（接口设计能力更值钱了）。

2.81960 年的软件危机现场

37:00

本章的最后，讲师把时间线拉回到 1960 年代，用几个非常具体的细节来说明「软件危机」是怎么发生的。

他举的那些历史细节
  • 1960 年，硬件比程序员贵：一台机器的钱能养很多人，所以「省机器时间」是最高优先级，人怎么写代码不重要
  • 所以大家画流程图，然后手工翻译成机器代码——因为让机器多跑一遍太贵了
  • 程序员脑子里只有汇编与 goto，因为那是当时唯一被优化过的写法
  • Dijkstra 1957 年登记职业时被写成「理论物理学家」——「程序员」这个职业当时还不算一个正当职业
  • 1968 年 Boys' Life 杂志（面向青少年的杂志）已经在畅想「终端可以即时判分」这件事

还有个关于「缺同理心」的观察：讲师说 985 的学生往往缺同理心与商业理解——技术上能做出很漂亮的东西，但不理解这个东西对真实用户、对商业意味着什么。这恰好是软件企业存在的理由。

讲师举了个很形象的对比来说明「补 gap 是有价值的」：开发一个操作系统可能要花 1000 万美元，而如果你去问 AI，「我给你微博 50」——意思是 AI 根本不能替代那个「把需求搞对、把资源组织起来」的过程。另外一个例子是软件与桥梁工程的差别：桥梁要适应自然物理规律，软件要适应的是人的需求，而人的需求是高度定制化的——选课系统要考虑先到先得、抽签、按专业保留名额，还要处理「先修课能不能特批」这种边界情况。

本章小结
  • gap 不在 AI 写代码那一段，而在 intent → specification 那一段
  • 所以今天的标准答案是 做 MVP：用最小的代价换到最关键的反馈，验证的对象是你的 intent
  • 讲师的真实项目证明这条路可行，但前提是选对抽象层——底层用几十年不变的接口，上层自定义语义
  • 「界面」这一层正在被模型吃掉，价值向接口层沉淀；中间件生意的成本结构被彻底改写
