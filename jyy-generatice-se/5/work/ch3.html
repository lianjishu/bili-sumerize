03

从软件危机到软件工程

39:01 – 75:06

这是全片最长、也最「补课」的一章。软件工程这门学科是被软件危机逼出来的，而危机不是「写不出代码」，是「进度、成本、质量一起失控」。讲师沿着 Dijkstra、NATO 会议、Margaret Hamilton、Winston Royce 四个坐标把这段历史讲透，最后一个反常识的结论：那张著名的瀑布模型图，出处是一篇批判瀑布模型的文章。

3.1进度、成本、质量一起失控

39:01

软件危机的定义不是「程序员水平不行」，而是三件事同时失控：进度拖、成本超、质量差。而且这三者是相互纠缠的——为了赶进度就砍测试，砍了测试质量就崩，质量崩了就返工，返工又拖进度。

危机现场的三个典型症状
  • 估算失效：没有人能说清楚这个系统要多久、要多少人、要花多少钱
  • 无法验证：做完了也不知道对不对，测试往往是最晚开始、最先被压缩的环节
  • 人不可替换：一个关键的人走了，这个系统就没人懂了——这在当时是常态

讲师强调：正是因为「写代码」这件事当时已经能做，但「把一个大系统按时按质做出来」做不到，才有了软件工程这门学科。

3.2GoTo Statement Considered Harmful

42:00

Dijkstra 那篇著名的短文标题是 「Go To Statement Considered Harmful」——注意原文里 Go To 是分开写的。它的核心论点不是「goto 这个指令有毒」，而是：goto 破坏了「程序状态可以被静态推理」这个前提。

讲师的暴论在这里出现了：程序员的水平随着 goto 密度的上升而下降。这句话当然是个玩笑式的夸张，但它抓住了一个真实的相关性——goto 用得越多，说明这个人越倾向于用「跳转」而不是「结构」来表达控制流。

但讲师紧接着就举了一个反例，而且是 Linux 内核里的：goto release 惯用法。

观察点

这里有一个重要的思维习惯：一个「最佳实践」被总结出来之后，往往会脱离它原本的语境，变成一个不能质疑的教条。讲师举 goto 的例子，就是在示范「读经典要读原文、要看它反对的具体是什么」。这个习惯在第 7 节讲 Royce 时会再来一次，而且那次更夸张。

3.3The Humble Programmer

48:00

1972 年，Dijkstra 获得图灵奖，按惯例要做一个图灵讲座。讲座的标题是 「The Humble Programmer」——谦卑的程序员。讲师挑了里面几个论点讲，每一个都跟今天高度相关。

The Humble Programmer 里的几个论点
  • Online Judge 不会有软件危机：因为题目是封闭的、边界是清晰的、验收是自动的。而真实软件没有这些性质
  • 机器越强，intent 就越多、不确定性就越多：能力边界外扩之后，人们会立刻提出更难的需求
  • 要写 nicely factored solutions：把问题拆成一个个小块的、可以独立理解的部分
  • 保守的力量来自教育机构与用户：教育机构习惯按老方式教，用户舍不得重写那些还能跑的旧程序——这两股力量在阻止进步

讲师对这条「保守力量」特别有感触：他既在教育机构里工作，也见过太多「这个系统还能跑就别动它」的决策。这两股力量加起来，会让软件世界里同时存在大量技术上早该被替换、但在组织上无法被替换的东西。

观察点

「Online Judge 不会有软件危机」这句话在今天的对应物就是：AI 在刷题与基准测试上表现极好，一进入真实项目就掉链子。原因是同一个——真实项目没有清晰的边界、没有自动验收、需求还在变。这条线索会一直连到软件工程存在的理由。

3.41968 年 NATO 软件工程会议

53:00

1968 年的 NATO 软件工程会议是「software engineering」这个词被正式提出的场合。讲师讲这个会议的方式很值得注意——他没有去讲会议达成了什么共识，而是讲了这个会议本身暴露的问题。

一个被反复提到的细节是：参加会议的人连「软件」这个词该叫什么都没统一。（会议记录里出现了 software、software engineering、programming 等多种叫法。）这说明这门学科在被命名的那一刻，连研究对象都还没界定清楚。

1968
NATO 会议，「software engineering」诞生。此时的动机很实际：军方的大型系统一再失败，需要把它当成工程来管
1970
Royce 发表《Managing the Development of Large Software Systems》——下一节的主角
1972
Dijkstra 的图灵讲座，给这门学科提供了一套哲学姿态（谦卑）
IEEE 定义
软件工程 = systematic, disciplined, quantifiable approach（系统的、有纪律的、可量化的方法）——三个词里最关键的是「可量化」

讲师顺带讲了一下软件工程的定义为什么必须包含「可量化」：因为不可量化的东西没法验收，没法验收的东西就没法管理。这正是软件危机的核心。

3.5Margaret Hamilton 与 Apollo

67:00

讲师放了那张著名的照片：Margaret Hamilton 站在打印出来的 Apollo 导航软件代码旁边，代码堆起来比她还高。1969 年，Apollo 11 成功登月，她负责的是导航与着陆软件。

讲师从这件事里挑了两个东西讲，都是软件工程的核心概念。

Apollo 软件留下的两个遗产
  1. 防御性编程：假设每一处都可能出错，代码里到处是检查。这个思想从 SICP 那本书开始就被系统讲授——而那本书的成书时间是 1980 年代，也就是说它把 60 年代的工程实践变成了教材
  2. 「The never going to happen can happen」：那些「绝对不可能发生」的情况，真的会发生。讲师说这句话是他理解软件工程的起点

最精彩的是那件真实事故的细节：Apollo 11 下降过程中，雷达数据把计算机的算力吃掉了，导致警报。软件没有崩溃，而是靠优先级机制与 recovery 逻辑把导航任务保了下来，让下降控制继续执行——最终阿姆斯特朗手动飞完了最后一段。如果没有那套优先级与恢复逻辑，这次着陆会直接中止。

3.6为什么必须把任务划开

61:00

讲师讲了一件他自己工作方式上的事：他同时开两个 agent，一个专门对付打印机，一个专门对付扫描仪。他说这不是因为效率，而是因为不划开就做不完。

为什么「划开」是硬要求
  • 任务不划开，你会一直在两个问题的上下文之间来回切换，每次切换都要重新加载状态
  • 更要紧的是：一个任务里混进两个目标，你连「它为什么失败」都判断不了——失败的是打印机那一半，还是扫描仪那一半？
  • 划开之后每个部分都有独立的验收标准，于是「做完了没有」这件事第一次变得可判断

讲师在这里把话题连到了软件工程最核心的操作：把一个大问题分解成若干个可以独立验证的小问题。这件事看起来基础，但它是所有方法论（瀑布、敏捷、TDD、MVP）的共同内核。

3.7Royce：瀑布图来自一篇批判瀑布的文章

68:00

这是全章最重要的一节。1970 年，Winston Royce 发表了《Managing the Development of Large Software Systems》。今天所有讲瀑布模型的书都会引用那几张图——需求 → 设计 → 编码 → 测试 → 维护，一级一级往下流。

但讲师强调：那篇文章实际上是批判瀑布模型的，它是软件工程史上被误读最严重的文章之一。

被误读的机制
  • Royce 在文章前半部分画出了那个大家都记得的「单向流动」图，然后明确指出这样做的致命问题
  • 文章后半部分他给出了自己的 Software Development Model——每一级都要能回到上一级，形成反馈回路
  • 但后人只引用了前半部分那张漂亮的图，把后半部分的批判整段丢掉了
  • 于是「瀑布模型」成了一种实践，而它的原作者是反对它的
观察点

讲师讲这件事的方式和第 2 节 goto 那一段完全一致：「一个被总结出来的最佳实践」与「它原本的语境」经常是相反的。这不是要在课堂上翻案，而是要训练一种阅读习惯——看到一张到处被引用的图，先去找它的出处上下文。

3.8Do it twice 与测试的第一个物理事件

73:00

Royce 文章里有两个概念被讲师单独拎了出来讲。

Do it twice
不要指望一次就做对。先做一版，扔掉，再做一版——因为只有做出第一版，你才真正知道自己要什么
Preliminary Pilot Program
Royce 提出要先做一个「试点的雏形程序」——这实际上就是今天的 MVP。也就是说 MVP 这个思想在 1970 年就已经写在论文里了
测试是链条上第一个物理事件
前面所有阶段（需求、设计、编码）都是在纸上发生的，只有测试是第一次让它真正跑起来、真正接触现实
风险在测试处爆炸
因为风险都被推迟到测试这一步才暴露，所以补救的本质不是「更努力地测试」，而是把发现问题的时间点提前

讲师用 TDD 与敏捷来反向解释 Do it twice：如果把「做两次」推到极限，就成了「做无数次」——也就是持续迭代。所以敏捷不是对 Royce 的否定，而是把 Do it twice 里那个「twice」放大了。

这一段最值得记住的一句话

「测试是链条上第一个物理事件」——这句话解释了为什么返工成本会随着阶段往后推进而急剧上升。因为前面每一级都只是「我认为它对」，只有测试是「它真的对不对」。所以工程上的所有努力，本质上都是在把「真的对不对」这个信息提早拿到。

3.9用 data dependency graph 解释返工成本

77:00

这一节讲师给了一个他自己很喜欢的模型：用 data dependency graph（数据依赖图）来解释返工成本。它的前提是一个很大胆的类比：把人当成程序，人和程序是等价的。

人做一件事也要 chain of thought，也要按依赖顺序推进；如果某个前置结论错了，后面所有基于它的工作都要作废——这跟程序里的数据依赖完全一样。

3.10阅读经典的启发价值

75:06

本章结尾，讲师回到「为什么要读这些老文章」。他的论证不是「经典所以好」，而是一个更实用的理由：

读经典的三个具体好处
  • 看到思想的原始形态：今天被简化成一句话的「最佳实践」，原文往往带着完整的条件与反例。读原文才不会把条件丢掉
  • 发现今天的问题早就被想过：返工成本、验收标准、需求的不确定性——这些问题在 1970 年就被讨论过了，只是每代人都在重新发现一次
  • 获得「不被一句话带走」的判断力：goto 与瀑布这两个例子都说明，脱离语境的结论会长期误导人
本章小结
  • 软件危机 = 进度、成本、质量一起失控，它逼出了「软件工程」这门学科（1968 NATO 会议）
  • Dijkstra 提供了哲学姿态（The Humble Programmer），Margaret Hamilton 提供了工程实践（防御性编程 + 优先级恢复）
  • Royce 提供了方法（Do it twice、Pilot Program = MVP），但那张最有名的瀑布图其实是他要批判的对象
  • 所有方法论的内核是同一件事：把「它到底对不对」这个信息尽早拿到——用依赖图来说，就是选择正确的遍历顺序
