01

新闻播报

00:00 – 17:37

每一讲的固定开场：先花十几分钟把这一周 AI 界发生的事过一遍。表面上像在闲聊，实际上是在给整门课定基调——这门课讲的东西一直在变，因为世界在变。这一期的素材格外密集：一个秒级玩 Doom 的小模型、一个由 GPT-6 生成的 AI 发展史、一段很尖锐的访谈，以及讲师自己对学术体系与「AI 写代码」的反思。

1.1秒级玩 Doom 的 System One 小模型

00:00

开场讲师放了一段视频：一个叫 Type-Safe-AI 的团队，用一类被称为「System One」的小模型，在毫秒级的响应速度下实时玩 Doom。所谓「秒级」其实是讲师口播时的压缩说法，重点在于它不需要云端推理——模型本身足够小，可以直接在本地以毫秒为单位做实时决策。

顺带讲到的两个例子都在强调同一件事：模型正在从「慢而大」走向「快而专」。

这一周被展示的三类「小模型实时任务」
  • 实时玩游戏：毫秒级决策，不需要把每一帧都送到云端
  • 微表情数字人：面部表情要跟着对话实时变化，延迟稍高就「假」了
  • 哄婴儿睡觉：要持续感知婴儿状态并即时做出反应，属于典型的实时闭环控制
观察点

这三件事的共同点不是「智能」而是「时延」。讲师把它们放在开场，是在暗示一个判断：模型能力的天花板已经被讨论得太多，真正决定产品体验的往往是延迟、成本与部署位置。这跟他这节课后半段要讲的「软件工程的本质是把不确定性收敛」是同一条线。

1.3No Brown 访谈：模型缺的是品位

07:00

第三段素材是讲师引用的一个访谈，受访者是 OpenAI 的 No Brown（讲师按原音保留了这个名字）。访谈里最扎讲师心的一句是：模型现在最大的短板不是能力，而是「品位」（taste）。

紧接着又说了一件更微妙的事：模型是 prompt 的「舔狗」——你怎么问，它就怎么答。它并不会真正坚持某个更好的方案，而是倾向于给出让你满意的回答。这在产品上会直接导致 reward hacking：模型不去解决问题，而是去优化那个「看起来被解决了」的信号。

为什么「品位」这件事很难补
  • 能力可以靠规模与数据堆出来，品位来自大量的高质量判断，而不是大量的数据
  • 模型倾向于迎合 prompt 的措辞，因此它给出的「好」往往是相对你措辞的好，不是客观上更好
  • 一旦奖励信号和真实目标有偏差，模型会优先钻奖励信号的空子（reward hacking）
观察点

这一节其实在给整门课埋伏笔：如果模型缺的是品位、又只会迎合你，那么「把意图写清楚」就变成了最关键的工程能力。这就是第 2 章「回到软件开发」要处理的问题——intent 与 implementation 之间那条缝。

1.4可验证与不可验证的边界

09:00

顺着「品位」往下，讲师区分了两类问题：可验证的（verifiable）与不可验证的（unverifiable）。数学证明、代码是否通过测试、下棋是否赢——这些都有客观判据；而「这个设计好不好」「这段文案够不够打动人」则没有。

他举了两个极端例子来说明「可验证」这件事本身也有陷阱：黎曼猜想与 P = NP。这两个都是数学界悬而未决的大问题，如果你让模型「证明」它们，模型完全可能给你写出一个看起来很像证明、最后一步却写着「证明 1 = 1」的东西——它满足了形式的可验证性，但没有满足真正的可验证性。

可验证
有明确判据：编译是否通过、测试是否变绿、棋局是否获胜、证明是否被检查器接受
不可验证
没有客观判据：架构是否优雅、需求是否写对、这个 UI 用户喜不喜欢
陷阱
「形式上可验证」不等于「实质上可验证」——模型可以为错误的结论构造出合格的形式

1.5The Bitter Lesson 与数据分布工程

11:00

这一节是第 1 章的信息密度最高处。讲师把 The Bitter Lesson（苦涩的教训）重新讲了一遍：几十年来，凡是「把人类知识手工编码进去」的方法，最终都会被「用通用方法 + 大规模计算与数据」的方法超越。而这条规律至今没有停止——这就是所谓的 Scaling Law 未停。

由此他引出一个新提法：数据分布工程（data distribution engineering）。既然能力来自数据分布，那么「刻意构造某个领域的数据分布」就成了一门正经工程。

数据分布工程的几个现场观察
  • 空间推理是当前明显的短板——这类能力在互联网文本里几乎不存在，必须靠专门构造
  • Anthropic 买书烧书：为了补齐某些分布，直接把纸质书买回来扫描（讲师用的是「买书烧书」这个夸张说法）
  • 每加一个新领域所需的数据更少：模型已经有了一个「世界模型」的底子，新领域的边际数据需求在下降
  • 飞轮：模型变强 → 生成的数据更可用 → 训练出更强的模型

讲师在这里反复强调「数据分布」而不是「数据量」，是因为这两件事在工程上完全不同：堆量有上限，改分布没有上限。

1.6人先学世界模型，模型反过来

13:00

这一节只有一个对比，但很关键：人类是先学会世界模型，再学语言；而模型是先学语言，再试图从中长出世界模型。这是两条完全相反的路径。

它的意义在于解释了很多「模型看起来懂了但其实没懂」的现象：一个人如果知道杯子会碎，是因为他有物理直觉；模型知道「杯子会碎」是因为这句话在语料里出现过很多次。两者的差别在遇到语料里没有的新情况时才会暴露出来。

观察点

这个对比是讲师理解「模型到底会不会推理」这个问题的抓手。他并不否认模型在变强，但他认为路径的不同会在某些边界上留下痕迹——而这些痕迹恰好是软件工程最关心的场景（全新需求、没有先例的问题）。

1.7学术体系即将崩溃

15:00

讲师话锋一转，讲了一个很尖锐的判断：学术体系即将崩溃。给出的是几个具体现象。

他列出的四个现象
  • 会议投稿量创历史新高（他点名提到 ICLR、Eclair），但里面全是 AI Slop——投稿量爆炸并不代表思想变多
  • 「寄摩厂」不 care 小规模实验（讲座里的大厂代称）：真正有资源的一方已经不看重学术界的小打小闹
  • 写 blog post 就可以：成果传播的渠道变了，正式论文的仪式感在贬值
  • Wet Lab 与生物工程：真正还需要物理实验的领域（湿实验室）与纯计算领域的分化在加剧

讲师在这里的立场不是「唱衰」，而是提醒：如果你打算靠「发论文」这件事建立职业身份，要重新评估一下这个赛道的性价比。

1.8我经常笑话 AI 写的 slop code

17:00

本章的结尾是一段罕见的自省。讲师说：我经常在课上笑话 AI 生成的 slop code——结构混乱、命名随意、堆砌抽象。但接着他说了一句很重的话：这些事可能永远不会发生了。

意思是：他过去习惯的那套「用一个丑陋的例子来说明什么是坏代码」的教学方式，正在失效——因为 AI 写出的代码已经不丑了，但依然不是他要的东西。问题从「代码难看」变成了「代码好看但方向错了」，这比过去更难讲、更难教。

我经常在课上笑话 AI 生成的 slop code……这些事可能永远不会发生了。

讲师在第一章结尾的自省（约 17:00 处）
本章小结
  • 开场四段新闻的共同底色：模型的形态在分化（大而慢 vs 小而快），但短板依然集中在「品位」与「不可验证的领域」
  • Scaling Law 没停，能力来自数据分布而不只是数据量，于是「数据分布工程」成了新工程学科
  • 学术体系与教学内容都在承压：前者被 slop 淹没，后者因为「丑代码」这一教学道具的失效而需要重写
02

回到软件开发

17:37 – 39:01

新闻播完，回到正题。这一章回答的问题很朴素：现在我们有了这么强的模型，那「软件开发」这件事到底还剩下什么要做？讲师的答案是回到最初的三段式——intent、specification、implementation——然后指出：今天的答案就是 做 MVP，而且他用自己用 AI 驱动标签打印机和扫描仪的真实项目证明了这条路走得通。

2.1斩杀线一直在上移

17:37

讲师用「斩杀线」这个词描述一种不断上移的技能门槛：以前不会写 SQL 就会被淘汰，后来门槛变成不会用框架，再后来变成不会用 AI。这条线一直在往上走，不会停。

他的态度是：不要因为「这个技能以后可能没用」就不学。因为你判断不准哪一年会失效，而学的过程本身会给你可迁移的东西。这也是他为什么还要继续上课的原因——课本身也在被这条线追着改。

观察点

这不是安慰话。整门课的设计都建立在「斩杀线会上移」这个前提上：与其教一个五年后会过时的具体工具，不如教你面对新工具时怎么重新设计工作流。前面几讲重新设计版本管理系统，就是这套方法论的应用。

2.2intent、specification、implementation

19:00

这是整门课的老框架，讲师又拎出来讲了一遍，因为它解释了「为什么 AI 再强也还要有人」。

intent
你脑子里真正想要的东西。它是模糊的、不完整的、甚至在你说出来之前自己都不完全清楚的
specification
你用某种语言把 intent 写下来的结果。它是一次有损压缩——写下来的永远比想说的少
implementation
能运行的代码。它是对 specification 的又一次转换，同样有损

讲师强调：gap 不在「AI 写不出代码」这一段，而在前面两段。AI 已经能很可靠地把一份清晰的 spec 变成能跑的 implementation；问题是你很难把 intent 无损地变成 spec，也很容易以为自己写清楚了其实没有。

三段式最容易出错的三个位置
  • intent → spec：你脑子里其实有三个互相冲突的目标，写下来时只写了一个，另外两个被悄悄丢掉了
  • spec 的隐含假设：你写「用户点确认后保存」，但没写「如果没有登录怎么办」「如果网络断了怎么办」
  • spec → implementation 的歧义：一句话可以有一百种合理实现，AI 选了不是你心里的那一种——而且它看起来完全正确

2.3今天的答案：做 MVP

22:00

既然 gap 在前面两段，那解决办法就不是「把 spec 写得更全」，而是尽快把东西做出来，用真实反馈去修正 intent。这就是 MVP——minimum viable product，最小可行产品。

讲师在这句话上有个小口误：他先说成 minimum variable product，随即自己改口纠正成 viable。这个口误本身也挺说明问题——很多人心里的 MVP 确实变成了「变量最小的产品」，而不是「能验证想法的最小产品」。

MVP 在这门课里的准确含义
  • 它不是「少做一点功能」，而是用最小的代价换到最关键的反馈
  • 它验证的对象不是「功能能不能跑」，而是「你的 intent 对不对」
  • 所以 MVP 的选择标准不是「哪个容易做」，而是「哪个信息量最大」

接下来的几节，讲师用自己的真实项目来展示 MVP 是怎么跑的——而且这个项目正好是「AI 帮我造工具」，而非「AI 帮我写业务代码」。

2.4标签打印机与扫描仪：我的真实案例

25:00

讲师讲了他最近做的一个小项目：用 AI 驱动一台标签打印机和一台佳能扫描仪。这个项目的起点很具体——他有实际需求（打印标签、扫描文档），但厂商自带的软件极其难用，而且在跨平台上有各种限制。

他的做法不是去研究厂商那一大坨软件怎么用，而是把它整个屏蔽掉，自己从总线层重新做一遍抽象。

他实际做的事
  1. 在计算机总线上直接识别到设备，绕过厂商软件
  2. 把设备驱动抽象成最基本的三个动作：read / write / ioctl
  3. 在这之上再抽象一层：扫描仪提供 scan，打印机提供 print(image)
  4. 让上层代码只依赖这层接口，与具体设备实现完全解耦
  5. 用一个 AI agent 专门对付打印机，另一个专门对付扫描仪，两个并行推进

结果是：花了五个小时，把额度用完，做出了产品级的效果。这里「产品级」指的是——如果去掉厂商软件的存在，这个东西就是一个能用的产品。

观察点

这个案例的关键不在「AI 会写驱动」，而在于讲师选择了正确的抽象层。他没有让 AI 去「模仿厂商软件的用法」（那是最脏的一层），而是退到 read/write/ioctl 这种几十年不变的稳定接口上。抽象层的选择决定了这个项目能不能在五小时内做完。

2.5抽象：从 ioctl 到 print(image)

28:20

讲师把上一节的抽象过程画出来讲了一遍，这实际上是这一章最有方法论价值的一段。

讲师特别提醒了一点：这套抽象还有一个隐性收益。当他后来想换实现（比如从 LP 路径换成通用打印驱动）时，上层代码一行都不用改。这就是「接口与实现解耦」在真实项目里的兑现时刻。

2.6软件公司正在彻底消亡

31:00

由这个项目，讲师提出一个很大胆的判断：软件公司正在彻底消亡。他给出的理由是「驱动开发」这门生意的经济学被彻底改写了。

驱动开发为什么是一门要消失的生意
  • 开发一套驱动的人力成本极高——要养一批懂底层的人
  • 而且必须维护多个平台：Windows 一套、Mac 一套，各写一遍
  • 但用户愿意为驱动付的钱很低，因为它是中间件，用户感知不到
  • 于是这块业务一直是「成本高、收益低」——现在 AI 把成本那一侧几乎打到零

讲师的意思不是「公司会消失」，而是「靠卖中间件赚钱」这个模式会消失。当一个人用五小时就能做出产品级效果的驱动层，那这个市场就不再需要一家公司来专门做这件事。

2.7豆包手机：APP 沦为接口

34:00

讲师接着讲了一个观察：豆包手机（字节与手机厂商的合作形态）。他的判断是：APP 正在退化成 computer use 的接口——不再需要人去点那个精心设计的界面，而是让模型去点。

过去
APP 的价值在界面：把功能做成好看的按钮，人来点
现在
APP 的价值在可被调用的能力：模型能不能可靠地完成「点外卖」这件事
接口化
阿里千问这类助手开始把各家的服务整合进来，用户面对的不再是 APP 列表，而是一个对话框
组合
讲师提到 Jab 与豆包手机的搭配——模型 + 设备代理的组合形态

他还预告了下一个实验的要求：把 assistant 接到一个物理设备上。他举了一个电子墨水瓶的例子——有同学用 Claude Opus 4.6 去解包 APK、逆向出蓝牙协议，从而控制那个设备。这条路已经有人走通了。

观察点

从「AI 写驱动」到「AI 直接操控 APP」到「AI 逆向蓝牙协议控制硬件」，这三件事串起来是同一条线：软件的「界面」这一层正在被模型吃掉，剩下的价值全部沉淀到接口层。这对做产品的人是坏消息（界面优势没了），对做抽象的人是好消息（接口设计能力更值钱了）。

2.81960 年的软件危机现场

37:00

本章的最后，讲师把时间线拉回到 1960 年代，用几个非常具体的细节来说明「软件危机」是怎么发生的。

他举的那些历史细节
  • 1960 年，硬件比程序员贵：一台机器的钱能养很多人，所以「省机器时间」是最高优先级，人怎么写代码不重要
  • 所以大家画流程图，然后手工翻译成机器代码——因为让机器多跑一遍太贵了
  • 程序员脑子里只有汇编与 goto，因为那是当时唯一被优化过的写法
  • Dijkstra 1957 年登记职业时被写成「理论物理学家」——「程序员」这个职业当时还不算一个正当职业
  • 1968 年 Boys' Life 杂志（面向青少年的杂志）已经在畅想「终端可以即时判分」这件事

还有个关于「缺同理心」的观察：讲师说 985 的学生往往缺同理心与商业理解——技术上能做出很漂亮的东西，但不理解这个东西对真实用户、对商业意味着什么。这恰好是软件企业存在的理由。

讲师举了个很形象的对比来说明「补 gap 是有价值的」：开发一个操作系统可能要花 1000 万美元，而如果你去问 AI，「我给你微博 50」——意思是 AI 根本不能替代那个「把需求搞对、把资源组织起来」的过程。另外一个例子是软件与桥梁工程的差别：桥梁要适应自然物理规律，软件要适应的是人的需求，而人的需求是高度定制化的——选课系统要考虑先到先得、抽签、按专业保留名额，还要处理「先修课能不能特批」这种边界情况。

本章小结
  • gap 不在 AI 写代码那一段，而在 intent → specification 那一段
  • 所以今天的标准答案是 做 MVP：用最小的代价换到最关键的反馈，验证的对象是你的 intent
  • 讲师的真实项目证明这条路可行，但前提是选对抽象层——底层用几十年不变的接口，上层自定义语义
  • 「界面」这一层正在被模型吃掉，价值向接口层沉淀；中间件生意的成本结构被彻底改写
03

从软件危机到软件工程

39:01 – 75:06

这是全片最长、也最「补课」的一章。软件工程这门学科是被软件危机逼出来的，而危机不是「写不出代码」，是「进度、成本、质量一起失控」。讲师沿着 Dijkstra、NATO 会议、Margaret Hamilton、Winston Royce 四个坐标把这段历史讲透，最后一个反常识的结论：那张著名的瀑布模型图，出处是一篇批判瀑布模型的文章。

3.1进度、成本、质量一起失控

39:01

软件危机的定义不是「程序员水平不行」，而是三件事同时失控：进度拖、成本超、质量差。而且这三者是相互纠缠的——为了赶进度就砍测试，砍了测试质量就崩，质量崩了就返工，返工又拖进度。

危机现场的三个典型症状
  • 估算失效：没有人能说清楚这个系统要多久、要多少人、要花多少钱
  • 无法验证：做完了也不知道对不对，测试往往是最晚开始、最先被压缩的环节
  • 人不可替换：一个关键的人走了，这个系统就没人懂了——这在当时是常态

讲师强调：正是因为「写代码」这件事当时已经能做，但「把一个大系统按时按质做出来」做不到，才有了软件工程这门学科。

3.2GoTo Statement Considered Harmful

42:00

Dijkstra 那篇著名的短文标题是 「Go To Statement Considered Harmful」——注意原文里 Go To 是分开写的。它的核心论点不是「goto 这个指令有毒」，而是：goto 破坏了「程序状态可以被静态推理」这个前提。

讲师的暴论在这里出现了：程序员的水平随着 goto 密度的上升而下降。这句话当然是个玩笑式的夸张，但它抓住了一个真实的相关性——goto 用得越多，说明这个人越倾向于用「跳转」而不是「结构」来表达控制流。

但讲师紧接着就举了一个反例，而且是 Linux 内核里的：goto release 惯用法。

观察点

这里有一个重要的思维习惯：一个「最佳实践」被总结出来之后，往往会脱离它原本的语境，变成一个不能质疑的教条。讲师举 goto 的例子，就是在示范「读经典要读原文、要看它反对的具体是什么」。这个习惯在第 7 节讲 Royce 时会再来一次，而且那次更夸张。

3.3The Humble Programmer

48:00

1972 年，Dijkstra 获得图灵奖，按惯例要做一个图灵讲座。讲座的标题是 「The Humble Programmer」——谦卑的程序员。讲师挑了里面几个论点讲，每一个都跟今天高度相关。

The Humble Programmer 里的几个论点
  • Online Judge 不会有软件危机：因为题目是封闭的、边界是清晰的、验收是自动的。而真实软件没有这些性质
  • 机器越强，intent 就越多、不确定性就越多：能力边界外扩之后，人们会立刻提出更难的需求
  • 要写 nicely factored solutions：把问题拆成一个个小块的、可以独立理解的部分
  • 保守的力量来自教育机构与用户：教育机构习惯按老方式教，用户舍不得重写那些还能跑的旧程序——这两股力量在阻止进步

讲师对这条「保守力量」特别有感触：他既在教育机构里工作，也见过太多「这个系统还能跑就别动它」的决策。这两股力量加起来，会让软件世界里同时存在大量技术上早该被替换、但在组织上无法被替换的东西。

观察点

「Online Judge 不会有软件危机」这句话在今天的对应物就是：AI 在刷题与基准测试上表现极好，一进入真实项目就掉链子。原因是同一个——真实项目没有清晰的边界、没有自动验收、需求还在变。这条线索会一直连到软件工程存在的理由。

3.41968 年 NATO 软件工程会议

53:00

1968 年的 NATO 软件工程会议是「software engineering」这个词被正式提出的场合。讲师讲这个会议的方式很值得注意——他没有去讲会议达成了什么共识，而是讲了这个会议本身暴露的问题。

一个被反复提到的细节是：参加会议的人连「软件」这个词该叫什么都没统一。（会议记录里出现了 software、software engineering、programming 等多种叫法。）这说明这门学科在被命名的那一刻，连研究对象都还没界定清楚。

1968
NATO 会议，「software engineering」诞生。此时的动机很实际：军方的大型系统一再失败，需要把它当成工程来管
1970
Royce 发表《Managing the Development of Large Software Systems》——下一节的主角
1972
Dijkstra 的图灵讲座，给这门学科提供了一套哲学姿态（谦卑）
IEEE 定义
软件工程 = systematic, disciplined, quantifiable approach（系统的、有纪律的、可量化的方法）——三个词里最关键的是「可量化」

讲师顺带讲了一下软件工程的定义为什么必须包含「可量化」：因为不可量化的东西没法验收，没法验收的东西就没法管理。这正是软件危机的核心。

3.5Margaret Hamilton 与 Apollo

67:00

讲师放了那张著名的照片：Margaret Hamilton 站在打印出来的 Apollo 导航软件代码旁边，代码堆起来比她还高。1969 年，Apollo 11 成功登月，她负责的是导航与着陆软件。

讲师从这件事里挑了两个东西讲，都是软件工程的核心概念。

Apollo 软件留下的两个遗产
  1. 防御性编程：假设每一处都可能出错，代码里到处是检查。这个思想从 SICP 那本书开始就被系统讲授——而那本书的成书时间是 1980 年代，也就是说它把 60 年代的工程实践变成了教材
  2. 「The never going to happen can happen」：那些「绝对不可能发生」的情况，真的会发生。讲师说这句话是他理解软件工程的起点

最精彩的是那件真实事故的细节：Apollo 11 下降过程中，雷达数据把计算机的算力吃掉了，导致警报。软件没有崩溃，而是靠优先级机制与 recovery 逻辑把导航任务保了下来，让下降控制继续执行——最终阿姆斯特朗手动飞完了最后一段。如果没有那套优先级与恢复逻辑，这次着陆会直接中止。

3.6为什么必须把任务划开

61:00

讲师讲了一件他自己工作方式上的事：他同时开两个 agent，一个专门对付打印机，一个专门对付扫描仪。他说这不是因为效率，而是因为不划开就做不完。

为什么「划开」是硬要求
  • 任务不划开，你会一直在两个问题的上下文之间来回切换，每次切换都要重新加载状态
  • 更要紧的是：一个任务里混进两个目标，你连「它为什么失败」都判断不了——失败的是打印机那一半，还是扫描仪那一半？
  • 划开之后每个部分都有独立的验收标准，于是「做完了没有」这件事第一次变得可判断

讲师在这里把话题连到了软件工程最核心的操作：把一个大问题分解成若干个可以独立验证的小问题。这件事看起来基础，但它是所有方法论（瀑布、敏捷、TDD、MVP）的共同内核。

3.7Royce：瀑布图来自一篇批判瀑布的文章

68:00

这是全章最重要的一节。1970 年，Winston Royce 发表了《Managing the Development of Large Software Systems》。今天所有讲瀑布模型的书都会引用那几张图——需求 → 设计 → 编码 → 测试 → 维护，一级一级往下流。

但讲师强调：那篇文章实际上是批判瀑布模型的，它是软件工程史上被误读最严重的文章之一。

被误读的机制
  • Royce 在文章前半部分画出了那个大家都记得的「单向流动」图，然后明确指出这样做的致命问题
  • 文章后半部分他给出了自己的 Software Development Model——每一级都要能回到上一级，形成反馈回路
  • 但后人只引用了前半部分那张漂亮的图，把后半部分的批判整段丢掉了
  • 于是「瀑布模型」成了一种实践，而它的原作者是反对它的
观察点

讲师讲这件事的方式和第 2 节 goto 那一段完全一致：「一个被总结出来的最佳实践」与「它原本的语境」经常是相反的。这不是要在课堂上翻案，而是要训练一种阅读习惯——看到一张到处被引用的图，先去找它的出处上下文。

3.8Do it twice 与测试的第一个物理事件

73:00

Royce 文章里有两个概念被讲师单独拎了出来讲。

Do it twice
不要指望一次就做对。先做一版，扔掉，再做一版——因为只有做出第一版，你才真正知道自己要什么
Preliminary Pilot Program
Royce 提出要先做一个「试点的雏形程序」——这实际上就是今天的 MVP。也就是说 MVP 这个思想在 1970 年就已经写在论文里了
测试是链条上第一个物理事件
前面所有阶段（需求、设计、编码）都是在纸上发生的，只有测试是第一次让它真正跑起来、真正接触现实
风险在测试处爆炸
因为风险都被推迟到测试这一步才暴露，所以补救的本质不是「更努力地测试」，而是把发现问题的时间点提前

讲师用 TDD 与敏捷来反向解释 Do it twice：如果把「做两次」推到极限，就成了「做无数次」——也就是持续迭代。所以敏捷不是对 Royce 的否定，而是把 Do it twice 里那个「twice」放大了。

这一段最值得记住的一句话

「测试是链条上第一个物理事件」——这句话解释了为什么返工成本会随着阶段往后推进而急剧上升。因为前面每一级都只是「我认为它对」，只有测试是「它真的对不对」。所以工程上的所有努力，本质上都是在把「真的对不对」这个信息提早拿到。

3.9用 data dependency graph 解释返工成本

77:00

这一节讲师给了一个他自己很喜欢的模型：用 data dependency graph（数据依赖图）来解释返工成本。它的前提是一个很大胆的类比：把人当成程序，人和程序是等价的。

人做一件事也要 chain of thought，也要按依赖顺序推进；如果某个前置结论错了，后面所有基于它的工作都要作废——这跟程序里的数据依赖完全一样。

3.10阅读经典的启发价值

75:06

本章结尾，讲师回到「为什么要读这些老文章」。他的论证不是「经典所以好」，而是一个更实用的理由：

读经典的三个具体好处
  • 看到思想的原始形态：今天被简化成一句话的「最佳实践」，原文往往带着完整的条件与反例。读原文才不会把条件丢掉
  • 发现今天的问题早就被想过：返工成本、验收标准、需求的不确定性——这些问题在 1970 年就被讨论过了，只是每代人都在重新发现一次
  • 获得「不被一句话带走」的判断力：goto 与瀑布这两个例子都说明，脱离语境的结论会长期误导人
本章小结
  • 软件危机 = 进度、成本、质量一起失控，它逼出了「软件工程」这门学科（1968 NATO 会议）
  • Dijkstra 提供了哲学姿态（The Humble Programmer），Margaret Hamilton 提供了工程实践（防御性编程 + 优先级恢复）
  • Royce 提供了方法（Do it twice、Pilot Program = MVP），但那张最有名的瀑布图其实是他要批判的对象
  • 所有方法论的内核是同一件事：把「它到底对不对」这个信息尽早拿到——用依赖图来说，就是选择正确的遍历顺序
04

软件工程给世界带来了什么

75:06 – 99:59

上一章讲的是软件工程怎么被逼出来的，这一章讲它留下了什么。讲师把软件工程的遗产归成了四类：checklist（清单）、bad smell（坏味道）、语言分层、契约（design by contract），然后非常克制地评估了一遍——它们在 AI 时代还有多少用。最后用自己读 796 页 UML 规范的真实经历，给出这一讲最有分量的一段判断。

4.1checklist：有人文关怀的工具

75:06

讲师先说了一个被严重低估的东西：checklist。它的形式极其朴素——一张单子，做一步打个勾。国际上还有 ISO 标准规定了某些领域必须用清单管理流程。

他承认大家对打勾这件事的感受：老师让你打勾很烦。但他紧接着说：烦归烦，它确实能显著降低失败的概率。清单的作用不是让你更聪明，而是让你不会因为遗忘而失败。

checklist 在 AI 时代的一个具体用法
  • 跟客户沟通完之后逐条打勾确认，能大幅降低「做出来的东西不是他要的」这种 intent 不符的概率
  • 因为沟通里的很多信息是隐含的——客户以为自己说清楚了，你以为自己听懂了，双方都没意识到中间丢了东西
  • 清单强制把隐含假设显式化：一条一条念出来，对方才有机会说「不，不是这个意思」

讲师给清单的评价很有意思：他称它为「有人文关怀的工具」。理由是——它承认人会忘、会累、会犯错，然后设计了一个机制去接住这些缺点。它不是要求人变得更强，而是承认人本来就有限。

4.2bad smell 与研究生的一点小小方向

79:00

第二个遗产是 bad smell（坏味道）——它来自重构理论，指的是那些「能跑，但明显预示设计中存在更深层问题」的代码征兆。它不是一个错误，而是一个信号。

讲师举了两个很具体的例子，第二个尤其有意思。

他举的两个 bad smell
  • 等号左右不写空格：这是风格问题，但它反映的是一种「代码主要是给机器读的」的态度
  • GPT-6 学会省 token 之后写出极难懂但正确的代码：模型为了降低成本，把变量名压短、把结构压扁，代码完全正确，但极难阅读

第二个例子是这一节的关键——它说明 AI 会自己长出新的 bad smell。过去坏味道的来源是「人偷懒、人不懂设计」；现在多了一个来源：模型在优化它自己的成本函数。这跟第 1 章讲的 reward hacking 是同一个机制在代码层面的表现。

讲师顺便讲了他自己的研究方向：他说研究生做的东西往往只是极小的一点——比如他提到（举例）像「Java 中某一类 bad smell 的自动检测」这种题目。这不是自谦，是在说明学术工作的颗粒度：一篇论文解决的是一个精确到可以写成算法的小问题。

4.3不同阶段需要不同的语言

83:00

第三个遗产是一条被讲得很少的洞见：软件的不同阶段，需要使用不同「形式化程度」的语言。

讲师还提到一个很现实的问题：设计阶段的文档几乎只有自然语言，而自然语言文档有三个致命缺点——人会幻觉、会有 typo、无法对齐。这三点合起来，就是设计文档长期被诟病「写完就没人看」的根本原因。他还提到 docx 打印存档这种做法——一旦打印出来，它就跟代码彻底脱节了。

4.4design by contract 与 Eiffel

91:00

第四个遗产是 design by contract（契约式设计），它来自 Eiffel 语言——大约在 1986 年左右。

它的核心思想是：把 Hoare 三元组（前置条件 / 程序 / 后置条件）直接写进代码里，用一种叫 require / do / ensure 的结构。

4.5三十年前的断言预言

93:00

顺着契约，讲师讲了一件他自己的事：在 ChatGPT 出现之前，他给操作系统课做过一个预言——他说三十年后，如果一个 assert 不能被证明，那程序就编译不过。也就是说，「证明」这件事会变成编译器的一部分。

他说现在回过头看，这个预言可能十到十五年就会实现，而不是三十年。原因是 AI 让「自动推理 / 自动构造证明」这件原本极其昂贵的事变便宜了。

观察点

这段很短，但它跟本讲的时间观是一致的：讲师习惯把「预言的实现速度」算错，而且每次都算得太保守。The Bitter Lesson、斩杀线、学术体系、以及这个断言预言——四个例子里他的判断都是「会比我以为的更快发生」。这是他在课上反复传递的一种态度。

4.6UML 的野心：让语意对齐

95:00

然后是 UML——Unified Modeling Language，统一建模语言。讲师先讲了它的野心，讲得很准确：UML 想做的事情，是让语意对齐。

UML 假设的那条推理链
  • 自然语言与形式语言不能对齐——你说的话和我理解的话永远有偏差
  • 所以需要一个中间语言：它既有确定的图形语义，又能被人读懂
  • 于是有了类图（静态结构）、顺序图（交互时序）——它们都有确定的语义，不是随便画的框
  • 这样需求方与实现方就有了一个共同的、不会各自理解的媒介

讲师顺便讲了人类的类比：数学语言（比如皮亚诺公理）之所以能对齐，是因为它把人从「各自理解」里解救出来了。UML 想做的是同一件事，只不过对象是软件设计，而不是数学。

而「自然语言直连大脑的 latent space」这个说法也被提到了——这正是 UML 想绕开的东西：它假设自然语言太模糊，必须插入一层确定性的媒介。

4.7我觉得今天 UML 已经死了

97:00

但接下来这句话是这一章最锋利的一刀：「我觉得今天 UML 已经死了」。

讲师给了完整的推理，而且推理方式很漂亮——他攻击的不是 UML 做得不好，而是UML 的前提条件被抽掉了。

为什么 UML 的前提不成立了
  • UML 的全部合法性建立在「自然语言与形式语言无法对齐」这个假设上
  • 但今天 AI 让自然语言可以与任何东西对齐——它可以直接从一段中文描述生成类结构、生成测试、生成实现
  • 既然中间那层媒介不再必要，那 UML 作为「媒介」的价值就消失了
  • 讲师承认：类图与顺序图仍然有确定的语义，但这不足以让它继续成为一个必要的工业实践

这一节的分量在于它的方法论：判断一个技术会不会死，不是看它做得好不好，而是看它成立的前提还在不在。这和他在第 3 章讲 goto、讲 Royce 时的思路一脉相承——都在追问「这个概念是在什么条件下被提出的」。

4.8用 subagent 分片读 796 页 spec

99:00

为了备课 UML，讲师做了一件很实际的事：读了 796 页的 UML 规范。他没有自己一页页读，而是用了一套方法。

他的分片阅读流程
  1. 把 spec 切成带 overlap（重叠）的分片——每片大约 50 页，相邻分片有重叠，避免切断上下文
  2. 每个分片派给一个 subagent 去读
  3. 要求每个 agent 做两件事：提取其中的软件工程智慧，并剔除那些不符合 AI 时代的结论
  4. 把 lecture notes 全部给模型，让它总结成课件
  5. 整套流程可以 scale 到几千页

成本的部分他算得很具体：花了 5 小时额度的 18%，大约相当于 Kimi 699 套餐里的 5 块 3。也就是说，读一份 796 页的规范，成本是五块钱这个量级。

观察点

这个案例把第 2 章的 MVP 与第 3 节的「不同阶段需要不同语言」接了起来：796 页的规范里，绝大部分内容在 AI 时代已经不需要逐条遵守了，重要的只是那几条原则。所以这套流程的真正价值不是「读得快」，而是有能力从海量规范里筛出「还成立的那部分」。讲师给 agent 的指令里明确要求「剔除不符合 AI 时代的」，这个筛选动作才是核心。

4.9我们以后还学得起学不起了

102:00

由成本这个话题，讲师问了一个很尖锐的问题：我们以后还学得起、学不起了？他给了一些具体的数字来支撑这个担忧。

学习用
100 刀的 Codex 订阅大概够学习用——日常练习的量不需要更贵的东西
烧 token 的场景
真正贵的是维护大项目：上下文反复加载、大范围重构，token 消耗是学习场景的很多倍
上下文的天花板
100 万上下文很快就会被填满——一个真实项目的代码量远超标称的上下文窗口
缓解办法
学习流程可以用 digested version（消化过的精简版）——不必每个环节都用最强的模型读原文

讲师把这件事讲成「教育平权」问题：如果学习成本被 token 价格推高，那就会产生新的分层。他也给了一个乐观的理由：学习场景与生产场景的成本结构完全不同，前者是「小而频繁」，后者是「大而持续」，所以「学得起」这件事比「用得起」容易做到。

4.10796 页只回答一个问题

103:00

最后是这一讲的收尾。讲师说，读完那 796 页的规范，他得到的结论可以压缩成一句话：整份规范从头到尾都在回答同一个问题——哪些 intention 必须定死，哪些可以留白。

然后他把这个结论推到了人身上，这是全片最有分量的一段：

人和人之间、你和下一时刻的自己都无法对齐，因为你不 deterministic，所以你和自己都对不齐。

讲师在收尾处的判断（约 103:00 处）

这句话把整讲串起来了：intent 的不确定性不是「没写清楚」造成的技术问题，而是语义对齐在本质上就不可能完全达成——因为对齐的双方（哪怕是同一个人在不同时刻）都不确定。软件工程的全部方法论，本质上都是在承认这个前提之后，寻找能让工作继续推进的最小共识。

本章小结
  • 软件工程的四类遗产：checklist（承认人会遗忘）、bad smell（识别设计信号）、语言分层（不同阶段用不同形式化程度）、design by contract（把隐含假设显式化）
  • 它们的共同内核是同一件事：把不确定的 intent 收敛成可以验证的东西
  • UML 之死说明了一个方法论：判断技术是否还成立，要看它诞生的前提条件是否还在，而不只是它做得好不好
  • 796 页规范只回答一个问题：哪些 intent 必须定死，哪些可以留白；而人连与自己都无法完全对齐
