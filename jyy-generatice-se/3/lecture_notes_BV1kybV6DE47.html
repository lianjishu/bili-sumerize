CHAPTER 01

开场 & 版本管理

00:00 – 24:40 · 8 节

1.1开头：一次 GPT-6 的现场演示 00:00

课程从新模型的进展讲起：GPT-6 真的发布了，大家用上了，讲师的总体评价是「还是有惊喜的」——各方面能力都提升，做更复杂的任务时变得更快、省很多 token（他特意 measure 过）。但具体到软件工程，他认为编程上的提升有限：模型还没有学会那种「好的品位」，还经常需要人来骂、来指导。

讲师原话 「品位可以指导 AI 做出更好的东西，现在 AI 更多的时候是完成任务，好像 GPT-6 还没有学会这种非常好的品位……所以我觉得我可能还能再苟活个几个月。」

另一个值得记录的现象：面对「做一个国民级的应用」这类开放任务，哪怕是顶级产品经理，每个人脑袋里想的东西都不一样——AI 没办法和人脑直接对齐，它总会按照自己的方式去漂移（drift）。这延续了上一讲的 intent → spec → implementation 框架：intent 与 spec 之间的空间越开放，漂移就越明显。

本节要点

  • GPT-6 能力全面提升、更快更省 token，但「品位」仍需人提供。
  • 开放 intent 下 AI 必然漂移：它无法与人脑直接对齐。

1.2代码正在变得不需要人读 01:53

讲师观察到一个趋势：AI 写出来的代码，人类越来越难读了。从 GPT-5 到 5.6 再到 6，代码写得越来越紧凑——可能受思维链变短的影响，模型写的代码也非常紧凑，人已经没有办法 review 那个代码。曾经大家会用各种 prompt 要求 AI 写「符合人类工程规范的代码」，现在的态度变成了：「我们再也不会看 AI 写的代码了，所以随它去吧，它反正能把代码弄对。」

这个判断直接改变了本讲的问题设定：既然代码不再给人读，那么真正需要人管理的是什么？答案就是本讲的主题——软件仓库与版本管理。

本节要点

  • 模型迭代：代码越来越紧凑，人类 review 逐步退出。
  • 代码可读性弱化之后，版本管理与过程管理成为人的核心工作。

1.3AI 时代还要不要学数据库和操作系统 06:54

有人问讲师：AI 时代还要不要学数据库、操作系统？他的答案「其实也不是特别的确定」，但给了一个非常干净的比喻：

课堂案例 · 汽车与司机 一百多年前汽车刚发明的时候，开一两公里就会出故障，所以每一个司机（driver）都必须对汽车的工作原理了解得非常清楚。今天我们在地下车库直接说「帮我开到什么地方」，自动驾驶汽车就出发了——中间经历的所有东西你都不需要知道，你就可以把汽车开起来。人工智能也是类似的东西，只不过它替代的不只是人的腿，还有人的智力。

所以「要不要学」不是一个能一锤定音的问题，但他给出的当下结论是明确的：要学。因为学了以后，你可以更好地解锁 AI 的创造力——理解了正确的概念，就能从别的地方借鉴知识，去创造更好的东西。而「以后应该怎么学」，他自己也承认暂时不知道，欢迎同学们来探讨。

本节要点

  • 汽车比喻：工具成熟度决定了「懂原理」是不是必需品。
  • 当下的答案：概念仍然要学，它是解锁 AI 创造力的杠杆。

1.4惊人的注意力 17:04

这一节是讲师每节课几乎都要讲的方法论：当学习变容易了以后，这门课上讲的知识都不重要，重要的是学习意识。你们看过很多 Git 项目——有没有留意过不同项目之间细微的区别？有的项目有这个文件、有的没有；有的文档这样写、有的那样写。信号看得多了，你自然就能判断出「应该怎么用 Git」。

他批评了一种「中学心态」：中学时老师说的话太多，你必须完全听话才能把事情做完。但到了 GitHub 上学习，如果还带着这种心态，老师说「把作业拉下来」你就只做这一件事，「你就有点像 AI」——被强化学习成了老师让干什么就只干什么、绝不多碰一点点的状态。

对照实验就在眼前：今天满世界的 GitHub 项目都是巨长无比的 README，里面是用 unicode 字符拼的目录结构和框图，一股 AI slop 的感觉。而一个十几年前开始维护的老项目，README 很短、文档清新舒服，看完想看的东西三个链接就走过去了。你不需要看那么长的 slop，你就学会了文档应该这样写。

概念卡 · 讲师的自查法 看到任何东西之前，先把眼前的东西全部忽略掉，想「如果我要自己来解决这个问题，我会怎么做」；然后立即比较：我做的和他做的，谁更好？如果我做得更好，就认为这是一个 slop；如果发现他做得比我好，就很惊喜地追问「他为什么做得比我好」。这是个「非常恐怖的习惯」——你在任何时候都在疯狂地从外面接受信息，留意到生活中的小细节，就不停地在提升。

本节要点

  • 知识会过时，学习意识不会；对比不同项目的细微差别就是学习。
  • 警惕「中学心态」：被动执行指令 = 把自己活成被 RL 调好的 AI。
  • slop 与好设计的分辨力，来自「先自己想一遍再比较」的习惯。

1.5第一个博士生的 U 盘事故 13:45

开始做软件工程、开始 vibe coding，干的第一件事是什么？建一个目录，起个名字——比如「我的最酷的 GaoGame」——然后开始 webcoding。但什么才算一个软件工程项目？目录里有一堆文件，共同构成一个可交付的东西，最后变成你的产品。

这里有一个著名的笑话：「GPT-6 太牛逼了，我又做了多少个 killer 级的产品——它们是 localhost:5137 上的。」你本机可以打开它，但世界上的其他人打不开它。这暴露的是知识：agent 默认把你的 intent 当成开发者的 intent——先起一个本地 development server 调试，直到你觉得 ready 才送到远端。如果你在 intent 里写明「这个东西要被全世界看到」，它就会做对。

软件是什么？标准定义是「代码、文档等等一切和软件相关的东西的集合」。讲师的说法更透：软件是人类世界的需求在信息世界里的投影，这个投影今天看到是一个目录，目录里面有各种各样的东西。

然后是本节的标题故事。讲师的第一个博士生（2012 年入学）大一时常去机房——那时笔记本屏幕小，去机房就得来回拷贝代码。他想出的妙招是把代码保存到 U 盘上；结果到大二，U 盘坏了，代码全部没有了，启蒙阶段的作业也不见了。我们很长时间都是这样管理代码的：讲师上学时交作业的方式是打一个压缩包发邮件，现在你们是在网页上上传。

而软件工程在今天是有标准答案的：用 Git。它除了保存目录（代码、binary、文档），还能保留、比较和恢复历史的版本。有了 Git，作业可以用 git clone 从远端获取、更新了用 git pull 下载；讲师课程的 make submit 会自动打包上传到课程网站，「有点像一个 CI」——现代 CI/CD 的流程，后面会专门有一节课讲。

本节要点

  • 项目 = 目录 + 可交付物；localhost 笑话说明 intent 必须说清「给谁用」。
  • 软件 = 人类需求在信息世界里的投影。
  • U 盘 / 压缩包邮件 → Git：版本管理是项目管理的标准答案。

1.6我要的是对世界的感知能力 02:36

GPT-6 给讲师最大的惊喜，是它的空间感知和理解能力。他一直认为 OpenAI 对 AGI 的理解路线是：先把数学学会——因为数学是人类世界里最难的语言，有一个全球所有人都认同的推理系统（一个定理证明出来，全球的人都会认为它对或不对），是很好的 grounding；而且数学的逻辑推理可以解释人类生活里的各种行为——比如「中午吃什么」看起来要灵魂给出答案，其实你的大脑里不停在各种因素之间投票：「我在那边订饭，因为它最快，我下午还要开会；时间来得及还可以小睡一会儿」——这里面「如果做了 A 就会做 B」，就是离散数学里的命题逻辑。

数学学完之后再去强化学习别的能力，比如空间感知：给你一个鲁班锁那样复杂的结构，问你按什么方向可以把第一块抽出来；或者给你一个六面骰子，问哪个展开图对应它——这类题目只要从简单任务开始强化学习，肯定是能做到的。

课堂案例 · 心疼我的 PhD 讲师的组里已经做了小半年的 3D 打印工作：在 GPT-5.6 空间感知很差的情况下，通过直接对话生成还很像样、符合规范的 3D 打印模型，还有比较 killer 的应用——比如「光栅尺」玩具（从左边看和右边看是两个不同图案）。结果 GPT-6 发布后第二天 one shot 直接搞定。「我当时看到这个例子，我就心疼我的 PhD。」同一天，很多人在小红书上发：直接用 GPT-6 控制机械臂做抓取、叠衣服这样的复杂动作——注意 GPT-6 是一个语言模型，它一帧一帧地问「下面要干什么」，还没解锁提示词工程就已经达到了 state-of-the-art。

结论：模型一定会进步，「也许在我上到某一次课的时候，我突然就可以说这个课不用上了，这样也好，大家就可以去做产品了」。但到今天，我们仍然需要学习软件工程的知识——因为 AI 解锁的是你的执行力。

本节要点

  • OpenAI 的路线：先训数学（全球共识的推理系统），再 RL 出空间感知等能力。
  • 3D 打印与机械臂案例说明：多模态执行力正在快速逼近可用。

1.7香港与南京的地铁标识 19:30

一个真实观察：在香港找路的时候，每当有不确定性——比如前面有三个口——正前方一定有一个路牌告诉你三个口分别是什么，「从来没有过」例外；香港还有一个非常复杂的地下系统。回到南京，你经常要在地铁站里环顾四周寻找「下一步到哪一个口」，甚至要走比较远的距离找到一个地图再看。

这个对比让讲师学到一个 lesson：如果他要做一个 UI 设计，就应该站在人的角度想——人站在这个页面上时他会想什么，不同的人要的 A、B、C 会引向不同的方向，我希望用最少的方式把 ABC 全部呈现出来。信息应该出现在你有不确定性的那个位置上。

概念卡 · 一致的设计哲学 README 也一样：你会用 AI 生成 slop README，但当你看过几个好的以后，你就会写 README。而且现在你有 AI，马上就可以问它「这个项目的 README 为什么没有 slop 的感觉」，它就会告诉你。好范例 + 追问，比任何教程都快。

本节要点

  • 好的界面/文档 = 在用户产生不确定性的地方，给出恰好需要的信息。
  • 对照范例学习是最快路径，AI 让「追问范例」的成本趋近于零。

1.8在脑中先实现一遍 23:24

读 research paper（也包括学任何课程——高等数学、计算机系统基础）的经典方法：virtually implement，在脑中先实现一遍。你有一个具体的问题或需求，先在脑袋里把这个问题自己做一遍，然后和作者的方法对比：

  1. 一致——很好，说明你已经学会了，完全掌握这个知识；
  2. 不一致，他比你精巧简洁——想清楚为什么他能想到，它就变成你知识的一部分；
  3. 不一致，你比他好——惊喜中的惊喜，可能一万次才遇到一次，但这个体验给你的正反馈很大：你突然会想「我能不能去做一个什么好玩的东西」。

所以讲师说，在 AI 时代你们更可以对细节保持注意力——看别人的 repo、读别人的东西、甚至 AI 生成的东西，都有感知细节的方式。第一章到此收尾：接下来讲 Git 的具体细节——「首先为什么要 Git」。

本章小结（01 章）

  • GPT-6 有惊喜但没学会品位；开放 intent 下 AI 必然漂移；代码正变得不需要人读。
  • 概念仍然要学（汽车司机比喻），它决定你能解锁多少 AI 的创造力。
  • 知识不重要、学习意识重要：惊人的注意力、自查法、virtually implement。
  • 项目管理方式的演进（U 盘 → 压缩包邮件 → Git）引出本讲主题：版本管理。

思考题（整理者补充）

  1. 回想你最近打开过的三个 GitHub 项目：它们各自的 README 与工程文件有什么细微差别？哪些信号是 slop，哪些是好设计？
  2. 选一个你熟悉的工具，用 1.8 的 virtually implement 方法先自己设计一遍再对比官方方案：你落在三种情况的哪一种？
  3. 「localhost:5137 笑话」暴露了什么信息差？你如何把「这个产品要被谁、在哪里使用」写进 intent？

CHAPTER 02

24:40 – 1:03:08 · 11 节

2.1什么是 Git：从推免面试的一个问题说起 24:43

GitHub 让代码分发变得前所未有的方便——这可能在他创立之初就想到了，但他们没有意识到的是，这竟然成为了 AI 时代的底层技术设施：NPM、各种工程配置，全部都在 GitHub 上。

上周末讲师参加了推免面试，问的问题是「什么是 Git」。大家多多少少都能说两句：「我从 Git 上可以下载分发代码」，有的同学能讲到 Git 管理的是目录（项目）的快照——「挺好的，当然我觉得也没有必要把所有人都挂掉，你能讲一些就可以，取决于你能讲多少」。git rebase 是 reflog 之外（更少有人会）的东西，这也在意料之内。

本节要点

  • GitHub 已是 AI 时代的底层技术设施，不只是代码托管。
  • 面试题「什么是 Git」的及格线：分发 + 目录快照。

2.2merge 冲突现场长什么样 25:53

面试里更意料之外的是另一问：git merge 发生冲突以后，你会观察到什么？大家都答得不好——第一说明没真正用过（没开发过；即使用 agent 开发，让它在不同分支开发也很容易遇到 conflict），第二说明没有留意过。

现场是这样的：老师的作业发布了一个更新，但你本地已经把代码改得面目全非，你让 agent「来吧」，它啪啪啪就给你修好了，说「测试都通过」，你看一眼觉得 OK——这个时候「惊人的注意力」就有用了。如果你愿意在冲突的时候停下来看一眼，你会看到一个非常神奇的东西：有好多等号、好多箭头。

站在 Git 设计者的角度想：文件原来是 1111，一个人把第二行改成 2，另一个人把第二行改成 3——到底应该是 2 还是 3？Git 不能只说一句「对不起冲突了，我不能合并了」然后躺在那，那对人的负担太大了。它要做的是把所有需要的信息全部放在现场：冲突的两部分代码同时显示，用 <<<<<<<、>>>>>>> 和 incoming / head 标记隔开；在 IDE 里还会有 accept incoming change 这样的按钮，你自己决定谁进谁出，完了再重新 commit 把冲突 resolve 掉。

概念卡 · First Principle 是连着的 「我刚才无意中举了那个地铁标识的例子，Git 也在用这个原则：如果你现在发生了一件事，最好就是在这个地方，把它所有要的信息全部都放进来。」冲突解决的责任曾经落在每一个开发者手上，所以 Git 把冲突现场完整地呈现给你——你只需要一点注意力，一两次就有印象了。

本节要点

  • merge 冲突现场：等号、箭头、双方代码并排 + IDE 的 accept incoming change。
  • Git 的设计哲学与地铁标识一致：信息出现在冲突发生的地方。
  • 结论两件事：多用一用；拥有更好的注意力。

2.3Git 是怎么被发明出来的 29:10

在 U 盘上放目录、每次打一个包的方式是不行的。讲师上学时（Git 还没流行）同学们的真实做法：作业 V1、作业 V2、作业最终版——每一次复制一个目录。这个方式能找回旧文件：万一你哪天手滑了、不小心改错了（新手阶段误操作非常正常），你想回去看上一个版本是怎么写的——这不就是一个需求吗？

概念卡 · 从需求发明 Git 项目就是一堆东西：代码、文档、intent、spec、implementation、测试用例，全部搅在一个目录里。如果我们能把目录的版本管理起来——只有一个作业目录，但可以提供一个命令行工具：list 一下作业有哪些版本、把当前版本切换回过去的某个版本——你就发明了一个简化版的 Git，哪怕还完全不懂分支、合并、冲突这些概念。等你用着用着，要和室友同步了，出现「两个人一起改同一个文件怎么办」，你就把合并也发明出来了。

所以版本管理不是需要「学」的天外来物，而是从「我想回到过去」这个需求里一步步推出来的东西——这也体现了人类的局限性：在 Git 之前我们用过的方案并不理想。

本节要点

  • 作业 V1/V2/最终版 = 最朴素的版本管理，核心需求是「回到过去」。
  • list 版本 + 切换版本 = 简化版 Git；多人同步需求自然催生合并。

2.4SVN 存 delta，Git 存快照 31:29

Git 之前有个你们可能听都没听过的东西：SVN（check in / check out）。SVN 的设计是存储项目的变化：保留最初的版本，每次文件改一行就存一个 patch。这看起来是一个非常高效的实现——但正是这个高效，随着项目增长把大家拖入了泥潭：你想回到一个早期的版本，就得一个 delta 一个 delta 往回退（当然可以用缓存优化，但讲师认为「有种确实是走错路了」）。

Git 的模型要干净得多：first principle 就是「我想回到过去的某一个版本，马上一秒钟就给我回去」。它的作者是 Linux 的作者 Linus。1991 到 2002 年维护 Linux 用的就是「作业 V1 作业 V2」的方式：在邮件列表上发补丁——我改了 a.c，往邮件列表一发，maintainer 看到后放进他的核心仓库再 release。中间用过 BitKeeper 这样的工具，直到 Linus 终于受不了了：他就想要一个绝对简单、又非常好用、概念正确的版本控制工具——2005 年，Git 诞生。所以它比我们想象的年轻一点。

想深入了解的同学可以去看《Pro Git》——「当然直接让 agent 看就可以了，不需要再去读了」。讲师顺带把这堂课的讲法点破：他从需求一路推下来，每一句话都和之前有逻辑关联，而逻辑关联多多少少都有数学在联系——「所以 OpenAI 认为它要把数学先训好，训好以后所有的问题可能都能解决；我自己是觉得，品位可能也是能解决的」。

本节要点

  • SVN 存 delta：省空间但回溯慢；Git 存快照：一秒钟回到任意版本。
  • 历史：邮件列表补丁 → BitKeeper → 2005 年 Linus 写下 Git。

2.5第一次 git init 34:58

COMMAND · 开启一个项目

git add hello.c

git status

git init 会告诉你一些奇怪的信息——这时你有两种选择：让 agent 帮你解答，或者把它忽略掉，「显然是高效的学习方法是更好的」。做完 init 之后，你得到了一个 .git 目录（默认隐藏，所以你看不到它），你的项目就变成了一个被 Git 版本管理的仓库——「就这么简单」。

之后你就可以从远端下载代码、把代码推到远端；最基础的命令：git add hello.c 把文件放进暂存区，git status 可以看到工作区里有什么。而 Git 很重要的一件事是创建项目的快照，使得你可以在任意时间之间穿梭。

本节要点

  • git init 的全部产物就是一个隐藏的 .git 目录。
  • add / status / commit 三个动作构成日常工作流的最小闭环。

2.6commit message 为什么重要 36:45

Git 推荐的 practice 和「作业 V1、作业 V2」完全不同：复制粘贴时代你把目录命名为「项目版本 V1 / V2 / V3」，而 Git 的世界里，每当你对项目做了任何改动——修了一个 bug、加了一个功能、调整了一个脚本或文档——你都应该立即做一次 git commit，并写一条说明「我这是做了什么」的消息（现场用 nano 编辑器完成）。

为什么 message 重要？项目本质上是从一个版本经过一次修改变到下一个版本，Git 虽然存储的是快照，但它鼓励你在 message 里描述你改了什么：一直看下来，你就知道这个项目是怎么发展走到现在的——修了多少 bug、加了什么需求、经历了什么样的重构。别人能够更容易地理解你的项目，这是好的软件工程 practice。

反面示范 · I did some cool stuff 讲师故意做了一个「I did some cool stuff」的提交，然后问 agent：这个 commit 符合 best practice 吗？回答：不太符合，主要问题在提交信息——可读性有问题，完全看不出做了什么。追问一句只要一秒钟，但它会给你很多解释。反证法也很干净：如果你有一万个提交，每个都是 I did some cool stuff，commit message 就变成 slop 了——那这个特性就不应该存在，直接叫 V1 到 V2 就行了。

本节要点

  • 任何改动 → 立即 commit + 有意义的 message。
  • message 是项目的「历史轨迹」，让协作者理解项目如何走到今天。

2.7空提交：一个可以但不应做的事 41:12

Git 允许你在不改任何代码（V 和 V2 完全相同）的时候再做一个提交吗？Git 本身会拒绝，但 agent 知道怎么做——现场让 agent 在不做修改的情况下完成了一次提交，果然得到了一个 empty commit。

什么时候有用？比如无改动时触发一次 CI 流水线；比如上一个提交修完了最后一个 bug，你已经得到了一个可以 release 的版本——你可以打一个 tag（V0.1），也可以强行做一个没有任何改动的提交，message 写「finalize：为 V0.1 freeze 所有东西」，把 bug fix 的提交和 finalize 的提交分开。这在偶尔的情况下是可以允许的，但你显然不能创建大量这样的空提交——「这个不是 best practice，所以尽量不要做」。

本节要点

  • 默认拒绝空提交；agent 知道绕过（有知识）。
  • 合法场景：触发 CI、用 finalize 提交分离 bugfix 与 release。

2.8把 agent 当最好的软件工程老师 43:41

学了 git add / git commit / git push / git pull，你就可以用 Git 了——「都会用了」。但真正水面下的冰山是各种各样的 best practice，而这每一个 best practice 其实都是血和泪的教训。为什么 message 要这样写？你转手问 AI，跟更有智慧的模型讨论一下「这样做有什么好处」。

讲师的自我解剖 「可能这个知识我是知道的，内化在我的脑子里面，你要给我两个小时，我可能也能给你写一个非常好的『为什么要做这件事』。但是我的智力是有限的，我的精力是有限的，我的注意力也是有限的——比如我现在上课，为了专注地和大家上课，大脑里做思考的那部分容量就有点不够了。所以我上课讲授一个概念的时候，讲的是 summarizable 的，不是最好的。」——把这些约定俗成的东西拿去和 AI 聊，它知道这个世界上所有的东西，能很好地把这些概念给你讲清楚。

这一节的态度很重要：不是「有了 agent 就不用学」，而是你多多少少还要知道我们为什么要做一件事——什么时候该 git add、什么时候该 git commit、commit message 应该怎么写；同时随时追问 agent「你刚才做的是不是符合 best practice」。

本节要点

  • 命令是冰山的水面上，best practice 是水下、是血和泪。
  • 人的智力/精力/注意力有限，agent 是随时在线的软件工程老师。

2.9.gitignore 与「不该进版本库的东西」 45:13

一个非常常见的场景：你有一个 untracked file，tutorial 里教你一个好命令 git add .——改了三五个文件时不需要 git add a.c b.c c.c，一把梭。Git 不阻止你，「这是完全合法的」。然后再问 agent：刚才的提交有什么不符合 best practice 的吗？它按严重程度排序回答（「还是很聪明的」）：第一，提交信息毫无信息量（开骂了：主观废话）；第二，提交粒度和内容混杂——hello 是编译产物，根本不应该进版本库，应该加进 .gitignore，用构建系统产出。它还会给出建议：用起始句、现在时描述变更动机（例如 fix off-by-one），以及 Conventional Commits 前缀约定。

为什么编译产物不能进版本库？讲师展开：每个合作者的环境都不一样，build 出来的东西也不一样——你的二进制里可能带日期、带 hash、带你本机的指纹，每次编译出来都可能不同。一旦提交，下一次就会产生冲突：这里有个 hello、对方有个 hello，同样的源码编译出来都可能不一样，更何况不一样的源码。二进制的冲突是很难合并的——文本冲突好歹能看，二进制（乃至图片）几乎没法合。

更精彩的现场：讲师继续「做坏事」，agent 甚至提出重写历史——丢弃空提交和编译产物的两段历史，新建 main 分支，重写为两个有意义、单一职责的提交；并且贴心地先检查了历史没有 remote（仓库没有和远端同步，不会有别人——「因为如果别人也持有这个历史，那就是一个比较糟糕的事情了」）。还有好玩的细节：commit message 里写 fixed #3，GitHub 会自动把对应的 issue close 掉——「这里面有很多好玩的，你只有反复地使用，才能获得初学者和有经验者的区别」。

规则没有绝对 不是所有 generated file 都不该提交：比如 package-lock.json 应该提交；再比如你用另一套工具链生成一个 header，把它放进来，别人在不需要下载很多依赖的情况下依然可以编译这个项目。「所以也没有绝对的规则。」

另外两个必须知道的老牌功能：git blame（讲师「很喜欢这个功能」）告诉你每一行代码是在哪一次提交、哪一个地方改的；git bisect 则是对提交历史做二分查找——当前版本发现一个 bug，它可能不是你的代码引起的，而是过去某一次提交引入的。如果你有一个能检查出 bug 的测试用例，就可以在整个 Git 历史上二分：从某一刻起所有提交都不通过、之前都 OK——「这不就是一个前缀全是 0、后缀全是 1 的数组里找第一个 1 吗？」（就是保研、工作面试要手写的那个二分查找。）

还有一条容易被忽略的基础要求：每次提交的代码应该能够通过构建和测试。现场演示提交一段编译不过的代码，agent 拒绝并解释：「Git 提交应当是一个完整自洽的快照，提交编译不过的代码，相当于让仓库处于坏状态」——然后顺手把代码修好了。「他比你聪明：改作业的时候我们都会有这种倾向，改一个字不要紧的，就改了就提交吧。」

agent native 的一代 「你们都是 agent native 的人，肯定也不会用古法——git status 这种都已经成为了古代手艺。你现在一定是用 agent：你不需要知道具体的命令是什么，但你要有概念说我的 Git 能干什么，你就可以让它用符合 best practice 的方式干。」当然这带来一个问题：你分不清你是真的自己能干，还是脱离了 agent 就干不了——「但也许我觉得这也不重要。」

本节要点

  • git add . 合法但危险：编译产物、临时文件会被一起提交。
  • 编译产物带日期/hash/本机指纹 → 二进制冲突几乎不可合并 → 进 .gitignore。
  • git blame 查行级出处；git bisect 在历史上二分找引入 bug 的提交。
  • 提交必须是能通过构建测试的自洽快照。

2.10导师的高血压时刻 55:14

讲师回忆 LLM 之前带新同学的固定剧情：新同学进组，开一个 Git repo，第一周打个架子跑起来——然后导师打开项目，进入高血压环节：dist、log 被交上来了（都是生成文件，不应该交）；个人的 VSCode 配置交上来了，里面甚至有 C 盘下的硬编码路径，在任何其他地方都没办法复现；更高血压的是，审的时候能看到一些处于 active 状态的 API key。

课堂名场面 「当我发现这个 API key 是 DeepSeek 的时候，我就知道这应该是一个中国兄弟。」

另一个经典是 .DS_Store：用 Mac 的同学在 Finder 里打开一个目录，系统会自动留下索引（你展开了哪些子目录），存在一个叫 .DS_Store 的文件里。因为它以点开头所以默认隐藏（讲师的 ls 还贴心地给它一个苹果图标），你看不到它，然后一 git add . 就糟糕了——它会被 Git 追踪。这其实是合理的：点开头的文件里有很多约定俗成要进库的东西（.github/workflows 等配置），默认都会被收进来；但 .DS_Store 这种经常变化的临时文件就不应该提交。

概念卡 · AI 解放了师生关系 过去的场景：导师把学生叫到办公室，肯定已经高血压了，还得装作 nice：「你提交的项目不太符合软件工程的实践……」而学生听着总觉得老板不满意——「无论我的情绪多么正常，我只是在教他一个知识，学生总是有压力的。」AI 把这一层人际摩擦拿掉了：那个你无法控制的力量，反而让同学可以零压力地把 best practice 学对。

本节要点

  • 高血压三件套：生成文件（dist/log）、个人配置与硬编码路径、API key。
  • .DS_Store：隐藏 + git add . 的组合陷阱；点开头默认进库是合理但需甄别。
  • 基于规则的检查工具路线，已被大模型的耐心检查取代。

3.1Git 是一个持久化的数据结构 1:03:41

AGENTS.md 也有了，接下来要学一学 Git 到底是怎么工作的。讲师推荐去看他操作系统课上讲 Git 的那一段，「我就没有必要再讲一遍了」，只讲一个头：Git 是一个持久化的数据结构。那它持久化的是什么呢？——目录树。

从最基础的想法出发：项目是一棵树（根目录下有 a.txt、b.txt，还有子目录 d，d 里面还有很多文件）。现在要创建 V2，需要把所有文件都复制一份吗？不需要。假设这次只改了 b.txt：只需要为 b.txt 创建一个新版本；树的其余部分——a.txt、d 目录——都可以用指针指回旧版本。唯一要复制的是从改动节点到根的路径：根节点必须新建（不能指向旧的），否则就会用上旧的 b.txt。

概念卡 · 小增量，整棵树 即便项目有一百万个文件，目录本身不可能很深——没有人会建一千层深的目录，每一级索引都是指数级增长的。所以每次提交只需要创建一个非常小的增量（改动的文件 + 到根的路径），就得到了一个版本的快照。从 first principle 出发，一个大学生想设计出这样的东西是完全有可能的。

本节要点

  • Git 持久化的是目录树；新版本 = 改动文件的新版本 + 到根路径的复制 + 其余用指针。
  • 目录浅、分叉多 → 增量极小，快照极其廉价。

3.2三大对象：blob / tree / commit 1:06:29

打开 .git 目录（在 .git/objects 里面），你会看到各种各样的 object——它们就是普通的文件，带 hash 索引，是这种数据结构的各种节点：目录的节点、文件的节点，还有 commit 的节点。一共三大类型：

  • blob object——blob 就是字节序列，文件内容本身；
  • tree object——目录节点，记录名字、权限和指向下层的指针；
  • commit object——版本节点，指向一棵 tree，串起历史。

「然后它就是一个数据结构，这个数据结构可以不断地向后生长，这个问题其实就解决了。」

本节要点

  • .git/objects 中的一切都是带 hash 索引的普通文件。
  • blob（内容）/ tree（目录）/ commit（版本）三类对象构成可生长的数据结构。

3.3不踏实：真的是这样实现的吗 1:07:27

纸面上讲完，一个健康的不踏实感应该出现：「老师，commit object、tree object、blob object，真的有这样吗？」再往前想一步：既然可以从 V1 创建另一个 tree——世界就分叉了——那分叉以后，合并到底会发生什么？你就自然而然地想象这些问题。

课堂案例 · 古法编程的巅峰之作 「根据计算机科学定律：你想要的东西，就一定有人做。」讲师打开浏览器，展示 learngitbranching.js.org——「这是古法编程的巅峰之作之一」，以可视化的方式展示 Git 是怎么工作的：它模拟了各种命令（git commit、git checkout 都有），你在左边敲命令，右边就用动画演示版本树的生长和切换，「它用这个方式来教你 Git 是怎么工作的」。

但注意它的局限：这是模拟出来的——它建了一个 Git 的模型。而今天你有办法在真正的、live 的 Git repo 上直接看到发生了什么。

本节要点

  • 「不踏实」是正确的学习状态：追问机制、想象分叉与合并。
  • learngitbranching.js.org 是模拟器；真仓库可视化是另一条路。

PROMPT · Git repo 可视化工具（课堂原文）

3.5现场看到 blob、tree 与 refs/heads 1:11:51

用这个工具看 main 分支，纸面上的说法全部被验证了：

  • 第一次提交的 message 是「I did some cool stuff」，里面有一个空的 hello.c——它对应一个真实的 blob object：你能看到磁盘上带 hash 的文件、它的原始字节序列，工具还会帮你解压缩（31 字节解压出 23 字节——「对于很小的文件来说，这个压缩反而是浪费，但这不要紧」）。可执行文件 hello 也是一个 blob，能看到它可执行文件的头。
  • tree object 同样可以看到磁盘上的原始数据（52 字节解压出 43 字节）：解压后以文本形式记录着 644 这样的文件权限、hello.c 的名字和指向 blob 的指针；根目录的 tree 里有两个文件——755 的 hello（可执行）和 644 的 hello.c。
  • 分支是什么？分支就是一个文件：refs/heads 下的 a——它就是一个指针，指向一棵 tree；而 HEAD 是指向指针的指针。「所谓分支，就是指向这些东西的指针，它在磁盘上是这些字节。」现场让它创建两个分支，左右两栏实时同步出动画。
关于直出的 slop 工具的视觉效果并不完美（连线歪、显示乱码字符）——「one shot 直出，没有改」，只发过第二个 prompt 微调过一点。「但我相信我跟它对话几轮以后，应该就能搞定了，就得到了一个近乎完美的 Git visualization。」

本节要点

  • blob = 字节序列（可执行文件也是 blob）；tree = 权限 + 名字 + 指针。
  • 分支 = refs/heads 下的一个文件（指针）；HEAD = 指向指针的指针。
  • 纸面模型在 live repo 上逐条验证，这就是「不踏实」的最好解药。

3.6merge 时 git 悄悄留下的三个版本 1:16:24

让工具展示 merge conflict 的状态：两个开发者——你和你的团队成员每个人都对这段代码不爽，你们俩都重构了——就会进入冲突状态：A 在这儿，B 在那儿；当你把另一边拉到本地，就会看到冲突现场，hello 的内容是带尖括号标记的那段文本。

更妙的是未提交的区域：index 里面有好几个你看不到的 hello.c——git 悄悄地在那里留了三个版本：base（公共祖先）、ours（你这边的）、theirs（对方那边的）。resolve 之后，那些临时文件消失，merge 创建了一个新的 commit object——它的 tree 是选定后的版本，它有两个 parent，还有 author——指向的关系被正确地保留下来。纸面上「合并产生双亲提交」的说法，在可视化里亲眼看到了。

本节要点

  • 冲突时 index 中藏着 base / ours / theirs 三个版本。
  • merge 产生有两个 parent 的 commit object，祖先关系完整保留。

3.9原子变更：为什么提交要小 1:29:37

网上可以找到很多 Git 的口号，比如 Commit often, Perfect later, Publish once——「这些其实都是有工程实践的经验的」。为什么要及时 commit？因为在复杂的项目里，随着你修改的东西越多，你错的东西就越可能多：小项目刚开始时一次提交两三千行都 OK；但一旦项目里有了错综复杂的关系，一个大的 commit 可能会 break 项目里多处的东西、引入多个 bug，后面又要引入多个 fix 来修它。如果你有一个一万行的大 commit（比如 V2），后面修了一百个 bug 你都说「这是 V2 产生的」——那就很糟糕，甚至修不过来，你也不知道 V2 到底修好没有。

概念卡 · 小提交的复利 「如果你每一次的 commit 都是很小的、都只做一个修改，那么冤有头债有主：这个 bug 就是你写的，好，我修完了也就修完了——这两个 commit 是可以配对的。」小提交给了我们审计的能力：可以 review、可以 revert、可以 bisect（二分查找）。还有一个朴素的好处：你改了很多东西、电脑突然物理损坏还没来得及推远端——小步提交、立即 push，你就有了一个互联网上的备份。

还有一块拼图：GitHub 实在太流行、太好用了，所以值得做一个命令行工具（gh，GitLab 对应 glab）把 non-Git 的部分管理起来——Git 管理的是代码快照，但 GitHub 上还有 issue、还有对你代码的 comments，这些东西不随着 Git 的 tree 做 persistence。装了 gh，agent 就可以 fetch 一个 issue、找到 assign 给我的 issue、把它 close 掉；你就可以在 agent 里设置一个很长的任务，要求它做小步的、可以审计的提交，并约定分支的规则、线性的历史等等。讲师自己的项目里就有大量这样的 agent 提交，「很多时候我都不管他们」。

本节要点

  • 大 commit 会同时 break 多处、引入多 bug，且事后无法定位；小 commit 可以配对、审计。
  • 小步提交 + 立即 push = 灾难备份。
  • gh/glab 补上 issue / comments 这些不进 Git tree 的协作数据。

3.10linear history 与工程细节 1:26:52

有注意力的话会注意到：AI 生成的 commit message 本身有格式——前面的提交都是英文、一行标题加一个详细解释；后面它开始自由发挥，混了英文和中文，但仍然遵循「一行带 scope 的标题 + message body」的结构。这个东西是有标准的，叫 Conventional Commits：文档很短，规定 commit 必须以一个 type 前缀开头（feat、fix 这样的名词），后面一个冒号、一个空格，描述以动词开头——「我如果要引入一个 feature，我要 fix 一个 bug」。

还有更小的工程细节：markdown 文档里英文和中文之间要有一个空格——讲师不知道从什么时候开始大家都用这个盘古之白，「对我来说这是肌肉记忆」。最难受的不是没有空格，而是一个文档里有些地方有空格、有些没有——不一致。你哪怕统一用另一种 convention，他都认为你是在遵循某种规范；不一致就「真的有点头大」。这些细节都是为了工程师在面对更大项目时有一种一致性：代码以同样的方式排版，文档自然也要以同样的方式排版，人维护起来会更好——虽然 AI 时代好像也不那么重要，AI 都会帮你解决，「所有用 AI 的学生都不会生成那样的 slop」。

然后是整讲最核心的一段总结。讲了很多 Git，其实这门课讲的是软件工程：

本讲要记住的一句话 「Git 本质上是一个软件，它说我们要把项目组织成用 atomic change（原子变更）推进的快照——这是你们今天要记住的事情，所有的一切都是从这句话里面推出来的。」管理快照，就可以随时开一个新的分支做尝试：失败就安全地扔掉，成功就合并进来；甚至可以同时推进多个主线、以合并的方式完成而互不干扰（古法做大作业改几个地方，改着改着就乱了）。项目管理的本质是人类没有办法处理一团混沌——很多需求、很多代码、一次做一大波——所以要把需求分解成可以理解、可以审计的小任务，一小步一小步来：出了问题可以 bisect、可以 blame；两个小任务发生冲突，也能知道是哪一个小的提交冲突了，剩下的部分合并起来会比较容易。

最后一个现代实践：合并可以产生有两个 parent 的 commit（又分又合的典型 Git 结构），但现在更流行 linear history——「反正都是 AI，它 resolve、它 rebase 都很容易」，就强行要求整个 commit history 都是线性的。它不全是好处，但至少对现在的项目维护来说：历史更易于追溯，对 cherry-pick 和 blame 更友好。在无限大能力的模型到来之前，把 Git 记录拆分得非常好，很容易找到一次修改是谁引入的，AI 维护项目的效率也会高一点、也省 token——有些文件它就可以不用去读了。

本节要点

  • Conventional Commits：type 前缀 + 冒号空格 + 动词描述；盘古之白式的排版一致性。
  • 一句话总纲：项目 = 用 atomic change 推进的快照。
  • linear history：AI 时代的合理选择，利于追溯、cherry-pick、blame，省 token。

3.11我是怎么管理一个项目的 1:36:37

讲师分享自己的实战流程。第一步，架构设计阶段用单线程：开一个智力比较高的模型跟他讨论——「这个其实很重要，因为如果你的软件设计得不好，你后面就是无穷的迭代」。他会把组件库的接口定得非常好，这也是他为什么敢信任 AI 的代码：绝大部分接口都设置成 pure function，包括 trace——它是程序的一个 pure function；有一个标准的程序 derivation graph，要求按这种方式展开；所有全局互相影响的状态，都注册到一个全局的地方（比如光标位置如何影响可视化、菜单条）。

结果是一个「非常干净、非常小」的状态：一个 playground，核心的共享状态只有十几行，组装也只有十几行，剩下所有东西都是黑盒子。他甚至直接要求 agent：在设计这些 visualization 的时候禁止看任何库函数的实现，只看接口——这非常省上下文，几万个 token 就可以做一个这样的 playground。

第二步，架构定稿后开三个（或几个）terminal 并行。他的 AGENTS.md 里有明确的协作规则：不让 agent 调用视觉模型去检查（agent 很喜欢做这件事，会花很多 token），也不调用浏览器任务——他在旁边另放一块屏，开一个浏览器实时刷新。然后「哪里不满意就骂他」，肉眼看着右边的东西不停地变好、变好、变好，问题就解决了。

讲师的边界判断 「这是一个 agent 能力之内的项目。」而他非常确信的是：agent 能力会不断增长，越来越多的项目能够被 agent 以这样的方式完成——一个比较轻量的讨论，然后剩下完成。

本节要点

  • 架构先行：单线程 × 高智力模型讨论；设计不好 = 无穷迭代。
  • 接口 pure function 化 + 全局状态集中 + 禁看实现 → 上下文极省。
  • 执行阶段多 terminal 并行 + AGENTS.md 协作规则 + 实时刷新屏验收。

附录 C课堂演示与命令范例复盘

本讲以现场演示为主。附录按课堂顺序复盘每一次演示的命令、prompt 与结果，可作为上机跟随的操作清单；演示结果的描述均来自逐字稿。

  1. 第一次 init 与最小工作流（2.5）——
    COMMAND

    git init　# 得到一个隐藏的 .git 目录，项目成为被 Git 管理的仓库

    git add hello.c

    git status　# 查看工作区状态

    git commit　#（现场用 nano 编辑器）写入 message 完成快照

    init 输出的「奇怪信息」两种处理法：让 agent 解答，或忽略。
  2. 反面示范 commit message 并让 agent 审查（2.6 / 2.9）——故意做一条「I did some cool stuff」提交，或用 git add . 把 untracked 文件一把梭，然后问：
    PROMPT

    我刚才做的一个 git 提交，有什么不符合 best practice 的吗？

    课堂结果：agent 按严重程度排序开骂——提交信息毫无信息量（主观废话）；编译产物不该进版本库，应加进 .gitignore；建议用起始句、现在时描述变更动机，并提及 Conventional Commits 前缀。
  3. 空提交演示（2.7）——Git 默认拒绝无改动的提交；让 agent「在不做修改的情况下提交」，得到一个 empty commit。合法场景：无改动触发 CI；用「finalize」空提交分离 bugfix 与 V0.1 release。
  4. 提交编译不过的代码（2.9）——
    PROMPT

    帮我提交（当前代码编译不过）。

    课堂结果：agent 拒绝直接提交并解释「提交应当是完整自洽的快照，提交编译不过的代码相当于让仓库处于坏状态」，随后把代码修好。
  5. 重写历史（2.9）——继续「做坏事」后，agent 提出：丢弃空提交和编译产物的两段历史、新建 main 分支、重写为两个有意义、单一职责的提交；并先检查仓库没有 remote（不会被别人持有旧历史）。
  6. 配置 agent 提醒钩子（2.11）——
    PROMPT

    帮我配置一个全局的 hook，在 agent 需要输入的时候「叮」一声提醒。

    现场曲折：两次没听到声音，agent 自己意识到意图后修好；同一节还演示了 pre-commit hook 规则命名「大写还是小写」的两难与 AI 的心理分析。
  7. gitv：live repo 可视化工具（3.4）——见 3.4 的完整 prompt。要点：从文件系统真实文件与原始 byte 出发解析对象、持续监听 .git 变化并用动画展示。随后依次演示：查看 main 分支的历史与对象（3.5）、创建两个分支观察 refs/heads 指针动画、展示 merge conflict 状态并 resolve（3.6）。
  8. 查证三件套（2.9）——
    COMMAND

    git blame hello.c　# 每一行是在哪次提交、哪里改的

    git bisect　　　　# 用测试用例对提交历史二分，定位引入 bug 的提交

    bisect 的本质：前缀全 0、后缀全 1 的数组里找第一个 1。
  9. 教学 playground 的架构清单（3.7 / 3.11）——非命令，而是给 agent 的架构约束：接口尽量 pure function（含 trace）、全局状态集中注册（十几行）、要求 agent「禁止看任何库函数的实现，只看接口」、AGENTS.md 写明协作规则（不调用视觉模型、不调用浏览器任务、旁屏浏览器实时刷新），架构定稿后开三个 terminal 并行，「哪里不满意就骂他」。
