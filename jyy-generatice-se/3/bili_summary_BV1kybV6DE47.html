01

开场 & 版本管理

00:00 开始播放

本章看似是闲聊，其实全部在讲同一件事：在 AI 什么都能做的时代，人还剩下什么是值得学的。答案不在「知识点」里，而在注意力和对世界的感知上。

1.1开头：一次 GPT-6 的现场演示

00:00

开场直接放了一段 GPT-6 的现场演示作为这学期的起点。上半年还在讨论 GPT-5.6s，几个月之后版本的迭代已经要重新理解一次。老师用这类演示来说明一件事：技术演进的速度已经超出了「按学期更新教学内容」的节奏。

为什么用演示开场
  • 先让同学对「能力上限」有一个体感，再谈课程安排才有效
  • 这些能力不是未来的可能性，而是当下就可以用到的东西
  • 课程的立场：不追着讲工具，而是讲判断力——什么时候该用、用到什么程度

1.2代码正在变得不需要人读

02:00

老师提到一个正在发生的转折：过去写代码是为了让人读懂，现在越来越多的代码是写给机器执行的——人不再需要逐行阅读它。这直接冲击了几十年来的工程惯例（命名、注释、可读性）。

1.3AI 时代还要不要学数据库和操作系统

04:40

这是全章最实在的一段。老师先复述了同学最常问的问题：既然 agent 都会写，为什么还要学数据库、操作系统、编译原理这些「底层」？他没有直接给答案，而是打了一个类比。

1900 年代的司机必须懂机械——会修化油器、会换轮胎、听得出发动机异响。今天的自动驾驶不需要你懂这些。但这不意味着机械知识没用了，而是它的用途变了：不再是开车的前提，而是理解限制、做出判断的背景。

——讲师用汽车与驾驶的类比说明「底层知识」地位的迁移
问题的表层
「学了这个还有用吗」——按「会不会被 AI 替代」来判断知识价值
问题的深层
「我能不能判断 AI 做得对不对」——这才是底层知识真正的作用
结论
底层知识从「操作技能」变成了「审查能力」，它不再帮你做事，而是帮你判断
具体到本课
不懂 Git 的对象模型，就没法判断 agent 那套「重写历史」的操作是否安全
值得记下的判断

老师在这一段的立场很明确：不是「要不要学」，而是「为什么学」发生了改变。为了动手而学、与为了判断而学，是两种完全不同的学习方式。

1.4惊人的注意力

07:40

老师反复提到的一个习惯，越到后面越重要，可以说贯穿了整门课：看到别人给你的答案之前，先自己想一想你会怎么做。

惊人的注意力 · 具体做法
  • 看到一个结论，先问「如果是我，我会怎么做」，再看别人怎么做的
  • 看到一次报错、一次冲突、一次失败，停下来一秒，看清楚它长什么样
  • 学生时代的时间成本极低——一秒钟的观察，换来的是一辈子的印象
  • 关键不是「多花时间」，而是把注意力放在别人会跳过的地方

1.5第一个博士生的 U 盘事故

10:20

老师讲了一个自己带过的故事：第一个博士生把研究数据放在 U 盘里，U 盘坏了，数据没了。这件事后来成了他坚持用版本控制的原因，也成了这一讲的叙事起点。

他借此说明：版本管理最初的动机不是「多人协作」，也不是「工程规范」，而是一个非常朴素的需求——我想回到上一个版本，看看那时候我写的是什么。

这一段的落点

所有版本控制系统的第一性原理，都可以从一个学生「怕文件丢、怕改错」的处境里推出来。先有需求，后有工具——这是老师反复示范的思考方式。

1.6我要的是对世界的感知能力

12:40

接着上面的话题，老师澄清了一件事：学习的产出不是一个知识点清单，而是对世界的感知能力——能不能判断一件事会发生什么、后果有多严重、哪个方向是对的。

为什么「感知」比「知识」更重要
  • 知识可以随时问 AI 得到，但「该问什么」问不出来
  • 感知能力决定了你能不能在信息不足时做判断
  • 它只能通过一次次真实的观察、失败、复盘积累

1.7香港与南京的地铁标识

15:00

这一讲里最精彩的类比之一。老师比较了香港地铁与南京地铁的站内标识设计：香港的出口指示牌在地上、在天花板上、在每一个转角处都有；南京的则往往集中在某个位置。

他由此引出一条通用原则：当一个人处于「需要做决定的那一刻」，应该把这个决定所需的所有信息，放在他所在的那个位置。信息要放在发生的地方，而不是放在「你应该去看」的地方。

1.8在脑中先实现一遍

19:40

章末给了一个具体的学习方法，后面第 3 章讲 Git 底层时会再次用到：在做之前，先在脑子里实现一遍。

virtually implement：四步
  1. 明确需求——「我想回到上一个版本」
  2. 自己设计一个最小方案——「那就每次复制一份目录，再加个命令列出所有版本」
  3. 发现这个方案的缺陷——「目录会爆炸、无法比较、无法多人协作」
  4. 对照真实实现——「原来 Git 是这么解决这些缺陷的」
本章小结

第 1 章没有讲任何 Git 命令，但它是第 2、3 章的前提：先把「学什么」想清楚，再去看「怎么用」。注意力的价值在于，它让你在第 2 章看到冲突现场时，不只是「修好了」，而是「看懂了」。

02

Git 入门与一些最佳实践

24:40 开始播放

本章是全片最长的一段，也是信息密度最高的。它从一个面试问题切入，一路推演出 Git 的设计动机，最后落在「水面下的冰山」——那些用血和泪换来的 best practice。

2.1什么是 Git：从推免面试的一个问题说起

24:40

老师刚参加完推免面试，把这个过程搬到了课堂上。他先问「什么是 Git」——大多数同学能答出「下载分发代码」「管理项目快照」，这在他意料之中。

真正让他意外的是下一个问题：git merge 发生冲突以后，你会观察到什么？几乎没有人答得好。

2.2merge 冲突现场长什么样

26:00

老师现场拆解了冲突现场。假设一个文件原来是 1 1 1 1，A 把第二行改成 2，B 把第二行改成 3。这时候 Git 不能替你决定——它把两边的版本都摆出来，把责任交回给人。

冲突标记的三段结构
  • <<<<<<< HEAD 之后是当前分支的内容
  • ======= 是分隔线
  • >>>>>>> incoming 之后是要合进来的分支的内容
  • IDE 会在上方多出按钮：accept incoming change，让你自己决定谁进谁出，再重新 commit 完成 resolve
老师的亲身经历

「我现在也是这样——merge 出错了，让 agent 帮我修，最后它说测试都通过，我看一眼觉得 OK。但如果你愿意在冲突的时候停下来，尤其是学生时代，你会发现一个完全不同的世界。」

2.3Git 是怎么被发明出来的

31:10

这一节是全片方法论最集中的地方。老师不是直接讲 Git 的历史，而是从需求一步步推到设计，让同学看到 Git 是可以被「想出来」的。

从需求推导 Git · 老师的推演链
  1. 起点：U 盘里放目录、每次打一个包 →「作业 V1、作业 V2、作业最终版」
  2. 发现需求：我想要回到上一个版本，看看我那时候怎么写的（可能是误操作，也可能是想看旧实现）
  3. 提炼需求：把「目录」的版本管理起来，不再靠复制多个目录
  4. 设计最小工具：一个命令能 list 所有版本、另一个命令能 切回某个版本——你已经发明了一个简化版 Git
  5. 需求继续生长：和室友一起改同一个文件怎么办？→ 你自然会推出分支、合并、冲突

老师强调这条推演链的意义：每一步都和前面有逻辑关联，而这些关联里「多多少少都有一些数学在」。他甚至把这一点和 OpenAI 说「要先把数学训好」联系起来——因为推理能力是一切问题的底层。

为什么人类先发明了 SVN 而不是 Git

「这体现了人类的局限性」——在没有 Git 之前，大家先用的是 SVN（check in / check out）。这说明最优解不是必然被最先找到的，路径依赖真实存在。这一段为下一节的对比做了铺垫。

2.4SVN 存 delta，Git 存快照

31:52

这是全章技术含量最高的一段对比。老师说 SVN 存的是项目的变化（每次改一行就存一个 patch），Git 存的是快照。前者看起来更省空间，但会随着项目增长把大家拖进泥潭。

2.5第一次 git init

34:48

开始动手。老师建了一个空的 terminal，演示最基础的两个动作：git init 和 git add。

两个必须知道的「隐性知识」
  • git init 之后会打印一些看起来很奇怪的信息。这时有两种选择：让 agent 解释给你听，或者忽略它——而前者是更高效的学习方式
  • 目录里多出一个 .git，但它默认是隐藏的，所以你看不到它
  • 做完这一步，你的项目就变成了一个「被 Git 版本管理的仓库」
git add
把一个文件的变化放进暂存区（staging area），准备提交
git status
看当前工作区里有哪些变化、哪些已暂存
git commit
创建一个带有消息的快照，可以在任意时间点之间穿梭

2.6commit message 为什么重要

36:40

老师在这里说了一句很重的话：「这体现了软件工程的智慧」。他用「作业 V1 / V2 / V3」和 commit message 做对比。

反面示范：I did some cool stuff

老师故意做了一个 I did some cool stuff 的提交，然后问 AI 这符不符合 best practice。AI 直接指出：提交信息毫无信息量，是最重要的问题；用祈使句、现在时，描述变更动机（例如 fix off-by-one in strlen check）；还建议考虑 conventional commits 前缀。

一个很实用的动作

「你真正需要的是：在任何时候学习。碰到新东西的时候追问一句——我刚才做的，符合 best practice 吗？」老师说这一问只要一秒钟（加上豆包语音输入），但会得到很多解释。

2.7空提交：一个可以但不应做的事

40:00

老师抛出一个反直觉的问题：能不能在不改任何代码的情况下，再做一个提交？你自己敲 git commit 会被拒绝（没有修改），但他让 agent 做，agent 知道怎么做。

场景
一个 bug fix 完成后，想为发布打一个「冻结点」
常规做法
在最后一次提交上打 tag（如 v0.1）
空提交的做法
强行做一次无改动提交，message 写「finalize for v0.1，冻结所有东西」
好处
把「bug fix 的提交」和「finalize 的提交」分开，历史更清晰
另一用途
无改动时触发 CI 或流水线
约束
偶尔可以，绝不能大量创建——所以它不是 best practice
这里真正的教学点

老师问的不是「能不能」，而是「你为什么想这么做」。能说清动机的空提交是工程判断；说不出动机的空提交是噪声。这和 commit message 那一节是同一个主题。

2.8把 agent 当最好的软件工程老师

44:00

老师让同学做了一件很违反直觉的事：故意做一次「不那么规范」的提交，然后让 AI 按严重程度排序指出问题。结果 AI 的表现相当好——它还会告诉你应该怎么做。

老师的一段自陈

「我可能这个知识是知道的、内化在脑子里面，但你给我两个小时去想，我也能写一个非常好的『为什么要做这件事』。但是我的智力是有限的、精力是有限的、注意力也是有限的。我在上课的时候，大脑里做思考的那部分容量就不够了，所以我讲的是 sub-optimal 的，不是最好的。」

——讲师解释为什么建议同学课后继续追问 AI

2.9.gitignore 与「不该进版本库的东西」

47:00

老师演示了 git add . 的危险：它会把所有未跟踪的文件都加进来，包括那些本不该进版本库的东西。

2.10导师的高血压时刻

56:00

老师很生动地讲了带新博士生的经历：打开新同学的 Git 项目，往往会进入一个「高血压环节」。这一节有点像「新人常见错误清单」，但老师的意图是——这些正是过往同学用真实的代价换来的经验。

打开项目就能看到的几类问题
  • dist、log 被提交上来——都是生成物，不该交
  • 个人配置、IDE 设置被提交——甚至带着 C:\... 这样的硬编码路径，换个环境根本无法复现
  • 更高血压的：处于 active 状态的 API key 被提交。老师说「当我发现这个 API key 是 DeepSeek 的时候，我就知道这应该是一个中国兄弟」
  • 没有 Mac 的同学不经意间把 .DS_Store 交上来——Finder 打开目录就会生成，而它是以点开头的隐藏文件，所以「你是看不到的」
一个耐人寻味的收束

老师说他做软件工程研究，其中一个很标准的课题就是「研究你的 Git 项目满不满足这些实践」，不满足就给你一个提示，最后做成一个小工具、在提交前告诉你 OK 不 OK。「但所有这些都被大模型杀死了——因为大模型可以如此耐心地给你检查，还给你一个 emoji 让你开心一下。」

2.11hook 与大写还是小写

59:20

章末，老师用一个很小的例子收尾：他在给几十条检查规则命名时，纠结该用全大写还是小写。他从使用角度看「两个都没问题」，但这是个两难。

他现场让 agent 配了一个 hook——在 agent 需要我输入的时候「叮」一声提醒——并且演示了 hook 在 git pre-commit 上的用法。然后他把这个「大写还是小写」的问题丢给 GPT 解释，AI 从他的心理动机出发分析「为什么全大写会显得更强」。

本章小结

「你学了 git init、git push、git pull，就会用 Git 了。但真正水面下的冰山是各种各样的 best practice，而每一个 best practice 其实都是血和泪的教训。」——第 2 章的实操到此收尾，下一章要从「用」转向「理解它是怎么实现的」。

03

学习 Git

63:08 开始播放

本章从「讲完了但我有点不踏实」出发，把 .git 目录拆开看。老师用自己 webcoding 出来的可视化工具，现场验证了纸面上讲的对象模型——并在最后回到软件工程本身。

3.1Git 是一个持久化的数据结构

63:08

老师先给了一个一句话的定义：Git 是一个持久化的数据结构。它持久化的是「目录树」。

接下来他用一个非常关键的问题推进：如果你有一个很大的项目（比如说一百万文件），要创建 V2，需要把所有文件都复制一份吗？答案是不需要——只需要复制「从改动文件到根的那条路径」。

顺带一句关于目录设计的话

老师说「没有人会去建一个一千层深的目录」，从「渐进式披露」的角度也没必要——每一级索引都是指数级增加，很快就能把所有的类分完。这句话虽然是顺带提的，但它是理解 Git 效率的前提。

3.2三大对象：blob / tree / commit

66:00

3.3不踏实：真的是这样实现的吗

73:40

讲完纸面上的模型之后，老师问了同学一个问题：你有没有觉得有点不踏实？我们的 Git 真的是这样实现的吗？tree object、blob object 真的有这样吗？

3.5现场看到 blob、tree 与 refs/heads

72:00

老师删掉一个文件、创建分支，然后逐个查看 .git 里的原始数据。这是全章最「实证」的一段，也是对 3.2 节模型的直接验证。

blob（文本）
压缩前是 blob 15\0… 的字节序列；解压后看到「blob 15 + 内容」——对于很小的文件来说，压缩反而是浪费（31 字节压出了 23 字节）
blob（二进制）
一个可执行文件，头部以 7F 12 F 之类的字节开头，同样能看到原始序列
tree
压缩前 52 字节，解压 43 字节。内容形如 100644 hello.c <hash>，其中 644 是文件权限；755 则说明这是一个可执行文件
分支
refs/heads/A 就是一个文件——所谓分支，就是一个指向 commit 的指针
HEAD
「指向指针的指针」，告诉 Git 你当前在哪个分支上
一个反直觉的细节

老师展示 tree 里同一个目录 / 下有两个条目：755 hello 与 644 hello.c。权限位被完整保存在 tree 里——这就是为什么 Git 能正确恢复可执行位，而 zip 包常常丢掉它。

3.9原子变更：为什么提交要小

90:00

进入全章的理论总结。老师先给了 best practice 的一个例子——Commit often, Perfect later, Publish once——然后解释为什么。

他还展示了另一个可以「惊人的注意力」观察到的事实：你们的项目托管在 GitHub 或 GitLab 上时，agent 会试图调用 gh 或 glab 命令，失败了就回退到古法编程、开始写裸 git 命令。原因是 GitHub 太流行了，值得为它做一个单独的命令行工具，用来管理那些不随 Git tree 持久化的东西（issue、评论、指派等）。

一段关于工程细节的感慨

老师又举了一个 Markdown 的排版规范：中英文之间要有空格（他称之为「盘古之白」）。他说「对我来说这是肌肉记忆」，最难受的是一个文档里有的地方有、有的地方没有——「你哪怕保持一致我都认为你在遵循某一种 convention。」

落点是：这些工程细节其实都是为了工程师在面对更大项目的时候，有一种一致性和规范。代码以同样的方式排版，文档也以同样的方式排版，人维护起来会更好。

3.10linear history 与工程细节

93:00

老师提到一个正在变成主流的实践：要求整个 commit history 是线性的（linear history）。理由是「反正都是 AI，它 resolve 和 rebase 都很容易」。

传统做法
保留分叉与合并的多父结构，如实记录协作过程
linear history
通过 rebase / squash，让历史看起来是一条直线
好处
更易于追溯；对 cherry-pick 和 blame 更友好；AI 维护项目时更省 token（有些文件可以不用读）
代价
「也不完全是好处」——丢失了真实的分叉结构
老师的立场
「在无限大能力的模型到来之前，这件事情都是好的」
Git 的本质（本讲最重要的一句话）

我们要把项目组织成用 atomic change 推进的快照。这是你们今天要记住的事情，然后所有的一切都是从这句话里面推出来的。

3.11我是怎么管理一个项目的

97:00

章末，老师分享了自己的实际工作流。这部分很有价值，因为它把「原子变更」的原则落到了具体的多 agent 协作上。

老师的工作流 · 两个阶段
  1. 架构设计阶段：单线程 + 高智力模型。先用一个智力比较高的模型，一对一讨论架构。
    「如果你的软件设计得不好，你后面就是无穷的迭代。」
  2. 定好接口：把组件做成 pure function。老师说他把绝大部分接口都设置成了纯函数（包括 trace），并定义一个标准的结果展开方式。
  3. 全局状态收拢到一处。所有互相影响的状态都注册到一个全局的地方——「这样一个 playground，基本上核心的共享状态也就只有十几行」。
  4. 要求 agent 只看接口、不看实现。「禁止看任何库函数的实现」，于是 agent 很省上下文，几万个 token 就能做出一个 playground。
  5. 开多个 terminal 并行。架构完成后开三个 agent，哪里不满意就骂它；在旁边屏幕上放一个浏览器实时刷新，眼看着它一点点变好。
