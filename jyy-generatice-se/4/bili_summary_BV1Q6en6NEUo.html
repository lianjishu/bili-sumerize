01

重新设计版本管理系统

00:00 – 35:53

这一章不讲「怎么用 Git」，而是问一个更狠的问题：如果我们今天从零开始设计一个版本管理系统，它会是什么样？讲师的切入点是——文件系统不是组织项目的正确方式，而现有 VCS 的每一处设计（暂存区、非线性历史、命令命名）都是过去几十年人类工作方式的路径依赖。

1.1lab 1 与「会成长的个人助手」

00:00

承接上一讲的版本管理，这一周发布了第一个 lab：会成长的个人助手（a personal assistant that grows）。要求刻意写得非常宽松——不限，你想怎么做就怎么做，最好能用 webcode 的方式做出来。讲师说今天会留出时间，自己现场 webcode 一个，并把「直接让 AI 从零开始写」会遇到的小坑演示给大家看。

这个需求为什么选它
  • 每个同学都会需要——它对应的是「持续为你工作」这一件事，而不是一次性作业
  • 可以接到你的学习数据库：把专业课（计网、概率）的资料、研究组的论文与教科书整理成个人库
  • 也可以接个人信息：填表要姓名/学号/身份证号，讲师说这些他现在全交给 agent 了
  • 更可以接邮件：把你的邮箱和数据库关联起来，让助手替你做收件箱流水线

讲师顺带讲了一个有点残酷的小故事：疫情时他招过一个研究生，做了三年「自动填表系统」，毕业那年 ChatGPT 出现了，学生很慌，觉得三年的工作瞬间被替代。讲师说：不要紧，赶快答辩，然后就可以毕业了——世界发展就是这么快要适应。

观察点

这个 lab 的定位不是「练一个技术」，而是给你一个真实长期存在的痛点，逼你把这两节课讲的版本管理、下一节的软件架构全部用在自己身上。需求写宽，是为了让你在「自己定义需求」这一步就开始暴露问题——第 3 章会现场演示这件事有多难。

1.2AI Slop 的沼泽地与可追溯性

03:00

讲师提出问题：当 AI 生成的代码越来越多，我们会掉进一片 AI Slop 的沼泽地——代码堆得越来越厚，但没人真正理解它。而你要在这片沼泽里追溯（traceability）：某一处行为是谁引入的、为什么引入、当时的上下文是什么。

核心矛盾
AI 让「生产代码」成本骤降，但「理解代码」的成本没有降——两者之间的缺口就是 slop 的沼泽
可追溯性
每一个变更要能回答三件事：改了什么、为什么改、谁/什么时候改的
版本管理的位置
它是唯一能在时间轴上把这些信息钉住的基础设施，因此 AI 时代它只会更重要，不会消失

这里有个反直觉的关键点：AI 让写代码变便宜，反而让版本管理变得更关键。因为在人类手写代码的时代，代码量小、作者记得住；而 agent 一天能产出你过去一个月的工作量，你唯一能依赖的就是那条被认真维护的历史记录。

1.3文件系统不是组织项目的方式

10:00

这一节是第一章的思想起点。讲师的观点很直接：我们把项目组织成「文件夹套文件夹」，这其实是一种很别扭的方式。它之所以成为主流，只是因为计算机早期就是按文件系统设计的，我们从小就习惯了它。

文件系统的四个根本局限
  • 它是一棵树：一个文件只能属于一个目录，但真实世界里一个对象常常同时属于多个分类（一份论文既是「研究组」又是「本学期」）
  • 它没有时间维度：你看到的是「现在」，看不见「怎么变成现在这样的」
  • 它没有出处：一个文件是 AI 生成的、抄来的、还是自己写的，文件系统本身不知道
  • 它拍平了结构：目录层级只表达「在哪里」，不表达「是什么关系」

正是在这里，讲师引出了「带环图 → repository.db」这条线：如果把项目组织成一个有向无环图甚至带环图（一个对象可以有多个父节点），那么「一个文件同时属于多个集合」「一个文件的历史是一张图而不是一条线」这些事就自然成立了。而承载这张图的形式，就不必是文件夹，而可以是一个数据库。

1.4从带环图走到 repository.db

15:00

顺着「项目不是文件夹」往下推，讲师给出的设想是：仓库本身就应该是一个数据库（他称之为 repository.db）。你在里面存的不是「一堆文件」，而是对象与对象之间的关系——文件、版本、标签、评论、责任人，全部是表里的行，用外键和索引去表达关系。

注意讲师在这里强调的不是「数据库一定更好」，而是「文件系统只是一种历史选择」。第 3 章他会亲自演示一个反例：在没有性能瓶颈之前，他反而不建议你一开始就用数据库——因为文件系统的心智负担更低。这两处看似矛盾，其实是同一套逻辑的两端：形式要匹配你当前真正需要的能力。

1.5jujutsu：把 change 当一等公民

20:00

既然现有 Git 是路径依赖的产物，那有没有人已经按「重新设计」的思路做过了？讲师举了 Jujutsu（jj） 这个新一代版本控制系统。它的核心差异是把 change（一次变更）当成一等公民，而不是把 commit 当成「提交动作产生的结果」。

Git 的心智模型
工作区 → git add 暂存区 → git commit 落库。提交是一个动作，你要先想清楚再按下
jj 的心智模型
你始终工作在一个 change 上，它自动被记录、可以随时被改写。提交不是动作，而是一种持续状态
带来的改变
不需要「我该不该 add」「这个文件要不要提交」这类中间决策，注意力全部留给「这次变更在语义上是否是一个整体」

这个对比之所以重要，是因为它直接呼应了本讲的主线：Git 的暂存区是一个为「人类犹豫」而设计的缓冲——人类需要时间思考「我现在到底改了哪些东西」，所以给了一个可以部分提交的中间层。而如果提交者是 agent，它不存在犹豫，暂存区就变成了纯粹的负担。

1.6没有暂存区，也没有「未提交」

23:20

顺着 jj 继续推：如果 change 是一等公民，那么「未提交的修改」这个概念本身就不该存在。你在编辑器里每动一下，都是一次 change 的演化；你想把哪几个 change 合成一个、想怎么重排它们的顺序，都是对已有对象的整理，而不是对「还没进入系统的脏数据」的抢救。

概念的重新划分
  • 没有暂存区：不再需要「选一部分提交」，因为每次变更本来就被完整记录
  • 没有脏工作区：不存在「改了但没提交」的状态，所有修改都在版本树里
  • 历史可以随手改写：改写历史不是危险操作，而是日常整理（rebase 变成默认行为而非例外）
  • 代价：这套模型对人的直觉是反的——你已经习惯了「提交前要检查」，突然不用检查了，反而会觉得不踏实

讲师没有在推荐你立刻换工具，他的目的是通过一个「已经存在的反例」，让你看清 Git 里哪些部分是本质、哪些只是历史包袱。这个分辨能力，恰好就是第 2 章「为 Agent 重新设计」所需要的。

1.7线性历史与 rebase

26:40

继续推演：如果改历史是日常，那么历史就应该是一条线，而不是一堆并行的分叉再被 merge 揉成一团。这就是 jj 与 Git 的另一个关键差异——通过 rebase 维护线性历史，而不是留下 merge 节点。

这里有个容易忽略的工程含义：线性历史让「二分定位 bug」变得简单。在分叉历史里，git bisect 要在多条线上跳，语义是模糊的；在线性历史里，它就是在一个数组上二分，非常干净。这一点在第 2 章「Agent 时代 bisect 会失效」那里还会再绕回来。

1.8肌肉记忆造成的路径依赖

31:40

第一章的收尾，讲师点出为什么这些「明显更合理」的设计没有普及：肌肉记忆与路径依赖。你已经在 Git 上敲了十年命令，团队里的每个人都默认了这套流程；换一套模型的成本，远大于它带来的那点优雅。

不是 Git 的设计有多完美，而是所有人都会用 Git。

—— 讲师对「工具演进为什么慢」的解释
本章结论
  • 形式要匹配需求：文件系统、数据库、图结构，各自适合不同的组织诉求，没有绝对优劣
  • 现有 VCS 大量设计是「为人类服务」的：暂存区缓冲犹豫、merge 保留并行工作、命令命名迁移自 SVN 时代
  • 路径依赖是最大的阻力：技术上的最优解常常输给习惯上的默认解
  • 但 Agent 的出现，可能会打破这种惯性——因为提交者的形态变了，为人类设计的那套假设就集体失效了。这正好是第 2 章的命题
02

为 Agent 设计版本管理系统

35:53 – 63:48

第一章讲的是「现有工具为什么长这样」。这一章换成第一性原理：如果提交者不是人、而是每秒能提交一次的 Agent，版本管理系统该怎么重新设计？讲师的答案落在一个从操作系统和数据库课程里搬来的概念上——乐观并发控制 → 悲观锁。

2.1现有 VCS 都假设用户是人

35:53

讲师先把话说透：Git 里的每一个设计，背后都站着一个「人类用户」的假设。把这个假设抽掉，很多设计就失去了理由。

假设①：你是单线程的
一个时刻你只能在一处工作，所以「工作区」是唯一的，切换分支要 checkout——本质是在单线程里切换上下文
假设②：提交是稀缺的
提交意味着「我做完了一段有意义的工作」，所以要写 message、要 review、要慎重
假设③：你需要被保护
暂存区、--force 警告、危险操作二次确认，都是在防止人类手滑
假设④：责任可以归属
git blame 之所以有意义，是因为「人」要为代码负责，会被批评、会被追责

这四个假设在人类团队里都成立。但讲师指出，它们没有一条对 Agent 成立——而这就是重新设计的全部空间。

2.2人的通信带宽只有「十分钟一次提交」

38:20

最核心的一个洞察在这里。讲师说：人类协作的瓶颈从来不在算力，而在通信带宽。一个人完成一小步、想清楚、写成提交信息、和别人同步，这一圈下来大概要十分钟。所以 Git 的整个节奏是围绕「十分钟一次提交」这个带宽设计的。

讲师用操作系统的类比把这件事说清楚：多个 Agent 就像多个线程在并发访问共享内存。你在操作系统课上学的那些东西——临界区、互斥锁、读者写者问题——在这里全部重新出现，只是被换了一个宿主。

2.3乐观并发控制是怎么来的

43:20

讲师明确给 Git 的并发模型定了性：Git 是乐观并发控制（optimistic concurrency control）。它的假设是——冲突很少发生，所以先让大家放手干，等真要合并时再处理冲突；冲突了就让人类坐下来手动解决。

乐观并发的完整链条
  • 假设冲突罕见：每个人都基于自己的副本工作，互不打扰
  • 不设锁：没人会阻止你修改任何文件
  • 冲突延迟到合并时暴露：<<<<<<< 标记就是冲突现场
  • 解决成本由人承担：冲突需要人判断语义，机器给不出正确答案

这套模型在人类团队里非常合算：冲突少、解冲突的人有业务上下文。但讲师指出——这个前提正在被打破。当十个 Agent 同时在一个仓库里干活，它们会频繁改到同一个文件；而「坐下来手动解冲突」这件事，Agent 做得并不比人靠谱，尤其当冲突涉及跨文件的设计意图时。

2.4数据库里的乐观锁与悲观锁

48:20

为了讲清「另一种选择」，讲师直接调用了数据库课的知识：事务并发控制里的乐观锁与悲观锁。

维度乐观锁（optimistic）悲观锁（pessimistic）
核心假设冲突很少发生冲突很可能发生
做法先干活，提交时校验版本号/时间戳干活前先加锁，别人只能等
冲突代价回滚重做（要能重放）等待（要能等，且不会死锁）
适合场景读多写少、冲突概率低写多、冲突概率高、重做成本高
对应到 VCSGit 的模型讲师设想的 Agent 模型

讲师特别强调为什么数据库课要教这两样：因为这两条路各自有适用面，你必须知道「当时的人为什么选乐观/悲观」，才能在场景变化时做出正确迁移。而当前的场景变化正是——提交者从低频人类变成了高频 Agent。

2.5Agent 时代需要悲观锁

51:40

结论在这里给出：当提交者变成 Agent，乐观并发控制的代价会反超悲观锁。原因有三条：

为什么会反转
  1. 冲突从偶发变常态：多 Agent 同仓库并发，改到同一文件的概率大幅上升
  2. 「回滚重做」对 Agent 不便宜：Agent 的一次尝试可能消耗大量 token 与上下文，重做等于把成本乘以冲突次数
  3. Agent 不会「坐下来好好谈」：人类解冲突靠的是对业务的共同理解，Agent 缺少这层共享上下文，冲突解决质量不稳定
讲师的关键论断

「即使它慢一点，等一会儿总比重做一遍便宜。」——用等待换确定性，这是悲观锁的本质交易。在人手不足、Agent 却可以无限并行的时代，让部分 Agent 排队，反而比让它们全部冲上去然后大面积冲突更划算。

注意这不是「悲观锁一定更好」，而是前提变了，最优解跟着变。讲师特意点明：这套推理链（识别假设 → 发现假设失效 → 换模型）本身就是软件工程最核心的能力，而不是哪个具体工具的知识。

2.6git worktree：一个目录还不够

55:50

顺着「多 Agent 并行」往下，讲师提到了一个很具体的工程点：git worktree。它允许同一个仓库挂出多个工作目录，每个目录检出不同的分支——这样多个 Agent 就能各自占据一个目录，互不干扰地工作。

一个容易踩的细节

在 worktree 模式下，.git 不再是目录，而是一个文件，里面写着 gitdir: /path/to/main/.git/worktrees/xxx。如果你写脚本时习惯性判断「.git 是不是目录」，就会在多 worktree 环境下判断错误。判断仓库是否存在，应该用 git rev-parse --git-dir。

2.7Agent 的 blame 和 git bisect 都会失效

58:40

讲师接着点名了两类「人类专用」的能力，在 Agent 时代会失去意义：

git blame
逐行追问「这行是谁写的」。它的价值来自人的可追责性——人会被批评、会被扣分、会被开除。Agent 不会被解雇，也不会「因为怕被 blame 而写得更好」，所以 blame 的激励意义消失
git bisect
二分查找引入 bug 的提交。它依赖「提交粒度稳定、每个提交都能跑」。但 Agent 每秒提交一次时，一次逻辑变更会被切成几十个提交，「哪一个提交引入了 bug」这个问题的粒度就不成立了
共同点
它们都建立在「提交是有意义的、可读的、数量不多的」之上；当提交密度爆炸，这个前提塌了

这里讲师补了一句很值得回味的话：这些工具不是「没用」，而是「衡量的对象变了」。在 Agent 团队里，你关心的不再是「谁写的」，而是「这段逻辑是哪次任务推进带来的、当时的目标是什么」——这又回到了第 1 章那个词：可追溯性，只是追溯的锚点从「人」换成了「任务意图」。

如果 blame 不需要了，那要什么
  • 要的是「这次变更隶属哪个任务」，而不是「这行代码隶属哪个人」
  • 要的是变更的意图记录（为什么要做这件事），而不是变更的作者
  • 要的是可以被机器消费的结构化历史——因为下一个读这段历史的，很可能也是 Agent

2.8版本控制是工具，团队管理才是难题

63:48

第二章的收尾，也是全讲的第一个转折点。讲师把话拉回到「软件工程为什么还存在」：版本控制终究只是工具，真正难的是团队管理与任务分解。

本章结论
  • Git 的模型 = 乐观并发控制，它的每个假设都指向「低频提交的人类」
  • Agent 把提交频率提高几个数量级，乐观策略的冲突代价随之反超，悲观锁重新变得合理
  • worktree 解决并行，不解决冲突；blame 与 bisect 的价值基础被动摇
  • 但工具层面的重新设计并不能拯救软件工程——真正的瓶颈是「怎么把一个大目标拆成可以并行的子任务」。这件事，沟通关系是平方级增长的，目前 AI 还不会做

讲师在这里给了一个很实在的建议：现在就把自己当成主 agent，去练习「怎么把任务分解给 2 个、3 个 slave」。他说自己前面给了个不好的示范（随手创建两个 slave 就开干），真正成熟的做法是——在写下第一行代码之前，先想清楚协作怎么做、项目怎么管、每天什么时候同步。这句铺垫，直接接到了第 3 章的现场演示。

03

从零开始一个新项目

63:48 – 98:29

前两章都在「设计」，这一章讲师直接打开终端，现场 webcode 一个个人助手——然后把它翻的车一帧一帧讲给你看。核心结论是那句经典的产品箴言：最大的风险是做出了没人想要的东西；而对抗它的方法只有一个——先做出最小的、能被验证的那一小步。

3.1汉诺塔的单向限制与递归

65:40

讲师先插了一个看似跑题的例子——只能朝一个方向移动的汉诺塔。这是他在网上看到的、据说出现在小学生编程考级里的题：盘子的移动方向被限制为单一方向，不能来回。

为什么讲这个

它其实是后面那个商业模式小例子的「内容素材」。讲师说这道题很难，但最优解有漂亮的结构：考虑最大的盘子，它总是「向右再向右」，这个移动次数不可再少；剩下的子问题基于归纳法（inductive）也是最优的。一个递归结构一旦想对，整道题就塌了。

他顺手演示了自己写的一个小程序：可编辑代码、可视化随代码运动。如果你把代码写错——比如试图把大盘子挪到小盘子上——可视化会立刻停在出错的那条语句，学生一眼就能找到 bug。这个「代码 ↔ 可视化实时联动」的做法，是后面整套商业设计的起点。

3.2把 playground 卖给小学生

73:40

讲师把它当成一个产品来推演：如果要把这个 Python playground 卖给小学生，怎么挣钱？

免费的部分
  1. 一个纯粹的 playground：能写代码、能运行、可视化跟着动
  2. 出错时定位到具体语句，帮助找 bug
  3. 尽量以很低的成本提供给小朋友（讲师特意强调「开玩笑的，我们还是尽可能便宜」）

增值的部分是 AI 助教：小孩子实在做不下去时点一下「我要助教」，此时 DeepSeek 的 token 开始燃烧，费用记在账户上。讲师说你完全可以收比 DeepSeek 原价更贵的 token 费——因为 prompt 是你独门的：「我作为一个有经验的老教师，可以把自己蒸馏成 prompt」，能敏锐判断这个小朋友卡在哪、给个性化指导。卖的不是模型，是教学经验。

这一步的意义

注意这个设计的精妙处：它就是第 3 章后面「MVP」思路的正面样板——先做一个能独立运行、价值成立的最小闭环（playground），再挂一个可选的增值模块（AI 助教）。对比之下，第 3.5 节那个被 AI 一次生成出来的「教育系统」，就是反面样板。

3.3GPT 给的标准架构，为什么我不喜欢

74:30

要做增值服务就得做信息系统。讲师让学生先和 AI 聊了一版设计，他自己也让 GPT 梳理了一遍需求。GPT 给的是教科书级答案：

GPT 的方案
一个 API 应用 + 一个关系数据库 + 一个对象存储；需要逐题点评时再加后台任务进程
数据划分
数据库存关系与记录，大课程包与完整轨迹放对象存储；任务量小时，数据库里一张任务表就够
讲师评价
「就是一个非常正常的」——如果这是软件工程课的作业，这个答案完全正确、挑不出错

但讲师说：「我不喜欢这个设计。」为什么？他先举了 Overleaf 的例子：Overleaf 可以把项目导出成一个 Git 仓库，于是他能把要改的学生论文 clone 到本地，直接开 Codex 起 sub-agent，逐个 .tex 文件修语法错误，一条长 prompt 下来论文就改好了——不需要忍受网页界面。

这就引出了他的核心反问：pico playground 为什么不是「学生每改一次代码，就自动做一次 git commit」？申请 AI 助教的时候转圈圈，正好可以在那个提交上产生一个分叉，把 AI 的点评作为 comment 挂上去。

3.4用版本管理替代数据库

76:40

讲师把账算得很清楚：产生一个 Git 提交 + 在它上挂一个 comment 的成本，远远小于把剩下所有东西持久化进数据库的成本——前者几乎可以忽略不计。

这里讲师再次强调一个元观点：「你们学任何东西都是有用的。」学 Git 有用、学多 Agent 管理有用——因为两条知识交叉时，你才会想到一个和别人不一样的设计（用版本管理做信息系统）。这正是这一讲存在的理由。

3.5现场 webcode：不加约束地丢一个需求

79:00

到这里讲师说：「我们真的可以干一件事了。」他先给出一条铁律——项目早期阶段你肯定不能用 multi-agent，你就是包工头：找一个你手上能力最强的 agent，和它多轮对话。

包工头模式

「你们现在开始干，就比什么都要好。」讲师决定当场打开课程作业，把需求直接丢给 agent，完全没有事先准备。他给了一个很开放的、类似讨论稿的需求，然后观察它会发生什么。

第一件被观察到的事，是 AI 的直觉和人的直觉不一样：一线模型收到复杂任务时会先进入 plan mode——先跟你确认事实，再生成一个 workflow。讲师顺手讲了 Claude Code 的实现细节：它需要执行复杂任务时，会生成一段 TypeScript，里面有一个叫 Agent 的函数，函数体是自然语言，甚至可以有循环——用它来组织 workflow。

上下文工程最危险的一点（本讲重点）

你提示词里的每一个词，self-attention 都会看到它。因为 AI 现在已经被训练成了「prompt 的填狗」，它有一种没有办法往外拉的倾向——必须遵循你的指令。所以当需求本身是一个开放的讨论稿时，它会过度遵循：最终生成一个「确实满足了指令、但完全不是你想要的」东西。

讲师特别点出那个实验需求的言外之意：实现一个「持续为你工作的个人助手」——这一句最重要，其他都是解读。但模型不会替你判断哪一句重要，它会平等地对待每一个字。

3.6它做对了每一步，却做出了我不要的东西

84:20

结果出来了。讲师先说自己真正的需求是什么：一个比较好的学习助手——能从外网自动收集数据、以层次化方式归档、再给出一个不错的界面，还能根据他的进度来安排学习。然后他去看 agent 做出来的东西。

做出来的
一个相当完整的「教育系统」：入口层 / 编排层 / 能力层 / 数据层，引擎全是真代码，手机端是真 HTTP 服务，Pi 是集成的，模拟部分自洽
讲师的反应
「我就不试图 review 了」——它还做了一个提交，但甚至没有先创建一个 Git repository，直接一把梭
关键诊断
从 readme.md 来看，它做的所有事情都是对的，没有一个错误；但最终得到了一个你不想要的东西

讲师解释了这个 gap 的来源：他提「填表」的时候，真正需要的是一个 browser-use agent——能在各种网页上替他处理事情，「一号」（某个填表入口）只是测试出口。但因为需求里出现了「教育系统」的措辞，agent 就真的去实现教育系统了。他的原话是：

你的 intent、你的 specification、你的 intention 是有巨大 gap 的。当你一旦模型看到说「你要实现这个」，它就真的是真的去实现它了。

—— 讲师对「为什么 AI 一定产出 slop」的解释

从这一刻开始，讲师用两句英文格言把结论钉死：

两条格言
  • The biggest risk in product development is building something nobody wants.　产品开发最大的风险，是做出没人想要的东西——而 AI 恰好非常擅长高效地做出这种东西
  • 在没想清楚之前，先别写第一行代码。讲师说如果他是成熟的产品经理，老板丢来一个想法，他一定会先跟团队讨论「项目怎么管」——甚至在自己写下第一行代码之前，就要把「协作怎么做、每天什么时候开会」谈好。而 agent 很好玩，它直接上手就做

有意思的是，讲师在这里自己承认：他也没跟 agent 讲「要先建仓库」。如果换成 Codex 可能会主动初始化、或反问「这个项目该怎么管理」——但默认行为通常不是这样，你得自己说。这也是本讲为什么反复强调「包工头要先想清楚」。

3.7MVP：先卖出一小步

91:30

讲师给出正面做法：MVP（minimum viable product，最小可行产品）。它的作用不是「少做点」，而是逼你想清楚哪些需求是你绝对要的。

从「大而全」倒推 MVP
  1. 先问本质：如果我要一个个人助手，我最想要的是什么？——提升学习效率 + 提升工作效率
  2. 再问第一步：为了实现这两条，我第一个必须有的 feature 是什么？——能从外网收集数据、层次化归档、给出好用的界面
  3. 然后砍掉一切不直接支撑它的东西：第一个 MVP 里可以没有任何数据库
  4. 因为文件系统膨胀时，你可以直接跟 agent 说「按照这个数据的组织，帮我抽象出一个数据库」——问题就结束了

讲师把「要不要数据库」这件事讲得特别细：一旦你带上数据库，每次重构都要让 agent 做 database migration；而文件系统不一样——你自己就能在文件管理器里调整目录结构，逐渐梳理到舒服的形状。调文件和调 database schema，心智负担完全不同。

两条开发路径（讲师的原话对比）
  • 路径 A（反面）：上来就是一个大的，好几大步把需求都实现完，然后拖着技术债不断往后迭代、加功能加功能
  • 路径 B（正面）：从最小的开始，「得到一个特别精巧的东西」，然后在遇到性能瓶颈之前，都不迁移到任何数据库

这里与第 1 章「文件系统不是组织项目的方式」形成了刻意的张力：长期看图和数据库更本质，但短期看文件系统的低心智负担更划算。讲师用 Git 管理的例子收尾——当学生的提交都用 Git 管起来之后，很多事情都变得非常容易，他自己控制起来也轻松很多。

3.8文件系统与数据库的心智负担

95:00

这一节讲师把「为什么先用文件系统」从直觉上升成一条可复用的判断标准：人类对直观的东西已经训练得非常舒服了。

讲师总结成一句很朴素的话：用最简单的方式帮你把「学习资料的进入、通知消息的进入」这些事管起来——先让它跑起来，形式以后可以再换。

3.9我自己的邮件 agent 连数据库都没有

96:00

为了证明「不用数据库」不是纸上谈兵，讲师晒了自己在用的邮件 agent 的真实流程——到现场为止都没有用任何数据库：

他的邮件流水线
  1. agent 收他的邮箱，把 email id 写到一个共享云盘同步目录里
  2. 每个 email id 里带着 agent 解析出的东西：回复草稿、邮件分类、是不是垃圾邮件
  3. 再由下一级流水线去处理这些中间产物
  4. 整个系统他只关心一件事：有哪几级流水线、它们怎么协作、哪些东西通过云盘传递

然后他当场演示了一次真实的「需求变更」：「我很喜欢我的云盘，是不是引入云盘要做一些架构的修改？我希望邮件资料等都和云盘保持同步。」——这就是一个典型的需求更改，于是他把架构丢给 agent 让它看看好不好。

这引出了「什么是好的软件架构」

讲师的定义很直接：在当前需求下能正常工作，不算好架构。真正要问的是——当需求发生变更的时候，你相应做出的那个变化，是局部的、还是摧毁性的？是背上一个技术债，还是平滑演进？他的 agent 当前设计里有一个 system.db，把个人资料、邮件归档、索引草稿全放进去；现阶段「看起来还不会引起很大问题」，但随着项目推进就要看了。

这也把话题自然过渡到了下一节（也是下一讲的主题）：软件架构与构造。讲师把「能不能以不变应万变」定为核心问题——你设计的架构，能不能抵抗未来需求发生根本性的变化？ AI 助教可能是文字助教、可能是图像助教，可能有交互、可能没有；需求在不停地变，而架构的变化要尽量小。这一条，数据库课不教、操作系统课也不教，是软件工程独有的。

3.10结尾：早期的 prompt 影响最大

97:40

全讲的最后，讲师收回到两句可以带走的话。

版本管理做的三件事（在 Agent 时代同样成立）
  • 记住现在：你必须有一个 Repository，把文件管起来——不管是数据库形式，还是今天的 C/C++/Python/JavaScript 项目形式
  • 记住历史：有一天你不要某个东西了、或者删掉了某个东西，它还能被捞回来；你也能看见「怎么演进到这一点、在哪里失败了、又从哪里拐向另一条正确路线」
  • 记住教训：这些 lessons 不停地警示你下一步该怎么做——从第一步开始，每次只向前迈一小步

然后是本讲最后一句，也是贯穿全讲的核心：你早期的 prompt，对整个项目的走向影响是最大的。每一次最早的输入（哪怕是直接把 readme 丢过去、说「我要做一个 MVP」）都会对项目造成很大的影响。这也解释了为什么第 3.5–3.6 节那场「翻车演示」值得花二十分钟：它不是段子，它是在展示一条极具破坏力的因果链——含糊的早期输入 → agent 过度遵循 → 完整的错误产品。

好，今天下课。我下一节课就（这周日）会进入软件架构和构造的内容。

把这一讲串起来看
